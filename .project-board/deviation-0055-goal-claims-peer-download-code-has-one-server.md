## Суть

CONCEPT.md (заголовок раздела переименован в ходе idea-0046) утверждает:

> каждый участник поднимает свой бэкенд со своим торрент-клиентом и тянет данные
> из роя сам. Сервер хоста — это точка встречи … а **медиатрафик не проходит**.

Код этого не делает. У клиента **один** базовый URL на всё.

`frontend/src/networkmanager.cpp:95` — `m_serverUrl` инициализируется
`http://localhost:8889` и подставляется в `safeUrl(...)` для торрентов, комнат,
синхронизации и SSE (строки 893, 912, 934, 982). Тот же `m_serverUrl` строит
`streamUrl()` (строка 457) — то есть URL медиапотока.

Отсюда две реальные топологии, и обе расходятся с целью:

| режим | что происходит | расхождение |
|---|---|---|
| без `--server-url` (по умолчанию) | клиент поднимает свой бэкенд на localhost и ходит только в него | две машины создают комнаты в **разных** бэкендах и никогда не видят друг друга — совместный просмотр не работает вообще |
| `--server-url http://host:8889` | гость направляет всё, включая `streamUrl()`, на сервер хоста; свой бэкенд не поднимается | у гостя нет торрент-клиента, mpv тянет байты **с сервера хоста** — медиа идёт через хост |

То есть работающая топология — ровно та, от которой отказались: медиа через
хост-сервер. Именно это и утверждает `.github/SECURITY.md#What the Server Sees`,
проверенный против кода: «**Media data passes through the server.** … The
desktop app has no torrent client of its own».

Частично реализованная часть idea-0046 реальна: `Room.TorrentID`,
`torrentId` в `POST /rooms` и `POST /rooms/join` с проверкой несовпадения есть.
Но привязка бесполезна: гость в режиме `--server-url` обращается к чужому
бэкенду, где торрент лежит один — на хосте.

Прежняя формулировка расхождения жила на доске как deviation-0035 и была
объявлена закрытой сменой цели в CHANGELOG («This resolves deviation-0035»).
Закрыта она была сменой формулировки цели, а не кодом.

## Обсуждение

2026-10-14: Найдено сверкой. Это самое крупное расхождение в проекте: оно
затрагивает центральную задумку, а не отдельный модуль.

Чинить молча нельзя в любую сторону. Либо код доводится до цели (клиент
разделяет control-plane URL и media-plane URL, поднимает свой бэкенд всегда и
качает торрент сам — это архитектурная правка фронтенда), либо цель
формулируется честно под то, что реально работает. Оба варианта требуют
решения владельца, поэтому карточка, а не правка.

До решения расходится и документация: CONCEPT.md говорит одно, SECURITY.md —
другое, а код соответствует SECURITY.md.

2026-10-14: **Решение владельца — «данные у каждого свои».** Цель остаётся в
формулировке idea-0046, код доводится до неё: сервер хоста остаётся плоскостью
управления (команды синка, ростер, передача magnet гостю), а каждый участник
качает из роя сам. ADR «сервер-брокер через SSE против WebRTC P2P» не
пересматривается — SSE-брокер остаётся для плоскости управления, меняется
только плоскость данных.

Очерёдность, зафиксированная владельцем в этой же сессии: сначала довести
рабочее дерево до коммиттабельного состояния (`bug-0052`, `bug-0053`,
`bug-0056`), затем сама топология, и только после неё дистрибуция
(`idea-0026`). Карточка остаётся открытой до появления кода: правки цели не
требуется — она уже сформулирована верно, отстаёт код.
