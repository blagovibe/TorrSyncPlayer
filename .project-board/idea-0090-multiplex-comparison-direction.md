## Суть

Сравнение TorrSyncPlayer с pojntfx/multiplex (GTK4/Linux-only, hTorrent +
weron, Flathub, AGPL-3.0) показало: ядро совпадает (mpv отдельным процессом
по JSON IPC, код приглашения `community:password:key`, каждый тянет из роя
сам, ремотинг через hTorrent-шлюз), а расхождения — в транспорте, покрытии
платформ, UX-полировке и дистрибуции.

TorrSyncPlayer сильнее в: трёх платформах (Fyne против GTK4-only), своём
HTTP API со Swagger/Prometheus, приоритизации кусков по позиции, per-peer
выборе файла, владении/видимости торрентов, реестре с источником
(magnet/bytes), тестах (сценарии против реального бинарника, pact,
race, mutation) и методологии project-docs.

Отстаёт в: завершённости libp2p-транспланта (слайсы 1–2 в дереве, autorelay
без peer source — только прямые + hole punching, см. idea-0087), UX-потоке
(magnet → выбор файла → confirm → preparing MB/MB + peers → seeker
elapsed/remaining, volume, fullscreen, media info, тосты join/leave,
watching-with, error/warning/shortcuts диалоги), упаковке (AppImage/zip/DMG
зелёные на rc, но релиз не опубликован; Winget и автообновление открыты,
см. idea-0026) и переводах (ru/en каталог руками против gettext/Weblate).

Кандидат: зафиксировать очередь до «идеального рабочего состояния» —
сначала зелёный трансплант + реле, затем UX-паритет с multiplex-туториалом,
затем релиз v1.2.0 + Winget/обновления. Правок цели и способа пока нет —
только кандидат на доске.
