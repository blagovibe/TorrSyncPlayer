## Суть

Способ обещает «Go 1.26+» в двух местах (`DEV.md`, «Зависимости» и
«Технологический стек»), README повторяет, `go.mod` обоих модулей объявляет
`go 1.26.0`. Пайплайн при этом пинит `1.27.3`
(`.github/workflows/ci.yml`, `release.yml:9`, `security.yml`, `codeql.yml`), и
журнал объясняет почему: `govulncheck` нашёл уязвимость в `crypto/x509`
стандартной библиотеки, исправленную в `go1.27.3` (`CHANGELOG.md:171–178`).

Значит, человек, который собирает по документации на Go 1.26, собирает
приложение с известной уязвимостью в стандартной библиотеке — а способ при этом
утверждает, что «версия Go закреплена в `GO_VERSION` во всех workflow — это
единственное место, где она меняется».

## Обсуждение

2026-10-23: Найдено аудитом. Проверено чтением `DEV.md` (разделы «Зависимости»,
«Технологический стек»), `README.md`, обоих `go.mod` и всех workflow. Лечение:
поднять минимум в способе и README до 1.27.3 (или до версии, где уязвимость
закрыта) и, если нужно, в `go`-директиве; это правка способа по правилу
изменения, а не молчаливая правка текста.
