## Суть

Скачанный с GitHub Release v0.4.4 (и v0.4.3) `TorrSyncPlayer.exe` не
запускается на чистой Windows-системе. Три последовательных системных
окна (скриншоты владельца, 2026-11-15):

- «libstdc++-6.dll»
- «libgcc_s_seh-1.dll»
- «libwinpthread-1.dll»

То есть исполняемый файл импортирует рантайм MinGW-w64, которого нет у
пользователя. CI и Windows-раннеру эти DLL доступны; настоящего
пользователя приложение падает на первом же системном вызове.

Предварительная причина: внешняя линковка Файне-приложения против MinGW не
прошла `-extldflags` со `-static` (полная статическая линковка
GCC-рантайма), а в release-zip DLL не положены рядом с exe. Ожидаемое
поведение («скачай файл под свою систему — и запусти») нарушено с первых
релизов; CI-зелёный вводит в заблуждение каждый раз, потому что на
runner'е эти файлы всегда есть.

Отдельно отмечать для будущих сезонов: то же самое по классу — сборки для
Linux, сделанные на ubuntu-22.04 (glibc 2.35), не обязаны запускаться у
пользователей со старшей glibc (20.04 и ниже) — AppImage не решает это сам
по себе. macOS этот класс не затрагивает (системный libSystem/libc++
есть всегда).

## Обсуждение

2026-11-15: Найдено владельцем на чистой машине сразу после v0.4.4. Это же
отказавшая premises: закрытие idea-0159 решением «релиз — достаточное
свидетельство» опиралось на то, что артефакт хоть где-то запускался; теперь
известно, что на самой массовой платформе — нет. Отмечаем: тест
«собралось» больше не принимается как достаточный аргумент вне
CI-раннера.
