## Суть

Одно из смыслов вопроса «встройте плеер» — не чинить поиск, а держать mpv
внутри адресного пространства приложения (libmpv через cgo), без внешнего
процесса и без зависимости от PATH вовсе.

Что это влечёт (оценка, не план):

- малая или большая миграция транспорта: сегодня приложение говорит с mpv по
  его JSON IPC как с отдельным процессом (окна mpv — экран, наше окно —
  пульт); libmpv спрягает плеер с нашим GL-контекстом совершенно иначе
  (обычный путь — `--wid=<чужое окно>` либо GL-вывод в нашу область; управлять
  позициями/паузой потребуется через libmpv API, а не JSON IPC);
- сборка под три ОС через cgo+MinGW/xcode — тот самый класс боли, из-за
  которого проект уже ушёл с MSVC; libmpv-заголовки у нас одинаковые
  только под линукс-пути, дальше — ручная упаковка и пиннинг;
- лицензионный груз: линковка против LGPL/GPL-кода libmpv требует
  отдавать исходники той части, что линкуется (у нас MIT — это отдельная
  работа по NOTICE/совместимости, ее нельзя «замечательным текстом» закрыть);
- что она даст: ничего пользователю не видимого — то же «смотрю фильм»,
  без IPC-сокета, чуть меньше задержек на семафоре, одна зависимость меньше
  как процесс. Цена — самая большая в списке вариантов.

Заметки по вариантам меньшей цены (зафиксированы, чтобы не забыть):

- чинить поиск бандла — bug-0181 (сделано по умолчанию, если решим так);
- веб-вью / HTML5 (WebView2/WebKitGTK/WKWebView): плеер «встроен», но кодек-
  покрытие хуже (MKV/AC3/DTS/HEVC/AV1 — на милость ОС);
- GStreamer: GLib+OO bundle веса больше, чем выигрыша, по сравнению с mpv;
- ffmpeg/libav непосредственно: вершина переписывания, не вариант.

## Обсуждение

2026-11-15: Заведено после вопроса владельца: «не нравится, что нужно внешне
устанавливать mpv». Сырьё, решение не принято; архитектура сейчас верно
выбирает внешний процесс (три платформы, один транспорт, ноль линковки).
