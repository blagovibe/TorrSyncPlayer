## Суть

Бэкенд занимает один номер двумя слушателями: HTTP по TCP и libp2p по UDP.
И `backend.PickFreePort()`, и `freePort` в интеграционном харнессе спрашивали
систему только про TCP.

Windows держит целые диапазоны UDP-портов для себя (WSL, Hyper-V, Docker
Desktop). Bind внутри такого диапазона отклоняется с WSAEACCES —
«An attempt was made to access a socket in a way forbidden by its access
permissions» — а не с «занято». Порт, свободный по TCP, оказывается
непригодным, и никто нигде не проверяет, что он годится и для UDP.

Поймал `Test Frontend (windows-latest)`: `TestARoomWithoutAServer` — «the
backend never became ready», а в логе бэкенда
`subsequent listen: listen udp4 :64275: bind: ... access permissions`.

## Почему это не только про тесты

То же самое в `backend.PickFreePort()`, то есть в приложении. На машине с
WSL или Hyper-V (то есть почти везде, где стоит инструмент для разработки)
приложение изредка **не стартует**: бэкенд умирает на подъёме, причина есть
только в логе, а человек видит окно, которое не открылось. Ровно тот класс
дефекта, ради которого в проекте есть живой прогон артефакта.

## Обсуждение

2026-10-17: Найдено CI на Windows, тем же прогоном, где до этого поймали
занятый канал (bug-0117) — две разные причины красного, обе про один и тот же
принцип: «платформа отличается, значит проверять надо иначе».

Сделано в обоих местах:

- `PickFreePort` держит TCP и UDP на одном номере одновременно, пока не найдёт
  пару, которая берётся обоими; UDP проверяется в той же форме, в какой его
  будет bind'ить libp2p (на всех интерфейсах), иначе проверка ничего не
  значит.
- `freePort` в харнессе переписан на Go и больше не зовёт `python3` через `sh`:
  во-первых, он тоже спрашивал только TCP, во-вторых, CI-раннеры не обязаны
  иметь python, и сбой в нём выглядел бы как «порт не найден».

Тесты: `TestPickedPortIsFreeForBothListeners` и `TestAFreePortIsFreeForBothListeners`
берут порт и честно bind'ят оба протокола.

Чего эти тесты не доказывают: на Linux исключающих диапазонов нет, поэтому
старый код на нём прошёл бы и новый тест не мог бы упасть на старом коде.
Красным старый код сделал windows-джоба, и закрывает это тоже она. Локально
проверено другое: собранное приложение стартует, слушает 127.0.0.1, отвечает
200 и показывает трей.
2026-10-17 (позже в тот же день): Правка не помогла — windows-джоба упала
снова, с тем же `listen udp4 :63515: bind: ... access permissions` (уже на
`TestSubtitlesTravelTheEndpoint`). Значит причина не в выборе номера, и версия
«исключающий диапазон» осталась гипотезой, а не выводом.

Чтобы не гадать третью версию, в харнесс добавлена диагностика, которая
печатается при любом падении: bind'ит ли этот порт сам тест по TCP и по UDP,
плюс на Windows — `netsh interface ipv4 show excludedportrange protocol=udp` и
вердикт, внутри ли порт какого-нибудь диапазона. Ответ читается прямо из
следующего прогона:

- если тест тоже не может заbind'ить — машина отказывает номеру, и лечится
  исключением диапазонов при выборе;
- если тест bind'ит свободно, а бэкенд — нет, причина в том, что бэкенд
  делает с сокетом, и другой порт её не уберёт вовсе.

Это как раз тот случай, где красная джоба полезнее зелёной: она отвечает на
вопрос, который чтение кода не отвечает.
