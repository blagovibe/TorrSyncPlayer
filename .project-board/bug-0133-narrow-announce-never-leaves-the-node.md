## Суть

`frontend/internal/rtc/p2p.go:453` объявляет `announceOnJoinBroadcast = false`,
и в go-libp2p-kad-dht v0.42.2 (`routing.go:398-427`) флаг `brdcst=false` означает:

```go
// add self locally
if err := dht.providerStore.AddProvider(ctx, keyMH, peer.AddrInfo{ID: dht.self}); err != nil {
    return err
}
if !brdcst {
    return nil
}
return dht.classicProvide(ctx, keyMH)
```

То есть «узкий анонс» пишет запись **в локальный store своего узла** и в сеть не
уходит ни одного байта. Комната становится видимой для другой стороны только
после широкой публикации (`p2p.go:552`, `classicProvide` → обход ближайших
пиров → `PUT_PROVIDER`), а «ближайшие пиры» у публикатора и у ищущего — разные
множества: обход спрашивает ближайших **по своей картине**. Это и написано в
комментарии `p2p.go:466-470`, и это же объясняет асимметрию, которую видно в
срывах bug-0130.

Следствия:

- DEV.md#Рандеву: свои ноды, узкий анонс и широкий следом описывает
  «узкий — мгновенно» как реальное действие в сети, которого нет;
- весь путь входа в комнату держится на широкой публикации, то есть на самой
  медленной и на самой зависимой от чужой сети части;
- DHT-путь остаётся запасным (idea-0131), и запасной путь должен работать
  не хуже основного.

Чинить кодом, а не описанием: пока флаг не реализован, документация права
(DEV.md, принцип 9) — но «права» тут только в том, что описывает цель
политики анонса, а не то, что сеть делает.

## Обсуждение

2026-10-19: Найдено при разведке по факту ошибочной модели анонса, а не по
тесту: тест на политику (`rendezvous_test.go`, `announce_retry_test.go`) пиннит
собственные константы проекта, но не семантику библиотеки. Механика
подтверждена чтением `go-libp2p-kad-dht@v0.42.2/routing.go:398-427`.

2026-10-19: Причина не «в том, что узкий анонс слабый», а в том, что его нет.
Замерами с живой машины подтверждено, что широкая публикация против публичного
DHT занимает 2m16s…2m36s — то есть всё, что стоит между двумя участниками,
сегодня — это одна медленная публикация.

2026-10-19: Что делается: запасной (DHT) путь должен публиковать так, чтобы
другая сторона нашла запись, — либо широкая публикация при входе, либо поиск
у того же набора пиров, у которого публиковал хост. Проверяется герметичным
тестом на локальном testbed'е: участник публикует, второй находит без
ожидания широкого анонса.
