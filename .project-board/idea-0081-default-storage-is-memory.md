## Суть

Способ описывает выбор: куски торрентов по умолчанию лежат **в памяти** (лимит
`--memory-capacity`, максимум 256 ГБ), на диск их кладут только явно —
`--data-dir` + `--disk-storage`, и тогда куски пишутся в `<DATA_DIR>/torrents`.

Сверка с pojntfx/multiplex показала, что референс выбрал обратное: htorrent
держит `storage.NewFileByInfoHash(<settings storage dir>)`, то есть пишет на диск
всегда, в `<storage>/Manual Downloads/<infohash>/<file>`.

Почему это вопрос, а не констатация. Пока проект запускали из исходников и
смотрели короткие файлы, память была разумным дефолтом: ничего не остаётся на
диске, ничего не надо чистить, торрент исчезает вместе с процессом. Но
«идеальное рабочее состояние» — это установленное приложение, и там дефолт
встречается с реальностью:

- фильм на 8–20 ГБ в памяти это 8–20 ГБ RAM, которых может не быть — минимум
  по `DEV.md#Системные требования` равен **8 ГБ**, то есть ровно столько,
  сколько занимает один средний фильм;
- лимит ёмкости (`--memory-capacity`) при превышении ведёт себя как отказ в
  аллокации куска, то есть поток начинает проседать, а не «скачивается дальше
  на диск»;
- после перезапуска скачивание начинается заново: `--disk-storage` даёт
  возобновление, память — нет;
- плюс ко всему субтитры (`idea-0080`) требуют пути к файлу, а у куска в памяти
  пути нет.

Что предлагается решить владельцу (нужно подтверждение — это правка способа):

1. **Дефолт сделать диском**, оставив память как опцию (`--memory-storage` или
   лимит без каталога). Для установленного приложения это поведение, которое
   не удивляет: то же, что у Multiplex и любого торрент-клиента.
2. **Оставить память дефолтом**, но поднять минимум в системных требованиях до
   размера типичного фильма либо написать в README прямо: «для фильмов
   включайте `--disk-storage`».
3. **Спросить при первом запуске** — первый торрент, которого нет в памяти:
   сложнее в реализации, зато выбор делает человек, а не документация.
