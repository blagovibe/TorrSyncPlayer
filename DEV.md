# Dev — как устроен TorrSyncPlayer

Что проект делает и зачем — в [CONCEPT.md](CONCEPT.md). Этот файл отвечает на
вопрос «как его собрать, запустить и править» и не дублирует то, что и так
выводится из кода.

## Почему здесь нет справочника API

Формы запросов и ответов **не описаны вручную**. В коде стоят аннотации
`@Router`, `@Param`, `@Success`, из которых генерируется спецификация:

- `/swagger/index.html` на запущенном сервере — интерактивный вариант;
- `backend/docs/swagger.json` и `swagger.yaml` — тот же самый OpenAPI.

Спека перегенерируется командой и проверяется в CI на свежесть: если
аннотации разошлись с файлом, сборка падает. Поэтому она не может разойтись с
кодом — а ручной справочник может и разойдётся.

Чтобы посмотреть справочник, запустите сервер и откройте `/swagger/`.
Фильтр `TRUSTED_PROXIES`, список SSE-событий и правила rate limit описаны
ниже — это то, чего в спеке нет и что из кода не выводится.

Перегенерация после правки аннотаций:

```bash
cd backend
go run github.com/swaggo/swag/cmd/swag@v1.16.6 \
  init --generalInfo cmd/server/main.go --output docs --parseDependency
```

### Чего в спеке нет: формы SSE-событий

SSE-поток — единственная часть API, которой в спеке не видно. `P2PEvent.data`
выглядит в схеме как объект без полей, и это не недоработка аннотаций: полезная
нагрузка — **объединение, выбираемое полем `type`**, а OpenAPI в том виде, в
котором его генерирует swaggo, объединений по полю не выражает. `SyncEvent`,
`PeerJoinedEvent` и `PeerLeftEvent` поэтому не появляются в спеке отдельными
определениями, хотя типы существуют и используются.

Поэтому формы событий перечислены **прозой** в описании
`GET /api/v1/rooms/{roomID}/events`, а истина — в типах:
`backend/internal/models/events.go`. Проверяет их не спек, а тесты, которые
пинят точный JSON: `models/events_test.go` — что структуры сериализуются так,
`p2p/event_payload_test.go` — что на провод уходит именно это.

Если понадобится выразить объединение машинно, вариантов три: сменить формат
на вложенный (`data.sync`, `data.peer_joined`) — это **изменение протокола** и
правка клиента; ввести кастомный `MarshalJSON` — тогда схему придётся править
руками и swaggo перестанет быть её источником; завести отдельный генерируемый
артефакт. Ни один не выбран, и менять формат молча нельзя: это ломает всех, кто
уже подключён.

## Запуск

```bash
cd backend/build
./torrsyncplayer
```

Сервер печатает в лог случайный **токен доступа** при каждом старте. Он
передаётся клиентам в заголовке `X-Access-Token`; ни аккаунтов, ни паролей, ни
регистрации нет. Флаг `--token` заменяет случайный токен фиксированным — для
развёртываний, где секретом управляют вне процесса (EnvironmentFile systemd,
runbook конфигураций). Тогда токен в лог не печатается: тот, кто его задал,
знает его и так.

### Флаги

| Флаг | Назначение |
|---|---|
| `--addr` | адрес прослушивания целиком; заменяет `:port` (например `127.0.0.1:8889`, `:9999`) |
| `--port` | порт прослушивания, если `--addr` не задан (по умолчанию `8889`) |
| `--token` | зафиксировать токен вместо случайного |
| `--data-dir` | каталог для персистентных данных |
| `--disk-storage` | писать куски торрента на диск (требует `--data-dir`) |
| `--memory-capacity` | лимит памяти под куски, до 256 ГБ |
| `--tls-cert`, `--tls-key` | сертификат и ключ для TLS |
| `--tls` | включить TLS с самоподписанным сертификатом |
| `--auto-tls` | сгенерировать временный самоподписанный сертификат |
| `--enable-profiling` | pprof |
| `--gateway-url` | адрес htorrent-шлюза; включает режим ремотинга (см. ниже) |
| `--gateway-user` | basic-auth логин к шлюзу (обязателен вместе с `--gateway-url`) |
| `--gateway-pass` | basic-auth пароль к шлюзу |
| `--gateway-ca-cert` | CA-сертификат для проверки TLS шлюза (для внутренних и самоподписанных) |

Флаги шлюза дублируются переменными окружения `GATEWAY_URL`, `GATEWAY_USER`,
`GATEWAY_PASS`, `GATEWAY_CA_CERT` — чтобы unit-файл systemd не размазывал пароль
по командной строке. `--gateway-url` без обеих частей логина и пароля
останавливает старт: иначе сервер поднялся бы и падал бы уже на первом
воспроизведении.

Разбор флагов живёт в `parseFlags(fs *flag.FlagSet, args []string)`, а не в
`flag.Parse()` на глобальном наборе: так он тестируется —
`cmd/server/main_test.go` проверяет, что `--addr` вытесняет `:port`, что
`--token` доходит до сервиса авторизации, что неизвестный флаг даёт ошибку, а не
сервер со значениями по умолчанию, и что шлюз требует пароль. `main` вызывает
`parseFlagsOrExit`: тест не должен ронять тестовый бинарник через `os.Exit`.

### Переменные окружения

`PORT`, `DATA_DIR`, `DISK_STORAGE`, `MEMORY_CAPACITY`, `LOG_LEVEL`,
`LOG_FORMAT`, `TLS_CERT`, `TLS_KEY`, `API_RATE_LIMIT`, `API_RATE_BURST`,
`CORS_ORIGINS`, `ENV`, `GO_ENV`, `TRUSTED_PROXIES`.

Адрес прослушивания и сам токен задаются **только флагами** (`--addr`,
`--token`) — переменных окружения для них нет.

`TRUSTED_PROXIES` — список CIDR, которым **доверять** заголовку
`X-Forwarded-For`. Пока переменная не задана, заголовок игнорируется
полностью: иначе любой клиент из приватной сети мог бы подменить свой
IP. Формат — `10.0.0.0/8,192.168.0.0/16`.

## Архитектура

Два приложения: Go-бэкенд и Qt/C++-фронтенд. Фронтенд не содержит
бизнес-логики — он ходит в бэкенд по HTTP и получает события комнаты по SSE.

### Бэкенд (Go)

Слои: `cmd/server` (сборка сервисов и graceful shutdown) → `internal/api`
(роутинг, обработчики, middleware) → сервисы предметной области
(`internal/*`) → `pkg/` (журнал и формирование ответов).

| Пакет | Ответственность |
|---|---|
| `internal/api` | Роутинг chi, обработчики, middleware (security headers, recovery, CORS, content-type, логирование, rate limit), константы путей |
| `internal/auth` | Per-process access token, constant-time compare, HMAC stream tickets (см. ниже) |
| `internal/torrent` | Управление торрентами, HTTP-стриминг через anacrolix/torrent |
| `internal/buffer` | Расстановка приоритетов кусков по позиции воспроизведения (now → high → normal → readahead → none) для немедленного старта |
| `internal/p2p` | Комнаты, участники, сессии; брокер событий комнаты по SSE |
| `internal/sync` | Синхронизация позиции воспроизведения по командам комнаты |
| `internal/persistence` | JSON-файлы: комнаты и состояние синхронизации |
| `internal/storage` | Хранилище кусков: в памяти (по умолчанию, с лимитом ёмкости) или на диске |
| `internal/validation` | Общая валидация входных данных (идентификаторы комнат, размеры) |
| `internal/models` | Общие типы данных и структуры ответов |
| `internal/errors` | Структурированные ошибки AppError с типом ошибки |
| `internal/metrics` | Метрики Prometheus |
| `internal/constants` | Все магические числа проекта |
| `internal/utils` | Общие утилиты (идентификаторы, Debouncer) |
| `internal/version` | Информация о версии сервера |
| `internal/interfaces.go` | Интерфейсы, через которые api обращается к сервисам |
| `internal/contract` | Pact-проверка контракта (за build-тегом `contract`) |
| `pkg/logger` | slog-журнал с контекстом операции |
| `pkg/response` | Формирование JSON-ответов |

Порядок middleware: SecurityHeaders → Recovery → CORS → ContentType →
Logger → RateLimit → Token.

#### Stream-тикет

Тикет — не второй токен, а короткоживущая capability для одного эндпоинта.
Формат: `<expiry>.<userID>.<torrentID>.<hex(HMAC)>`.

Подпись (HMAC-SHA256) покрывает **все три** поля, поэтому подделать или продлить
срок нельзя, выбрать чужой торрент нельзя (`parts[2] != torrentID` отвергает), и
выбрать чужой `userID` тоже нельзя — это сломало бы подпись. Срок —
`StreamTicketTTL = 5 минут`.

**Чего подпись не делает: она не привязывает тикет к запросившему.** Ничего не
сверяет `userID` из тикета с `X-Client-ID` обращения; `StreamFile` возвращённый
`userID` попросту выбрасывает. Тикет можно передать другому — он останется
действительным до истечения.

**Почему так.** libmpv не умеет прикладывать заголовки к своим HTTP-запросам, а
токен живёт именно в заголовке. Передача доступа через URL — свойство
инструмента, а не дефект: вариант «привязать тикет к клиенту» потребовал бы
проброса `X-Client-ID` внутрь mpv, что сломало бы просмотр. Поэтому тикет —
сознательно короткоживущий и одноразово-передаваемый, а не идентичность.

Эндпоинт `/stream` при этом публичный для своего rate limiter'а
(`StreamRateLimit = 2/s`, `StreamRateBurst = 20`) — свой лимит, не общий
60/мин для защищённых эндпоинтов.

Известное ограничение описано в `.github/SECURITY.md`, раздел
«Known Security Limitations».


Транспорт синхронизации: клиент шлёт команды по REST, события комнаты
получает по SSE через сервер. Прямых соединений между участниками нет, STUN и
TURN не нужны. Обоснование выбора и условия пересмотра — в ADR «сервер-брокер
через SSE против WebRTC P2P» ниже.

#### Шов торрент-бэкенда (ремотинг)

`internal/torrent` разделён надвое. `Service` ничего не знает о том, что под ним
лежит: он валидирует, помнит выбранный файл, считает прогресс и защищает поток
от гонки с удалением. Всё, что связано с конкретным торрент-клиентом, живёт за
интерфейсом `TorrentBackend`:

| Реализация | Что это |
|---|---|
| `localBackend` | anacrolix/torrent в процессе — значение по умолчанию |
| `remoteBackend` | htorrent-шлюз по HTTPS, включается `--gateway-url` |

`TorrentHandle` — транспортно-нейтральное представление одного торрента: имя,
размер, прогресс, список файлов. Всё, что не имеет аналога у шлюза, наружу не
выдаётся: `SelectForStreaming` у шлюза — принять и проигнорировать, а
`BufferTarget` возвращает `nil`, и это единственный способ, которым `Service`
узнаёт, что приоритетами кусков владеет шлюз, а `buffer.Service` в этом режиме
должен остаться в покое.

Что режим ремотинга даёт: пиры не видят адресов друг друга, доверенный хост
кэширует куски один раз на всю комнату, а воспроизведение работает из сетей,
где закрыт P2P-трафик, потому что наружу уходит только HTTPS.

Чего он не умеет и почему это не обходно: приоритеты кусков и окно буфера —
забота шлюза; удалить торрент на шлюзе нельзя, поэтому `Drop` — это только
забывание у себя, и кэш шлюза живёт по его собственным правилам. Шлюз принимает
только magnet-ссылки, поэтому `.torrent` конвертируется в magnet локально перед
отправкой. Прогресс берётся из `/metrics` с кэшем на 2 секунды, а не на каждый
запрос списка.

### Код приглашения

Хост может положить в буфер обмена строку `ID:пароль` (меню «Комната → Скопировать
код приглашения»), а гость вставить её в поле «Код приглашения» на вкладке входа —
ID и пароль подставятся сами.

Формат — это ровно те два поля, которые `POST /rooms/join` и так требует,
собранные в одну строку. Код ничего не шифрует, не подписывает и не защищает: его
назначение — одно сообщение вместо двух полей. Всё, что не защищено, хост должен
передать получателю лично или по защищённому каналу, и код не отменяет этого.

Разделитель — **первое** двоеточие: ID комнаты состоит из 32 шестнадцатеричных
символов и двоеточия не содержит, а пароль произвольный и может содержать
двоеточие. Код без двоеточия читается как ID с пустым паролем. Разбор
(`RoomManager::parseInviteCode`) сверяет ID с тем же правилом, что и сервер, —
32 hex-символа, — и отвергает мусор на клиенте, а не отправляет его на сервер.

**Токен доступа в код не входит намеренно.** Он у хоста уже есть, но это учётка на
весь процесс, а не секрет комнаты: вложив её в приглашение, мы подняли бы права
гостя с «войти в эту комнату» до «управлять всем сервером». Смысла в ней для
входа нет — API всё равно требует заголовок, — а вреда наоборот. Всё, что нужно
гостю помимо кода, — адрес сервера и токен, и их передают отдельно, как и раньше.

Серверной части у этого нет: ни нового эндпоинта, ни нового поля в запросе.
`JoinRoomRequest` остался `{roomId, password}`.

### События SSE

Сервер шлёт `peer_joined`, `peer_left`, `peer_list`, `signal`, `sync` и `ping`
(последний не несёт данных, нужен чтобы прокси не рвали соединение).

Формы нагрузок описаны типами в `internal/models/events.go`, а не только
аннотациями: см. раздел «Чего в спеке нет» выше.

### Состав комнаты

Список участников доставляется **двумя** каналами, и оба нужны.

| канал | когда | зачем |
|---|---|---|
| `peers` в `GET /rooms/info` | один раз, при подключении | клиент, вошедший позже, не видел `peer_joined` для тех, кто был до него — без снимка он остался бы неполным навсегда |
| событие `peer_list` | при каждом изменении | список у всех, кто уже в комнате |

Каждый пир несёт `peerID`, `userID`, необязательный `username`, `isHost` и
`buffering`. Больше сервер не знает: **у пира нет «синхронизирован с комнатой»**,
потому что позиция в комнате одна общая, а не своя у каждого. Насколько отстал
конкретный клиент, считает он сам, сравнивая свою позицию с `status.position`.

`peerCount` и `peers` обязаны совпадать — оба описывают один и тот же состав.
`peerCount` считает **всех, включая хоста** (bug-0021: когда хост не попадал в
список, каждое число было на единицу меньше, а при уходе последнего гостя
комната удалялась из-под живого хоста).

**`rosterSeq` обязателен, а не оптимизация.** Два канала соревнуются по
построению: `/rooms/info` — асинхронный GET, то есть снимок на момент
обслуживания запроса, а `peer_list` прилетает по мере событий. Гость, вошедший
после отправки запроса, может прийти к клиенту **раньше** этого ответа — и старый
ответ стёр бы его из списка. Номер версии позволяет отбросить устаревший снимок
вместо того, чтобы применять его и терять участника.

По той же причине снимки применяются **целиком**, а не слиянием: повторное
применение одного и того же списка ничего не меняет. Это и позволяет `peer_list`
приходить поверх сверки после реконнекта (bug-0012) без двойного применения.

**Кто буферизирует** хранится на пире (`Peer.Buffering`), а не только в
`SyncStatus` комнаты: у комнаты один общий статус, и он не может сказать, кого
именно. `SyncEvent.Initiator` — это `userID`, поэтому клиент сопоставляет его с
`userID` из списка и помечает нужного пира сразу, не дожидаясь `peer_list`.

### Сглаживание перемотки

Синхронизация комнаты событийная, а не по таймеру: команда уходит всем
участникам, и они применяют её у себя. Постоянного догоняющего цикла нет —
это осознанное решение цели, а не пробел реализации (см. «Синхронные комнаты»
в [CONCEPT.md](CONCEPT.md)).

Что код делает на самом деле — `internal/sync`:

```
1. Клиент шлёт команду: POST /sync/play | /sync/pause | /sync/seek
2. Сервер обновляет статус комнаты и рассылает его участникам по SSE
3. Seek сглаживается на сервере:
   - |запрошенная − текущая| ≤ maxPositionJump (2 сек): ставится как есть
   - иначе: применяется 30 % разницы (SmoothAdjustmentRatio)
4. Клиент применяет команду локально: play → resume, pause → pause,
   seek → seek (с debounce 300 мс)
```

Измерения задержки нет: ни константы latency, ни поля в `SyncStatus`, ни
периодического опроса `/sync/status` со стороны фронтенда. Клиент выравнивает
позицию только по команде.

### Хранение данных

По умолчанию куски торрента лежат в памяти. Чтобы писать на диск:

```bash
./torrsyncplayer --data-dir ./data --disk-storage
```

или через `DATA_DIR` + `DISK_STORAGE=true`. Кучи пишутся в
`<DATA_DIR>/torrents`. Лимит памяти — `--memory-capacity`, максимум 256 ГБ
(`MaxMemoryStorageCapacity`).

## Фронтенд (Qt/C++)

- `mainwindow` — окно, список торрентов, диалоги комнаты
- `mpvwidget` — воспроизведение видео через libmpv
- `networkmanager` — HTTP-обмен с бэкендом, SSE-подписка на события комнаты
- `roommanager` — состояние комнаты на стороне клиента
- `torrentmanager` / `torrentmodel` — управление торрентами и их отображение
- `utils` — вспомогательные функции (форматирование времени и размера)
- `systemtray` — значок в системном лотке
- `interfaces/` — интерфейсы для тестируемости, `mocks/` — их заглушки

### Многопоточность libmpv

Все вызовы `mpv_*` защищены `QMutex`. События mpv буферизуются и
эмитятся в главном потоке через `QTimer`, чтобы Qt-сигналы не приходили из
чужого потока. Перемотка отложена на debounce-таймер, чтобы быстрая
перемотка мышью не превращалась в поток команд.

Отложенная перемотка переживает открытие файла: команда `seek` уходит в mpv
через 300 мс, а `loadfile` асинхронен, и поток из торрента открывается
дольше. Если файл к моменту команды ещё не загружен, mpv её отбрасывает —
поэтому `MPV_EVENT_FILE_LOADED` применяет неприменённую позицию заново.

### Интернационализация

Исходный язык — русский, поддерживаются `ru` и `en` (список `TS_LANGUAGES` в
`frontend/CMakeLists.txt`). Весь пользовательский текст уже обёрнут в `tr()`;
вне QObject-методов (как в `main()`) используется
`QCoreApplication::translate("Context", "…")` — `tr()` там не имеет контекста
и `lupdate` такую строку пропускает.

Команды:

```
cmake --build build --target update_translations   # исходники → .ts
python3 scripts/fill_translations.py               # наполнить .ts переводами
cmake --build build --target release_translations  # .ts → .qm (и обычная сборка)
```

`update_translations` вызывается вручную намеренно: генерировать `.ts` на
каждой сборке значило бы молча переписывать файл под ногами у того, кто
переводит. `lupdate` сохраняет уже сделанный перевод, но новые строки
оставляет пустыми — их заполняет `scripts/fill_translations.py`, который
заодно снимает флаг `unfinished` с identity-переводов (`Play`, `Pause`,
фильтр файлов), иначе `lrelease` вечно считал бы их незаконченными.

`ru.ts` намеренно пустой: пустая переводная строка означает «показывать
исходник», и Qt так и делает. Наполнять его копией исходника незачем — эти
строки молча расходились бы с кодом.

`lupdate`/`lrelease` ищутся через `find_program`, а не через
`find_package(Qt6LinguistTools)`: пакет подсказывает расположение самих
инструментов (им нужен префикс Qt, а не каталог пакета), а на машинах с
посторонней копией Qt в путях поиска находит именно её — часто обрезанную.
Если инструментов нет, конфигурация выдаёт предупреждение, а не ошибку:
приложение полностью работоспособно на языке исходников.

Выбор языка: `--lang ru|en` → сохранённая настройка `ui/language` → язык
системы, и только если он поддерживается (иначе английский). Переводчик
устанавливается **до** создания виджетов: подписи берут текст в конструкторах,
и установленный позже перевод к ним уже не применится.

Статус торрента приходит с бэкенда английским идентификатором
(`downloading`, `seeding`) — это машинное значение в API, а не текст для
человека. `localizedStatus()` в `torrentmodel.cpp` переводит его только для
отображения; в `toJson()` уходит исходный идентификатор, иначе переведённая
строка испортила бы состояние торрента на бэкенде. Неизвестный статус
показывается как пришёл — новое состояние видно сразу, без правки фронтенда.

Переводы ищутся рядом с exe (portable-сборка, AppImage, AppDir), в
`../share/TorrSyncPlayer/translations` (установленная сборка) и в системных
переводах Qt.

## ADR: сервер-брокер через SSE против WebRTC P2P

**Статус:** принято · **Дата:** 2026-10-09

### Контекст

Нужно, чтобы участники комнаты узнавали о действиях друг друга: кто вошёл, кто
вышел, кто играет, на какой позиции. Это обмен метаданными о просмотре, а не
медиаданные — сам файл идёт отдельным путём.

Вариантов два: гонять этот обмен через сервер (команды по REST, события по
SSE) или соединять участников напрямую через WebRTC, оставив сервер только
для согласования соединения.

Проект, который стоит противопоставить, — Multiplex: он использовал WebRTC
P2P поверх weron.

### Решение

Остаёмся на сервер-брокере: команды по REST, события по SSE. Один бинарник,
никакого внешнего сервиса для содержания.

### Почему не WebRTC

**Weron — это библиотека, а не хостинг.** Это важно и часто понимают неверно:
он не предоставляетsignaler «из коробки». Signaler нужно поднять и содержать
самостоятельно — отдельный сервис, отдельный деплой, отдельные обновления. То
есть WebRTC не отменяет сервер, а добавляет к нему ещё один.

**NAT traversal — не бесплатный.** Нужны STUN, а для симметричных NAT — TURN.
TURNrelay — это трафик, проходящий через чужой сервер, то есть ровно то, от чего
мы уходим, только теперь ещё и с расходами.

**Отладка дорожает кратно.** «Не соединились» в WebRTC — это десяток причин
(роли, кандидаты, ICE-агрегация, файрвол, MTU, симметричный NAT), и разбирать
приходится на глаз у пользователя. В SSE причина обычно одна и видна в логах.

### Чем мы платим за это решение

Честно — решение не бесплатное, и цена не только в простоте.

**Приватность метаданных просмотра.** Сервер видит, кто в комнате, кто хост, и
все команды синхронизации: play / pause / seek с позициями и временем. То есть
оператор сервера знает, что группа людей смотрела фильм и где именно
перематывала. Приватность **содержимого** тут ни при чём: медиаданные сервер
и так получает и отдаёт (см. [.github/SECURITY.md](.github/SECURITY.md)), P2P их бы не изменил.
WebRTC скрывал бы именно метаданные.

**Масштабируемость.** Сервер рассылает каждое событие каждому участнику, и
число отправок растёт квадратично с числом пиров. Прямые соединения этого не
устраняют полностью — согласование всё равно идёт через сервер, — но снимают
основную нагрузку с рассылки.

**Устойчивость к падению сервера.** Пока сервер жив, комната работает. Упал —
комнаты нет, даже если участники физически связаны. С WebRTC уже установленные
P2P-соединения могли бы пережить перезапуск сервера (согласование — нет).

### Условия пересмотра

Проверяемые условия, а не пожелания. Любое из них означает: открыть вопрос
заново, а не «когда-нибудь посмотреть».

1. **Нагрузка на рассылку.** Если комнаты на 100+ участников перестают быть
   редкостью — упереться в `MaxSSEConnections = 100` на комнату или
   `MaxGlobalSSEConnections = 1000`. Проверяемо: метрики подписчиков SSE.
2. **Приватность стала обязательным требованием,** а не пожеланием — например,
   появился контракт или требование, что оператор сервера не должен видеть
   действия пользователей. Тогда метаданные просмотра перестают быть приемлемой
   ценой.
3. **Появилось требование переживать недоступность сервера** — например, «комната
   продолжает работать при перезапуске бэкенда». Текущая архитектура так не
   умеет по построению, а не из-за недосмотра.
4. **Появился готовый signaler, за который не надо платить эксплуатацией.**
   До этого момента WebRTC обменивает одну зависимость на другую и не выигрывает
   ни в чём, что здесь важно.

## Принципы разработки

1. Магические числа живут только в `internal/constants/constants.go`.
2. Ошибки — структурированные, из `internal/errors`; тип проверяется через
   `errors.As`, прямым type assertion пользоваться нельзя.
3. Интерфейсы объявляются в `internal/interfaces.go`, а не рядом с
   реализацией: `api` не должен знать устройство сервисов.
4. Аккаунтов нет. Токен доступа один на процесс, сравнение —
   `crypto/subtle.ConstantTimeCompare`. Идентификаторы комнат
   нормализуются в нижний регистр.
5. Всё, что приходит от пользователя, валидируется и санируется; в URL
   попадают только проверенные значения.
6. Члены классов во фронтенде именуются с префиксом `m_`, методы — в
   camelCase.
7. События комнаты идут через сервер; прямые P2P-соединения не вводятся.
8. То, что выводится из кода, не переписывается руками: формы API живут в
   Swagger, метрики — в `internal/metrics`.
9. **Этот файл и [CONCEPT.md](CONCEPT.md) описывают целевое состояние, а не
   текущее.** Расхождение с кодом лечится кодом: пока флаг не реализован,
   документация права, и его нужно реализовать. «Описать в документации то,
   что делает код» делает расхождение невидимым, и следующая сессия примет
   исправленный вниз документ за цель. Документацию меняют только осознанным
   решением изменить цель — и тогда это правка цели, а не молчаливая правка
   описания.

## Проверки должны уметь краснеть

Зелёная сборка ценна только тогда, когда сломанная может стать красной.
Поэтому вне осознанного исключения запрещены:

- `|| true` в рецепте Makefile;
- `continue-on-error: true` у шага или джобы CI;
- `-` в конце команды в рецепте;
- тест, который проверяет только не-nil или повторяет собственную логику.

Два бага дошли до `main` при полностью зелёном пайплайне именно поэтому: SSE
отдавал 500, потому что обёртка middleware теряла `http.Flusher`, и подпись
stream-тикета считалась над пустой строкой, то есть не проверяла ничего.
Ни одна проверка этого не видела.

Если проверка выглядит нестабильной — чинить нестабильность, а не
заглушать её.
