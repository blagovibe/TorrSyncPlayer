# Dev — как устроен TorrSyncPlayer

Что проект делает и зачем — в [CONCEPT.md](CONCEPT.md). Этот файл отвечает на
вопрос «как его собрать, запустить и править» и не дублирует то, что и так
выводится из кода.

## Почему здесь нет справочника API

Формы запросов и ответов **не описаны вручную**. В коде стоят аннотации
`@Router`, `@Param`, `@Success`, из которых генерируется спецификация:

- `/swagger/index.html` на запущенном сервере — интерактивный вариант;
- `backend/docs/swagger.json` и `swagger.yaml` — тот же самый OpenAPI.

Спека перегенерируется командой и проверяется в CI на свежесть: если
аннотации разошлись с файлом, сборка падает. Поэтому она не может разойтись с
кодом — а ручной справочник может и разойдётся.

Чтобы посмотреть справочник, запустите сервер и откройте `/swagger/`.
Фильтр `TRUSTED_PROXIES` и правила rate limit описаны
ниже — это то, чего в спеке нет и что из кода не выводится.

Перегенерация после правки аннотаций:

```bash
cd backend
go run github.com/swaggo/swag/cmd/swag@v1.16.6 \
  init --generalInfo cmd/server/main.go --output docs --parseDependency
```

### Чего в спеке нет: протокол комнаты

Комнаты в спеке нет вовсе — и это не пробел, а следствие архитектуры: команды
синхронизации идут не по HTTP, а по шифрованным стримам libp2p между участниками, и
swaggo описывает только HTTP. Истина — в типах `frontend/internal/rtc`:
`protocol.go` (форма каждого сообщения), а проверяет её не спек, а тесты,
которые пинят точный JSON (`protocol_test.go` — разбор и отказ неизвестному
типу), плюс сценарий `TestARoomWithoutAServer`, который гоняет настоящий обмен
между двумя настоящими пирами.

Менять формат молча нельзя: это ломает всех, кто
уже подключён. `hello` несёт адреса отправителя — поле, которого раньше не
было; версия протокола говорит, какой форме сообщения соответствует пир, и
старый хост её просто не заполняет — расхождение видно (см. «Сообщения
комнаты»).

## Системные требования

| | Минимум | Рекомендуется |
|---|---|---|
| ОС | Windows 10+, Ubuntu 20.04+, macOS 12+ | Windows 11, Ubuntu 22.04+, macOS 13+ |
| ОЗУ | 8 ГБ | 16 ГБ |
| Диск | 500 МБ | SSD, 1 ГБ свободно |

Данные торрентов по умолчанию лежат **в памяти** — объём ограничен
`--memory-capacity` (максимум 256 ГБ). При первом запуске приложение спрашивает,
где хранить куски; ответ применяется со следующего запуска, а «на диске»
означает `--disk-storage` с каталогом, который предлагается по умолчанию:
`~/Downloads/TorrSyncPlayer`. См. «Хранение данных» и «Настройки окна».

## Зависимости

### Бэкенд — Go 1.26+

```bash
# Ubuntu/Debian
wget https://go.dev/dl/go1.26.linux-amd64.tar.gz
sudo tar -C /usr/local -xzf go1.26.linux-amd64.tar.gz
export PATH=$PATH:/usr/local/go/bin

# macOS
brew install go
```

Windows — установщик с [go.dev](https://go.dev/dl/).

### Фронтенд — Go, Fyne и mpv

Отдельного toolchain нет: это тот же Go, что и у бэкенда, плюс Fyne, который
тянет cgo и системные заголовки OpenGL/X11.

```bash
# Ubuntu/Debian — заголовки нужны Fyne на этапе сборки
sudo apt update
sudo apt install -y \
    build-essential pkg-config \
    libgl1-mesa-dev libx11-dev libxkbcommon-dev libfontconfig1-dev

# macOS
xcode-select --install
```

Windows — Go с [go.dev](https://go.dev/dl/) и Visual Studio Build Tools
(компонент «Разработка классических приложений на C++»): без него Fyne не
соберётся.

**mpv ставится отдельно и нужен для воспроизведения.** Это не библиотека, а
внешний процесс: клиент запускает `mpv` и говорит с ним по его JSON IPC
(`internal/player`). Без mpv приложение работает — список торрентов, комнаты,
команды синхронизации, — но видео не идёт, и в строке состояния об этом сказано
прямо.

```bash
# Ubuntu/Debian
sudo apt install -y mpv
# macOS
brew install mpv
# Windows
winget install mpv.net  # либо mpv из shinchiro; путь задаётся настройкой
```

Windows-путь к mpv, если он не на `PATH`, задаётся в настройках
(`playerBinary`). Раньше это поле существовало и молча не читалось.

Fyne нужен и на этапе тестов: без дисплея тесты висят, а не падают, поэтому
`FYNE_DRIVER=offscreen` обязателен в CI и при локальном прогоне без экрана.

## Сборка

Версия Go закреплена в `GO_VERSION` во всех workflow — это единственное
место, где она меняется.

Приложение и бэкенд — **неразделимая пара**: каждый участник запускает свой
собственный бэкенд, поэтому клиент ищет его рядом с собой
(`internal/backend.FindBackend`) и стартует сам. Сборка, давшая только клиент,
дала бы то, что не запускается.

```bash
cd frontend
go run ./cmd/build              # → ./dist/TorrSyncPlayer + ./dist/torrsyncplayer
go run ./cmd/build -out release # или в свой каталог
```

Скрипт сборки — программа на Go, а не shell-скрипт: проект рассчитан на три
платформы, а три скрипта, которые обязаны согласовать состав сборки между
собой, — это ещё одна вещь, которую надо держать в согласии. Go и так уже
зависимость сборки на всех трёх.

Только бэкенд — отдельно, так делает CI:

```bash
cd backend && make build   # → backend/build/torrsyncplayer
```

Кросс-компиляция с Linux на macOS и Windows **не работает**: драйверу Fyne
нужен cgo и нативный GL-тулчейн целевой платформы. `GOOS=windows go build
./internal/...` собирает внутренние пакеты и служит проверкой переносимости
логики; сам бинарник собирается на своей платформе.

## Запуск

Клиент и бэкенд запускаются вместе: приложение само поднимает свой бэкенд на
свободном порту и ждёт его готовности.

```bash
cd frontend
go run ./cmd/build -out dist
./dist/TorrSyncPlayer
```

Бэкенд в одиночку — когда нужен именно сервер (например, как плоскость
управления для чужих клиентов):

```bash
cd backend/build
./torrsyncplayer
```

Сервер печатает в лог случайный **токен доступа** при каждом старте. Он
передаётся клиентам в заголовке `X-Access-Token`; ни аккаунтов, ни паролей, ни
регистрации нет. Флаг `--token` заменяет случайный токен фиксированным — для
развёртываний, где секретом управляют вне процесса (EnvironmentFile systemd,
runbook конфигураций). Тогда токен в лог не печатается: тот, кто его задал,
знает его и так.

Встроенному бэкенду приложения секрет аргументом не передаётся: флаг
`--token-stdin` заставляет бэкенд прочитать токен из первой строки
стандартного ввода (пробелы обрезаются, пустая строка — отказ на старте).
Аргументы процесса видны любому, кто может запустить `ps`, и секрет в списке
процессов — ровно тот компромисс, от которого этот флаг уходит
(deviation-0061). `--token-stdin` вместе с `--token` — ошибка конфигурации: два
источника секрета означали бы, что неизвестно, какой из них действует.

### Флаги

Клиент:

| Флаг | Назначение |
|---|---|
| `-c`, `--client-id` | идентификатор участника в комнате (генерируется, если не задан) |
| `--bootstrap` | DHT-рандеву запасного пути: адреса нод с `/p2p/` (по умолчанию — собственный список проекта, см. «Рандеву»; для тестов — локальный testbed) |
| `--relays` | запасные релеи для autorelay, тот же формат (по умолчанию пусто — кандидаты ищутся обходами DHT) |

Рандеву и релеи применяются при следующем входе в комнату, а не к текущей:
комната — это уже открытые соединения. Рандеву теперь запасной путь, а не
способ встречи: комната собирается по адресу из кода приглашения.
| `--lang` | язык интерфейса: `ru`, `en` |
| `--no-tray` | без значка в лотке. Флаг, который делает ровно то, что написано: закрытие окна завершает приложение |
| `--dark-theme` | тёмная тема |

Бэкенд:

| Флаг | Назначение |
|---|---|
| `--addr` | адрес прослушивания целиком; заменяет `:port` (например `127.0.0.1:8889`, `:9999`) |
| `--port` | порт прослушивания, если `--addr` не задан (по умолчанию `8889`) |
| `--token` | зафиксировать токен вместо случайного |
| `--token-stdin` | взять токен из первой строки stdin (взаимоисключим с `--token`) |
| `--data-dir` | каталог для персистентных данных |
| `--disk-storage` | писать куски торрента на диск (требует `--data-dir`) |
| `--memory-capacity` | лимит памяти под куски, до 256 ГБ |
| `--tls-cert`, `--tls-key` | сертификат и ключ для TLS |
| `--tls` | включить TLS с самоподписанным сертификатом |
| `--auto-tls` | сгенерировать временный самоподписанный сертификат |
| `--enable-profiling` | pprof |
| `--gateway-url` | адрес htorrent-шлюза; включает режим ремотинга (см. ниже) |
| `--gateway-user` | basic-auth логин к шлюзу (обязателен вместе с `--gateway-url`) |
| `--gateway-pass` | basic-auth пароль к шлюзу |
| `--gateway-ca-cert` | CA-сертификат для проверки TLS шлюза (для внутренних и самоподписанных) |

Флаги шлюза дублируются переменными окружения `GATEWAY_URL`, `GATEWAY_USER`,
`GATEWAY_PASS`, `GATEWAY_CA_CERT` — чтобы unit-файл systemd не размазывал пароль
по командной строке. `--gateway-url` без обеих частей логина и пароля
останавливает старт: иначе сервер поднялся бы и падал бы уже на первом
воспроизведении.

Разбор флагов живёт в `parseFlags(fs *flag.FlagSet, args []string)`, а не в
`flag.Parse()` на глобальном наборе: так он тестируется —
`cmd/server/main_test.go` проверяет, что `--addr` вытесняет `:port`, что
`--token` доходит до сервиса авторизации, что неизвестный флаг даёт ошибку, а не
сервер со значениями по умолчанию, и что шлюз требует пароль. `main` вызывает
`parseFlagsOrExit`: тест не должен ронять тестовый бинарник через `os.Exit`.

### Переменные окружения

`PORT`, `DATA_DIR`, `DISK_STORAGE`, `MEMORY_CAPACITY`, `LOG_LEVEL`,
`LOG_FORMAT`, `TLS_CERT`, `TLS_KEY`, `API_RATE_LIMIT`, `API_RATE_BURST`,
`CORS_ORIGINS`, `ENV`, `GO_ENV`, `TRUSTED_PROXIES`.

Адрес прослушивания и сам токен задаются **только флагами** (`--addr`,
`--token`) — переменных окружения для них нет.

`TRUSTED_PROXIES` — список CIDR, которым **доверять** заголовку
`X-Forwarded-For`. Пока переменная не задана, заголовок игнорируется
полностью: иначе любой клиент из приватной сети мог бы подменить свой
IP. Формат — `10.0.0.0/8,192.168.0.0/16`.

## Архитектура

Два приложения, оба на Go: бэкенд и фронтенд. Фронтенд не содержит
бизнес-логики — он ходит в свой бэкенд по HTTP за торрентами и отдаёт команды
комнаты напрямую другим участникам по стримам libp2p. Сервер у каждого свой и только
для медиа: комнаты встречаются на DHT-рандеву (`--bootstrap`), а дальше
говорят mesh'ем без посредников (через релеи — только за жёстким NAT).

### Бэкенд (Go)

Слои: `cmd/server` (сборка сервисов и graceful shutdown) → `internal/api`
(роутинг, обработчики, middleware) → сервисы предметной области
(`internal/*`) → `pkg/` (журнал и формирование ответов).

| Пакет | Ответственность |
|---|---|
| `internal/api` | Роутинг chi, обработчики, middleware (security headers, recovery, CORS, content-type, логирование, rate limit), константы путей |
| `internal/auth` | Per-process access token, constant-time compare |
| `internal/torrent` | Управление торрентами, HTTP-стриминг через anacrolix/torrent |
| `internal/buffer` | Расстановка приоритетов кусков по позиции воспроизведения (now → high → normal → readahead → none) для немедленного старта |
| `internal/persistence` | JSON-файлы: реестр торрентов и владение (комнат и синк-стейта больше нет — их не хранит никто) |
| `internal/storage` | Хранилище кусков: в памяти (по умолчанию, с лимитом ёмкости) или на диске |
| `internal/validation` | Общая валидация входных данных (идентификаторы комнат, размеры) |
| `internal/models` | Общие типы данных и структуры ответов |
| `internal/errors` | Структурированные ошибки AppError с типом ошибки |
| `internal/metrics` | Метрики Prometheus |
| `internal/constants` | Все магические числа проекта |
| `internal/utils` | Общие утилиты (идентификаторы, Debouncer) |
| `internal/version` | Информация о версии сервера |
| `internal/interfaces.go` | Интерфейсы, через которые api обращается к сервисам |
| `internal/contract` | Pact-проверка контракта (за build-тегом `contract`) |
| `pkg/logger` | slog-журнал с контекстом операции |
| `pkg/response` | Формирование JSON-ответов |

Порядок middleware: SecurityHeaders → Recovery → CORS → ContentType →
Logger → RateLimit → Token.

#### Stream: заголовок, как везде

Медиа-эндпоинт `/stream` ничем не отличается от остальных: тот же
`X-Access-Token`, тот же клиентский заголовок. `mpv` передаёт его через
`--http-header-fields`, поэтому тикет в URL не нужен, и свойство «тике в URL
передаётся тому, кому хотят» не остаётся.

Ограничение читательского доступа не потерялось дважды: сначала при удалении
тикетов, потом при удалении комнат. Перед отдачей файла проверяется `CanRead`
(bug-0049): владелец проходит, чужой — нет. Проверки участия в комнате больше
нет, потому что комнат на сервере больше нет: гости вообще не трогают чужой
бэкенд, у каждого свой. Токен в приглашение не входит и никогда не входил —
deviation-0039 умер вместе с брокером, потому что умер единственный путь, на
котором он жил.

Транспорт синхронизации: команды идут шифрованными стримами libp2p-mesh'а между
участниками, сводит которых DHT-рандеву. Сервер в этом не участвует
вообще: он отдаёт торренты своему владельцу и ничего не знает о комнатах.
Обоснование выбора — в ADR ниже: он переписан тем же решением, которое его
опровергло.

#### Шов торрент-бэкенда (ремотинг)

`internal/torrent` разделён надвое. `Service` ничего не знает о том, что под ним
лежит: он валидирует, помнит выбранный файл, считает прогресс и защищает поток
от гонки с удалением. Всё, что связано с конкретным торрент-клиентом, живёт за
интерфейсом `TorrentBackend`:

| Реализация | Что это |
|---|---|
| `localBackend` | anacrolix/torrent в процессе — значение по умолчанию |
| `remoteBackend` | htorrent-шлюз по HTTPS, включается `--gateway-url` |

`TorrentHandle` — транспортно-нейтральное представление одного торрента: имя,
размер, прогресс, список файлов. Всё, что не имеет аналога у шлюза, наружу не
выдаётся: `SelectForStreaming` у шлюза — принять и проигнорировать, а
`BufferTarget` возвращает `nil`, и это единственный способ, которым `Service`
узнаёт, что приоритетами кусков владеет шлюз, а `buffer.Service` в этом режиме
должен остаться в покое.

Что режим ремотинга даёт: пиры не видят адресов друг друга, доверенный хост
кэширует куски один раз на всю комнату, а воспроизведение работает из сетей,
где закрыт P2P-трафик, потому что наружу уходит только HTTPS.

Чего он не умеет и почему это не обходно: приоритеты кусков и окно буфера —
забота шлюза; удалить торрент на шлюзе нельзя, поэтому `Drop` — это только
забывание у себя, и кэш шлюза живёт по его собственным правилам. Шлюз принимает
только magnet-ссылки, поэтому `.torrent` конвертируется в magnet локально перед
отправкой. Прогресс берётся из `/metrics` с кэшем на 2 секунды, а не на каждый
запрос списка.

### Поток «комната и синхронизация»

```
Host                                    Guest
  │  код: v2:community:password:key:addrs  │
  │────────────────────────────────────►│
  │  dial(addrs)                        │
  │◄────────────────────────────────────│
  │  hello(isHost, addrs, version=2)    │
  │────────────────────────────────────►│
  │  hello(isHost, addrs, version=2)    │
  │◄────────────────────────────────────│
  │  magnet{magnetUri, file}            │
  │────────────────────────────────────►│
  │  pause(false)                       │
  │────────────────────────────────────►│
  │  position(123.4)                   │
  │────────────────────────────────────►│
```

Знакомство происходит по адресу, который лежит в коде приглашения: гость
звонит хосту напрямую и доказывает пароль в handshake, а хост сверяет ключ,
которым шифруется сигналинг. DHT в этом пути не участвует вовсе: он остаётся
запасным — на случай, когда адрес не сработал, — и источником публичного
адреса узла и кандидатов в релеи. Серверов в этой схеме нет вообще — ни
своего, ни чужого. Медиа тем более идёт мимо: каждый тянет из роя сам, как
раньше.

Mesh достраивается сам: хост отвечает на приветствие адресной книгой комнаты,
и вошедший звонит по ней тем, кого в книге нет, а не только хосту. Старый хост
адреса не присылает и остаётся «листом» в звезде, и это видно, а не молчит.

Хост выделяется не сетью, а ролью: mesh симметричен, управление — нет.
Последователи принимают команды только от пира, приславшего magnet; уход
хоста без передачи закрывает наименьший живой peer ID, и он объявляет себя
сам — детерминированно, без выборов и часов.

### Код приглашения

Хост копирует строку `v2:community:password:key:addrs`, а гость вставляет её в
поле «Код приглашения» — и входит. Пять частей генерирует хост при создании
комнаты. Версия разбирается первая и отдельно, а остальные четыре — как
раньше: первые три не содержат двоеточия, поэтому разбор — строгий сплит на
четыре части по первым трём двоеточиям, а не «первое двоеточие»: четвёртая
часть — список multiaddr'ов хоста, и двоеточия в нём есть.

**Версия стоит первым и говорит, какой протокол говорит хост.** Префикс
`v2:` разбирается до остального: код без префикса — это код со сборки, где
версии ещё не было, и он открывает комнату как обычно (его сообщения —
подмножество того, что эта сборка понимает), но помечается в списке как
«старая версия». Код с версией **больше** этой сборки не разбирается вовсе:
гость не звонит, а говорит, что код из более новой сборки.

Версия есть и в приветствии (`hello`), и там решение строже: участник, который
говорит на более новом протоколе, **в комнату не попадает** — его не пускают в
ростер, и комната не слушает его сообщения (магнит, заявку на роль хоста,
команды). Отказ виден словами в строке событий, а не исчезновением человека из
списка. Причина простая: новый участник может прислать команду, которую эта
сборка поняла бы неправильно, — и «не понял, а исполнил» хуже, чем «не понял
и не исполнил».

Отказ липкий: peer, которого отказали однажды, не получает второго шанса с
другим номером.

Адреса в коде — не украшение. Код без них — это код от старой сборки, а
комната, собираемая через рандеву, собирается минутами и иногда не собирается
вовсе: ровно то, ради чего адрес в коде и появился. Такой код отвергается, и
человеку, который его вставил, говорится, что это код из старой версии и что
нужно попросить новый.

Код ничего не шифрует сам, но всё в нём — секрет: community называет комнату,
а допуск доказывается в handshake знанием пары «пароль + ключ» до принятия
стримов. PSK-гейта на весь рой нет осознанно: с ним узел не говорил бы ни с
публичными bootstrap-нодами, ни с публичными релеями — `PrivateNetwork`
оборачивает каждое соединение, а не только комнатные (idea-0091). Поэтому код
передают лично или по защищённому каналу, как раньше передавали пароль, —
назначение у него то же (одно сообщение вместо четырёх полей), а цена утечки
выше: утекший код — это зритель, а не гость.

В коде лежит peer ID хоста, и он не для красоты: гость знает, кому именно
дозвонился, и не примет никого другого на месте хоста. Раньше эту роль играл
community — DHT-ключ, по которому комната находилась, — и имя в коде значило
«вот этот узел в этой сети»; теперь community по-прежнему называет комнату,
а адрес говорит «вот этот узел», и нужны обе части.

**Токен доступа в код не входит намеренно.** Он у хоста уже есть, но это учётка
на весь процесс — свой бэкенд, а не секрет комнаты. Гость вообще не трогает
чужой бэкенд: у него свой, и magnet он кладёт в него. Приглашение, несущее
токен, дало бы гостю управление чужим сервером; приглашение без него даёт
только просмотр. Это и закрыло deviation-0039: проверять стало нечего, потому
что путь, на котором жило отклонение, исчез.

### Сообщения комнаты

По стримам ходят `magnet`, `pause`, `position`, `buffering`, `hello`, `host`,
`peers` и `bye` — и ничего серверного: ни версий ростера, ни номеров
последовательности, ни replay. Стрим надёжен и упорядочен, пока жив, поэтому
компенсировать нечего; история событий ушла вместе с брокером.

Сеть комнаты достраивается сама, и для этого в протоколе есть два поля.
`hello` несёт адреса отправителя: так хост знает, где каждый из его гостей
доступен. Ответом хост шлёт `peers` — адресную книгу комнаты, и тот, кто
пришёл, звонит по ней тем, кого в книге нет, а не только хосту. Сеть
получается mesh, а не звезда, и никто для этого не ищет никого в сети.

Поля новые, и старый хост их просто не заполняет: он остаётся «листом» в
звезде, и это видно, а не молчит. Неизвестное поле игнорируется, а неизвестный
тип — ошибка, а не догадка: новый хост не должен рулить старым последователем
во что-то, чего тот не понимает.

**Версия протокола есть, и она не переговоры.** `hello` несёт номер протокола
(`version`), и `ProtocolVersion` в `internal/rtc/protocol.go` — это то, что
говорит эта сборка. Правила ровно два:

- участник, чья версия **больше** нашей, в комнату не попадает, и комната
  не слушает его сообщения; отказ виден словами;
- участник без номера версии (сборка до её появления) — это версия
  `ProtocolVersionLegacy`: его сообщения — подмножество наших, поэтому он в
  комнате, но помечен в списке как «старая версия».

Согласованно с «Код приглашения»: там версия стоит в самом коде, чтобы гость
знал о ней **до** набора.

Формы описаны типами в `frontend/internal/rtc/protocol.go`: см. раздел «Чего в
спеке нет» выше.

### Состав комнаты

Ростер — это те, кто сказал hello и не сказал bye (и не замолчал). Никакого
второго канала со снимком больше нет: снимок был нужен, потому что два
серверных канала соревновались друг с другом, а здесь канал один.

Каждый пир несёт `peerID`, `userID`, необязательный `username`, `isHost` и
`buffering`. `username` берётся из `Settings.DisplayName` и в меш уходит при
входе в комнату; окно называет участника через один `peerLabel`, и этот же
ярлык идёт в строку состава, в «присоединился» и в «ушёл» — иначе уход
человека был бы назван его машиной. Без имени ярлык — это «устройство ab12», а
не сам идентификатор: выдуманное имя опаснее честного (idea-0125). **«Синхронизирован с комнатой»** у другого участника не
показывается, как раньше: позиция в комнате одна на всех, и насколько отстал
кто-то конкретный, знает только он сам — сравнивая свою позицию с командой.

**Кто буферизирует** хранится на пире, а не в общем статусе: у комнаты больше
нет общего статуса вообще — нет сервера, который бы его держал. Сообщение
`buffering` может прислать любой участник, а не только хост: иначе участник,
у которого всё в порядке, не смог бы сказать, что его поток восстановился.

### Рандеву: свои ноды, таблица маршрутизации и релеи

Рандеву больше не ищет комнаты: комнату собирают по адресу из кода
приглашения, а если адрес не сработал — по peer ID хоста, и это маршрутный
поиск, а не поиск провайдера (см. «Код приглашения»). Рандеву остаётся на
две роли: он сообщает узлу его публичный адрес (autonat) и даёт кандидатов в
релеи, без чего узел не знает, как его зовут снаружи, и не поднимает
резервацию. Таблица маршрутизации — то, чем запасной путь ищет пира по его
ID.

Рандеву по умолчанию — **собственный список проекта**, `ownSeedAddrs` в
`internal/rtc/p2p.go`: публичные DHT-серверы по именам, которые публикуют
A-записи, через TCP. Список libp2p остаётся хвостом: он ничего не стоит,
когда не отвечает, и это путь к ноде, о которой проект ещё не знает.

Свой список — не вкусовое решение, а вынужденное. `dht.DefaultBootstrapPeers`
достигает четырёх из пяти своих нод через `/dnsaddr/bootstrap.libp2p.io`, а
это имя не публикует SRV-записей (пустой ответ на 127.0.0.53, 1.1.1.1, 8.8.8.8
и 9.9.9.9), то есть четыре записи из пяти не набираются. Оставшаяся, пятая,
единственная — и с ней комната не собиралась (bug-0121).

Два правила, оба измерены на живой машине против публичного DHT и оба
сторожятся тестами в `internal/rtc/rendezvous_test.go`:

| Правило | Измерение |
|---|---|
| Seed, который не ответил, стоит этого seed, а не входа | диалы идут параллельно, каждый под `seedDialTimeout`; ответившие продолжают работу |
| Никто не ответил — вход останавливается словами «рандеву недоступно» | а не «connect to bootstrap peer», то есть причина, по которой человек знает, что делать |

**Записи о провайдерах в комнате больше нет.** Узкий анонс при входе
(`Provide(key, brdcst=false)`) писал запись только в локальный provider-store
узла и в сеть не уходил ничего (`routing.go:398-427`), а широкая публикация
доходила до «ближайших пиров» — и у публикатора и у ищущего эти множества
были разными. Именно этим объяснялись срывы сборки, которые чинились
четырьмя способами и ни одним (bug-0129, bug-0130, bug-0133). Запасной путь
теперь ищет пира по его ID, а это свойство таблицы маршрутизации, а не записи
о провайдере: пин на него — «узел, который не анонсировал ничего, всё равно
находится по своему ID».

**Запасной путь стоит минут, и это его цена, а не его поломка.** На живой
сети, когда адрес хоста недоступен, поиск по ID идёт через чужую сеть — и
это минуты, а не секунды. Минуты приняты как плата; поломка — нет, и её ловит
публичный ряд измерений (см. «Соглашения по тестам»): порог записан, и его
нарушение открывает карточку.


### Диагностика соединения

Компактный статус соединения — соединились ли, каким путём (напрямую, через
реле или через DHT-запасной), число пиров комнаты, сколько из них напрямую,
сколько через реле, собственный peer ID — показывает блок статуса в окне
комнаты (см. «Не нужно догадываться» в [CONCEPT.md](CONCEPT.md)).

Источник — сам узел, новых протоколов нет: `Node.DHTReady` (таблица
маршрутизации непуста), `Node.PeerRelayed` (среди соединений с пиром есть
адрес `/p2p-circuit`), `Mesh.ConnStatus` собирает их по пирам комнаты (до
входа — пусто: знать нечего).

Строка отвечает на четыре вопроса, и порядок у них такой: соединено ли, как
соединено, что с запасным путём, кто я. Состояния:

- «Подключаемся…» — гость соединяется (или хост ждёт, когда появятся адреса
  у его узла);
- «Комната открыта — ждём, кто подключится» — хост с пустой комнатой ждёт
  человека, а не сеть;
- «Соединено — участников: N (напрямую X, через реле Y, через DHT-запасной
  Z), вы <id>». Три пути — это список цели; пустые не показываются. Третий
  стоит отдельного внимания: пир, которого пришлось искать по его
  идентификатору, — это пир, которого быстрый путь не достал, и он стоит
  минут вместо секунд. Путь хранится в пире меша (`rtc.PeerPath`): «по коду»,
  «через запасной путь», «звонил сам»; релейность — свойство соединения, а
  не пути.
- «Не соединилось: адрес из кода не сработал, а запасное рандеву недоступно» —
  единственная поломка, которую видно и на которую можно повлиять: и адрес из
  кода не сработал (`Mesh.inviteFailed`), и запасного пути нет.

Пока запасное рандеву не поднялось, строка дописывает это («— запасное
рандеву не поднялось»): это способ зайти в комнату без адреса, и его
отсутствие меняет то, что человеку стоит делать. Когда он поднялся — молчание.

Счётчика ожидания больше нет, и порога в шесть минут тоже: сборка занимает
секунды, и ждать нечего — комната ждёт человека, а не сеть. Вместе с минутами
из цели ушли объяснение «почему ожидание длинное» и счётчик, который растёт
вечно (idea-0131, bug-0128, bug-0137). Публикации у комнаты больше нет, и состояния
«комната о себе не сообщила» — тоже: публиковать нечего, а рандеву ищет не
комнату, а пира по его ID.

Окно обновляет блок в своём двухсекундном опросе, а решения о тексте — чистая
`connStatusText` с ключами каталога: неизвестное состояние показывается как
есть, а не прячется.

### Следование за хостом и heartbeat

Синхронизация комнаты событийная с heartbeat: команды уходят всем участникам
в момент действия хоста, а каждые пять секунд хост повторяет свою текущую
позицию безусловно — так отставший молча догоняет, не дожидаясь следующей
команды (см. «Синхронные комнаты» в [CONCEPT.md](CONCEPT.md)).

Что код делает на самом деле — `frontend/internal/rtc` плюс цикл окна:

```
1. Хост замечает изменение своего плеера и шлёт команду в mesh:
   pause → Pause, play → Pause(false), seek → Position(сырая)
2. Каждый 10-й тик roomTick (500 мс) хост шлёт Position(текущая) в любом
   случае — это heartbeat; правило «команды только от хоста» не меняется
3. Каждый последователь принимает команду только от хоста (приславшего magnet)
4. Последователь встаёт туда же, где хост, и сразу: FollowPosition отдаёт
   позицию хоста как есть
5. Буферизация — не команда, а отчёт: комнату она останавливает, ведёт — нет
```

**Как комната останавливается.** Отчёт о буферизации отправляет кто угодно —
хост или гость: сообщение уходит всем участникам, и комната записывает его
в ростер (`Peer.Buffering`). Дальше решение принимает **хост**, и только он:
состояние воспроизведения в комнате — его, и только его слушают остальные.

- Хост слышит отчёт (от гостя) или видит собственный стоп (`mpv` сказал
  `stalled`) и **останавливает свою работу**; его цикл зеркалит состояние
  плеера в комнату, и это то сообщение, которому следуют все.
- Комната отпускается, когда **никто не отстаёт**: ни один участник в
  ростере не буферизует и сам хост не стоит.
- Гость, услышавший тот же отчёт, **ничего не делает**: отчёт — не команда,
  и состояние комнаты не его.

Собственный стоп хоста живёт рядом с ним, а не в ростере: пир не слышит
свой собственный отчёт. Это не деталь, а опора: `mpv` продолжает говорить
`stalled`, **пока плеер на паузе**, и снимает его, когда данные приходят, —
даже на паузе. Значит, остановка комнаты не маскирует стоп, который её
остановил, и комната отпускается ровно тогда, когда данные вернулись. Оба
факта закреплены тестом `TestMpvKeepsSayingStalledWhileThePlayerIsPaused`:
в апгрейде mpv они могут исчезнуть, и тогда остановка станет ложной.

Чужая пауза не отнимается: если участник поставил на паузу сам, а потом
кто-то отстал, комната остановится, но отпустит не его паузу — её снимет
только тот, кто её взял на себя.

**Сглаживания больше нет, и это решение, а не упущение.** Раньше
последователь закрывал треть расхождения за такт, и это покупало мягкое
приземление ценой обещания: после перемотки на минуту он полз к общему
моменту полторы минуты, и все в комнате смотрели разное. Измерение это
показало числами — 59.8 секунды расхождения и 74.9 секунды до схождения
(idea-0142), — и решение владельца было однозначным: «та же секунда» и после
перемотки (idea-0146). Прыжок на минуту видят все одинаково и заканчивают
одинаково; расхождение, которое никто не назвал, — нет. После правки прыжок
встаёт в комнату за 600 мс, и расхождение после него — 0.20 с.

Heartbeat идёт обычным `Position`; нового типа сообщений нет, и решение о
периоде (`heartbeatEvery`) вынесено в тестируемую функцию `hostSeekDue`, а не
закопано в цикл. Половина цикла окна — `roomTick` — вынесена отдельно от
цикла с виджетами, чтобы измерение расхождения гоняло те же решения, а не их
копию.

Цикл окна (`watchPlayer`) и его половина (`roomTick`) — это то, что измерение
расхождения гоняет: два настоящих mpv, одна настоящая комната поверх
настоящего libp2p-потока, тот же `applySeek`, тот же `FollowPosition`. Что
оно нашло и какой порог стоит — в разделе «Соглашения по тестам».

Измерения задержки нет, как раньше: ни константы latency, ни периодического
опроса чужой позиции. Клиент выравнивает позицию по команде и по heartbeat.

### Хранение данных

По умолчанию куски торрента лежат в памяти. Чтобы писать на диск:

```bash
./torrsyncplayer --data-dir ./data --disk-storage
```

или через `DATA_DIR` + `DISK_STORAGE=true`. Куски пишутся в
`<DATA_DIR>/torrents`. Лимит памяти — `--memory-capacity`, максимум 256 ГБ
(`MaxMemoryStorageCapacity`).

При первом запуске приложение спрашивает, где куски должны жить, — предвыбрана
«Память», потому что это текущий дефолт и человека не двигают на диск молча
(idea-0081). Ответ — обычная настройка: он применяется со следующего запуска и
меняется в окне настроек. «Позже» — не ответ: вопрос вернётся при следующем
запуске.

Режим памяти — это **ничего на диске**, включая реестр торрентов: после
перезапуска список торрентов пуст и загрузка начинается заново. Диск даёт
возобновление: и куски, и реестр лежат в `DATA_DIR`.

Перезапуск переживают и состав, и владение: `torrents_registry.json` хранит
источник каждого торрента — magnet-ссылку или исходные байты `.torrent`, — а
`torrents.json` помнит, кто его добавил. Источник, а не сводка метаданных:
infohash — это SHA-1 от info-словаря, и восстановленный по сводке торрент
получил бы другой хеш и потерял бы и владение, и привязку комнат (bug-0053).
Запись без источника пропускается с предупреждением. Владение, пережившее
рестарт, держит гейт чтения из bug-0049; торрент без владельца (старше учёта)
остаётся открыт всем — иначе он стал бы навсегда нечитаемым.

## Фронтенд (Go/Fyne)

Один язык с бэкендом, одна сборка, три платформы из одного места. Раньше
здесь был Qt/C++ с libmpv; причины смены и решение владельца — в idea-0067.

| Пакет | Ответственность |
|---|---|
| `internal/backend` | поиск, запуск и остановка бэкенда-ребёнка; наблюдение за его смертью |
| `internal/api` | HTTP-клиент своего бэкенда: торренты, файлы, magnet, телеметрия буфера |
| `internal/rtc` | Комната без сервера: протокол стримов, mesh поверх libp2p, ростер, хост, takeover, инвайты |
| `internal/room` | Только телеметрия буфера на data plane (остальное ушло в `rtc` вместе с брокером) |
| `internal/player` | внешний процесс `mpv`: запуск, JSON IPC, заголовки для потока |
| `internal/catalog` | пользовательские тексты ru/en |
| `internal/ui` | окно, лоток, настройки, решения окна, вынесенные в тестируемые функции |

### Один бэкенд

`api.Client` говорит с одним сервером — своим. Плоскостей больше нет: состав
и команды идут mesh'ем, а не с сервера комнаты, и второго адреса держать
незачем.

Проверить это можно одним утверждением, и оно неочевидно: `StreamURL()`
возвращает адрес **своего** бэкенда. Гость, собравший его из чужого адреса,
смотрел бы чужую загрузку вместо своей — ровно то, что запрещает цель.

### Настройки окна

Всё, что настраивается, живёт в одном окне настроек: язык, тема, путь к mpv,
хранилище (память или диск с каталогом), шлюз htorrent, рандеву запасного пути,
имя в комнате и запасные релеи. Раньше тут
были только язык, тема и путь к mpv, а полдюжины возможностей собственного
бэкенда требовали ручного запуска сервера, который тогда переставал быть
своим (idea-0083). Хранятся настройки в `settings.json` рядом с данными
приложения (`internal/ui.DefaultPath`); отсутствующий или повреждённый файл —
не ошибка, а дефолты.

Что применяется когда. Тема, рандеву и релеи — сразу: первая перекрашивает
окно, вторые читаются при следующем входе в комнату. Рандеву и релеи нужны для
запасного пути, но не для основного: адрес в коде комнату собирает сам. Язык, mpv, хранилище и шлюз
читаются при старте, и в форме об этом сказано прямо: бэкенд-ребёнок уже
запущен, и окно не может его перенастроить. Настройка, которая выглядит
применённой и не применена, хуже отсутствующей.

Как выбор доезжает до бэкенда-ребёнка — двумя каналами, и разделение
намеренное:

- хранилище — **флагами** `--data-dir` и `--disk-storage`: флаг не дефолт, и
  унаследованная переменная окружения (`DATA_DIR`) не подменит выбор человека.
  В режиме памяти передаётся пустой `--data-dir` — персистентность выключена
  целиком, на диске не остаётся ничего;
- шлюз — **окружением** (`GATEWAY_URL`, `GATEWAY_USER`, `GATEWAY_PASS`,
  `GATEWAY_CA_CERT`): переменные, решаемые запуском, заменяются, а не
  добавляются, поэтому выключенный в окне шлюз не переживёт следующий запуск.
  Пароль при этом не попадает в командную строку;
- токен доступа — на стандартный ввод ребёнка (`--token-stdin`), тоже не в
  командную строку (deviation-0061).

### Композиция окна

Зоны окна собираются в `internal/ui/layout.go`: заголовок (`zoneHeading`),
волосяная линия (`rule`), содержимое (`section`), промежутки между зонами
(`contentStack`). Тулбар и зоны делят верхнюю строку, библиотека — центр
`Border`: зона в строке `VBox` получает минимальную высоту, и окно под ней
пустует.

Две ловушки, обе вынужденно записаны, потому что обе выглядели как «просто
не работает»:

- **Поле не в том слоте.** Поле magnet и поле кода приглашения стояли в
  `left`/`HBox` и обрезались до «маг» и «вста:» — боковая панель получает
  свою минимальную ширину. Растягивается только объект `Border`, поэтому
  поле передаётся последним аргументом.
- **Пустая строка — это дыра.** Пустой `Label` сохраняет высоту, и под
  заголовком получается провал. `setLine` прячет строку вместо того, чтобы
  оставлять пустоту; `roomLabel`, `connLabel`, `preparing` и `mediaLbl`
  стартуют скрытыми.

Разделитель — прямоугольник в цвет `ColorNameSeparator` высотой в пиксель,
а не `widget.NewSeparator`: тот рисуется жирной серой полосой и читается как
заплатка поверх окна, а не как граница.

### Потокобезопасность виджетов

Fyne требует трогать виджеты из потока, где живёт цикл событий. Почти всё
здесь приходит откуда-то ещё: тикер опроса, HTTP-вызов, поток сообщений mesh'а.
Поэтому любое изменение виджета идёт через `onMain` (внутри — `fyne.Do`).

Это не теория: собранное приложение печатало предупреждение Fyne на каждом
тикере, пока правки не было.

### mpv как внешний процесс

Не libmpv внутри процесса, а `mpv` рядом. Причины: одно и то же работает на
трёх платформах без обёртки, и mpv не тащит в приложение половину своих
зависимостей.

Токен доступа не едет в URL: `player.FormatHeader` превращает его в
`--http-header-fields`, и `/stream` проверяет заголовок (idea-0066). В URL
остаётся только infohash.

Сокет IPC — на процесс (`torrsync-<pid>.sock`). Два экземпляра на одном
сокете управляли бы плеером друг друга молча: каждая команда успевала бы.

**Первую фразу цели держит проверка, а не вера.** «Файл начинает играть, как
только набрано достаточно данных» проверяется против настоящего mpv: источник
отдаёт треть фильма и останавливается — ровно торрент, у которого скачана
только голова, — и плеер обязан начать играть на этом. Проверка
`TestRealMpvPlaysWhileTheSourceIsIncomplete` требует, чтобы позиция сдвинулась
пока источник держит остаток, и чтобы она пошла дальше, когда остаток
наконец отпущен. Дальше остаток приходит под playback'ом — это и есть вторая
половина обещания. Проверка обязательна там, где mpv есть: гейт CI
(`Re-run player tests without skipping`) делает пропуск красным.

Проверка кусается: если источник придержит и голову, позиция не сдвинется и
проверка станет красной.

Окно mpv глухо к вводу намеренно: `--no-input-default-bindings` гасит и
встроенные биндинги, и клавиши скриптов (включая OSC — так и написано в
мануале), поэтому клавиатура и кнопки OSC в окне плеера не отвечают.
Это не дефект, а следствие решения «пульт — наше окно»: второй пульт,
который комната видит только опросом, не нужен (bug-0101, закрыт
документацией вместо живого прогона).

Пульт окна — те же два примитива, что весь остальной контроль: `command`
для set/cycle без ответа (громкость, fullscreen) и `request` для чтения
свойств (позиция, длительность, пауза, громкость). Окно mpv при этом
остаётся экраном: seeking идёт абсолютной командой, громкость —
свойством `volume`, fullscreen — циклом свойства — и всё это тем же
сокетом, которым комната ведёт плеер хоста.

### Интернационализация

Исходный язык — английский, поддерживаются `ru` и `en`. Тексты живут в
`internal/catalog`, ключ — смысловая строка вроде `status.playing`, а не
английский текст. Английский — источник и запасной вариант: непереведённый
ключ показывает английскую строку, а не ключ и не пустую подпись. Переводчиков
этим способом не запутать, а английский текст можно улучшать, не ломая ключи.

Выбор языка: `--lang ru|en` → сохранённая настройка → язык системы, и только
если он поддерживается (иначе английский). Флаг доходит и до окна, и до лотка:
раньше `--lang` менял только меню лотка, а окно продолжало читать настройку.
Настройка читается **до** создания виджетов: подписи берут текст в
конструкторах, и установленный позже перевод к ним уже не применится.

Любая видимая человеку строка идёт через каталог, и за этим следит проверка:
`internal/ui/catalog_usage_test.go` обходит исходники окна и падает и на
строковом литерале мимо `tr`/`trf`, и на ключе, которого в каталоге нет, —
второй случай рендерится пустой подписью и выглядит как отсутствующая функция
(idea-0073).

Статус торрента приходит с бэкенда английским идентификатором
(`downloading`, `seeding`) — это машинное значение в API, а не текст для
человека. Оно переводится только для отображения; на бэкенд уходит исходный
идентификатор, иначе переведённая строка испортила бы состояние торрента.
Неизвестный статус показывается как пришёл — новое состояние видно сразу, без
правки фронтенда.

## ADR: комната собирается по адресу из кода, DHT — запасной путь; команды идут стримами

**Статус:** принято · **Дата:** 2026-10-16 · **Заменяет:** ADR «комнаты
встречаются через weron, команды идут data-каналом» от 2026-10-15 (пересмотр
по собственному условию: зависимость заморожена — последний пуш 18 месяцев
назад, багфикс-PR висит 2 года, — а внутри две гонки, которые ловит
race-детектор и которые нельзя обойти из нашего кода, см. bug-0084; текст
ниже — новое решение, а не правка старого).

**Пересмотрено:** 2026-10-19, первое. Сработало условие пересмотра №1 («публичный
bootstrap стал ненадёжным»): на живой машине рандеву не сходилось, а локальный
testbed сходился. Решение ADR — меши поверх libp2p-DHT — остаётся; изменился
способ достижения рандеву, и он описан в секции «Рандеву: запасной путь — свои
ноды, узкий анонс и широкий следом»: собственные ноды вместо списка
библиотеки, мёртвый seed вместо мёртвого входа, узкий анонс на входе и широкий
следом (idea-0122).

**Пересмотрено:** 2026-10-19, второе. Сработало условие пересмотра №4
(«комната не собирается вовсе»): против публичного DHT встреча не состоялась
примерно в половине окон, а на локальном testbed'е срывалась в одном прогоне
из пяти при исправных участниках — то есть это свойство кода, а не погода
чужой сети. Причина найдена: «узкий анонс» при входе в сеть не уходит ничего
(`Provide(key, brdcst=false)` пишет запись только в локальный provider-store),
поэтому комната видима для другой стороны лишь после широкой публикации, а
«ближайшие пиры» у хоста и у гостя — разные множества. Меняется способ
встречи: комната собирается по адресу, который хост кладёт в код приглашения,
а публичный DHT остаётся запасным путём и источником публичного адреса узла и
кандидатов в релеи (idea-0131). Решение ADR — меши поверх libp2p, команды
по стримам, никакого сервера комнаты — остаётся.

### Контекст

Нужно, чтобы участники комнаты узнавали о действиях друг друга: кто вошёл, кто
вышел, кто играет, на какой позиции. Это обмен метаданными о просмотре, а не
медиаданные — сам файл идёт отдельным путём, из роя в каждый бэкенд сам.

### Решение

Серверного брокера нет, как раньше. Рандеву — публичный DHT
(bootstrap-ноды IPFS + Kademlia), транспорт — шифрованные стримы go-libp2p
v0.50.0 между участниками. Сервер хранит торренты своего владельца и ничего
не знает о комнатах.

- Bootstrap по умолчанию — собственный список нод проекта (см. «Рандеву»);
  `--bootstrap` меняет его целиком. Это запасной путь, а не основной: комната
  собирается по адресу из кода. В тестах — только локальный testbed: тест,
  которому нужен чужой сервис, падает по чужим причинам. Именно поэтому путь
  «публичный DHT» пришлось измерять пробником вне репозитория: тест, который
  ходит в чужую сеть, это не тест.
- Встреча — по адресу. Код приглашения несёт multiaddr'ы хоста, гость звонит
  напрямую; если адрес не сработал, гость ищет хоста **по его peer ID**
  (`Node.FindPeer` → `dht.FindPeer`), и это маршрутный поиск, а не поиск
  провайдера: запись о провайдере отвечают две стороны по-разному («ближайшие
  пиры» у публикатора и у ищущего — разные множества, bug-0133), а таблица
  маршрутизации отвечает одинаково. Пин на это свойство: узел, который не
  анонсировал ничего, всё равно находится по своему ID.
  DHT при этом остаётся источником публичного адреса узла (autonat) и
  кандидатов в релеи — без него узел не знает, как его зовут снаружи, и не
  поднимает резервацию.
  Гость, пришедший с адресом в коде, рандеву не ждёт: его вход возвращается
  сразу, а сеть поднимается следом. Хост то же самое: узел поднялся — адреса
  есть, код готов, а рандеву, если он понадобится, приходит следом.
- Mesh достраивается сам: `hello` несёт адреса отправителя, и каждый вошедший
  звонит тем, кто уже в комнате. Старый хост адреса не присылает и остаётся
  «листом» в звезде; версионирования протокола нет и не появилось.
- Admission — handshake по паре «пароль + ключ» из приглашения до принятия
  стримов. Ни пароль, ни ключ никуда не уходят: пир доказывает знание, а не
  предъявляет. PSK-гейта на весь рой нет осознанно: с ним узел не говорил бы
  ни с публичными bootstrap-нодами, ни с публичными релеями (idea-0091).
- Хост остаётся: mesh симметричен, управление — нет. Команды принимаются
  только от пира, приславшего magnet; уход хоста без передачи закрывает
  наименьший живой peer ID.
- Истории событий и replay нет: стрим надёжен и упорядочен, пока жив, и
  компенсировать нечего. Сверка при реконнекте осталась.
- Код приглашения — `community:password:key:addrs`, генерирует хост. Первые
  три части без двоеточий, четвёртая — список multiaddr'ов, и двоеточия в ней
  есть. community называет комнату, addrs — узел в ней, а peer ID хоста лежит
  в коде вместе с адресами: гость знает, кому именно дозвонился.
- Релеи — autorelay: за жёстким NAT комнату держит публичный релей, а не
  прямое соединение. Прямые пиры релея не касаются. Кандидатов autorelay
  берёт из двух источников: обходы DHT (ничего настраивать не надо) и
  запасные релеи владельца (`--relays`, настройка `relays`). Комнатные
  стримы открываются и по релеевым соединениям: они constrained, и без
  `WithAllowLimitedConn` в `DialRoom` такой путь был бы закрыт.
  У заданных релей резервацию берёт сам узел (`Node.ReserveAt`), а не
  autorelay: autorelay не берёт релей с приватным адресом, а именно такие
  релеи чаще всего и задают. Без резервации релеевый путь не существует
  вовсе, и тогда у пира, чей адрес недосягаем, не остаётся ничего.
  Дозвон через релей — когда адрес из кода не отвечает: идентификатор пира
  в коде есть, а релею для прыжка нужен именно он.

### Чем платится за это решение

Честно — решение не бесплатное, и цена не только в простоте.

**Отладка «не соединились».** Причин по-прежнему десяток, разбирать на глаз
у пользователя. libp2p добавляет hole punching и autorelay, поэтому
«не соединились» стало реже — но не читаемее.

**Медленное схождение запасного пути.** Основной путь — адрес из кода — идёт
секундами. Запасной, поиск по peer ID через публичный DHT, стоит минут:
полные прогоны против настоящей сети давали и 1m55s, и 3m04s, и 4m35s, и
«не сошлось за пять с половиной минут» (bug-0128). Минуты — принятая плата
запасного пути; поломка — нет, и её ловит публичный ряд измерений.

**Чужая зависимость осталась, но ушла с главного места.** Публичные DHT-ноды
видят IP пиров (маршрутизация публична по построению), релеи видят факт
шифрованного трафика. Список
нод теперь наш, а сеть вокруг них — по-прежнему чужая: собственные адреса
починили вход, но не отменили того, что запасной путь живёт в чужой
инфраструктуре и может перестать. Команды не видит никто: сигналинг
шифруется ключом из приглашения, стримы — Noise/TLS. Цена нулевой эксплуатации,
принятая осознанно; свой bootstrap — это тот самый отдельный сервис, из-за
которого ADR и был когда-то написан, и цель его по-прежнему запрещает.

**Код стал длиннее.** Адреса в коде — это сотня с лишним символов, и код
перестаёт читаться глазами. Он и не читался: это машинная строка, которую
копируют одним сообщением.

**Зависимость-стек.** go-libp2p тянет порядка сотни модулей против крошечного
weron: сборка дольше, обновления чаще, API churn выше. Принято как цена живого
мейнтейна — замороженная зависимость уже стоила двух гонок детектора.

### Что решение НЕ даёт (и не обещает)

Приватность содержимого не меняется: медиаданные шли мимо сервера и идут
мимо. Устойчивость к падению bootstrap — только у установленных соединений:
переговоры о новых без DHT невозможны, и это принято как есть. Адрес из кода
живёт ровно столько, сколько живёт адрес: перезапустился хост — нужен новый
код, и это не поломка, а свойство адреса.

### Условия пересмотра

Проверяемые условия, а не пожелания. Любое из них означает: открыть вопрос
заново, а не «когда-нибудь посмотреть».

1. ~~**Публичный bootstrap/DHT стал ненадёжным или враждебным**~~ —
   **сработало 2026-10-19**, см. bug-0121: четыре из пяти адресов по
   умолчанию не набираются, и с оставшимся один комната не собирается. Ответ,
   который дали: смена адресов по умолчанию (свой список нод), а не возврат
   брокера и не свой bootstrap — решение владельца, idea-0122.
2. **Комнатам на 100+ участников понадобился сервер.** Mesh рассылает каждую
   команду каждому напрямую; когда это перестанет хватать — метрики mesh'а,
   а не предположения.
3. **Приватность стала требовать, чтобы и рандеву не видел IP пиров.**
   Тогда нужен свой bootstrap с приватным рандеву как минимум, а как максимум —
   другой транспорт. Запасной выход проверен заранее: повторная оценка
   альтернатив — по карточке idea-0086, вариант «свой клиент на pion» отвергнут
   как стократ дороже за тот же результат.
4. ~~**Комната не собирается вовсе, и виноват код, а не чужая сеть**~~ —
   **сработало 2026-10-19**: на локальном testbed'е срыв в одном прогоне из
   пяти при исправных участниках (bug-0130), а причина — узкий анонс, который
   в сеть не уходит ничего (bug-0133). Ответ, который дали: встреча по адресу
   из кода, DHT — запасной путь, и он обязан работать не хуже основного —
   решение владельца, idea-0131.
5. **Запасной путь перестал быть запасным.** Если поиск по peer ID через
   публичный DHT перестал находить пира там, где адрес не работает, — снова
   открыть вопрос: собственная точка рандеву (запрещена целью, значит, это
   правка цели) или другой транспорт.

## Принципы разработки

1. Магические числа живут только в `internal/constants/constants.go`.
2. Ошибки — структурированные, из `internal/errors`; тип проверяется через
   `errors.As`, прямым type assertion пользоваться нельзя.
3. Интерфейсы объявляются в `internal/interfaces.go`, а не рядом с
   реализацией: `api` не должен знать устройство сервисов.
4. Аккаунтов нет. Токен доступа один на процесс, сравнение —
   `crypto/subtle.ConstantTimeCompare`. Идентификаторы комнат
   нормализуются в нижний регистр.
5. Всё, что приходит от пользователя, валидируется и санируется; в URL
   попадают только проверенные значения.
6. Комнаты собираются по адресу из кода приглашения и говорят шифрованными
   стримами напрямую; DHT-рандеву — запасной путь, а не способ встречи.
   Серверного брокера комнат нет и не вводится обратно молча — только через
   ADR.
7. То, что выводится из кода, не переписывается руками: формы API живут в
   Swagger, метрики — в `internal/metrics`.
8. Решение, которое нельзя проверить тестом, выносится в отдельную функцию и
   тестируется там. Так сделано для решений окна: поведение передачи закрытия
   в тест не попадает, потому что тестовый драйвер Fyne закрывает окно мимо
   перехвата.
9. **Этот файл и [CONCEPT.md](CONCEPT.md) описывают целевое состояние, а не
   текущее.** Расхождение с кодом лечится кодом: пока флаг не реализован,
   документация права, и его нужно реализовать. «Описать в документации то,
   что делает код» делает расхождение невидимым, и следующая сессия примет
   исправленный вниз документ за цель. Документацию меняют только осознанным
   решением изменить цель — и тогда это правка цели, а не молчаливая правка
   описания.

## Проверки должны уметь краснеть

Зелёная сборка ценна только тогда, когда сломанная может стать красной.
Поэтому вне осознанного исключения запрещены:

- `|| true` в рецепте Makefile;
- `continue-on-error: true` у шага или джобы CI;
- `-` в конце команды в рецепте;
- тест, который проверяет только не-nil или повторяет собственную логику.

Два бага дошли до `main` при полностью зелёном пайплайне именно поэтому: SSE
отдавал 500, потому что обёртка middleware теряла `http.Flusher`, и подпись
stream-тикета считалась над пустой строкой, то есть не проверяла ничего.
Ни одна проверка этого не видела.

Если проверка выглядит нестабильной — чинить нестабильность, а не
заглушать её.

**Чем закрывается карточка с багом.** Правка плюс тест, который без неё
падает, плюс зелёный CI на всех трёх платформах. Не «проверено на одной
машине» и не «остаётся до отзыва живых пользователей»: такой остаток —
это не знание, а ожидание, и доска, которая копит ожидания, перестаёт
отвечать на вопрос «что сейчас сломано». Остаточный риск при этом пишется
в журнал прямо — если правка окажется неверной на чужом железе, отчёт
пользователя будет про названный коммит, а не про версию, в которой он
вышел (решение владельца, 2026-10-19).

### Ворота репозитория

Проверка, которую можно обойти, не проверяет ничего. Поэтому у репозитория
есть ворота, и они настроены, а не подразумеваются (решение владельца,
2026-10-20, idea-0140):

- оповещения об уязвимостях зависимостей включены, а `dependabot.yml`
  поднимает их на обновления: два Go-модуля и действия GitHub;
- тег `v*` защищён правилом репозитория: создать релизный тег может только
  владелец. `main` намеренно остаётся без защиты — пуши в неё идут как
  шли, а линия релизов защищена;
- сторонние действия закреплены на полном SHA коммита: подменить версию
  действия нельзя. Свои действия GitHub остаются на тегах — их версии
  приходят из того же места, что и сам GitHub;
- вики выключена: править её может любой аккаунт, а документация проекта
  лежит в репозитории;
- секреты сканируются, а пуш с секретом отвергается.

То, что ворота настроены, — не «безопасно». Это значит, что ворота есть и
что их видно: остальное — вопрос кода, который эти ворота проверяют.

## Соглашения по тестам

Бэкенд:

```bash
cd backend
make test              # весь набор
make test-race         # с race-детектором
make test-coverage     # покрытие
make test-fuzz         # fuzzing
make test-mutation     # мутационное покрытие
make test-ci-contract  # проверка «CI описан верно»
```

`internal/cicontract` — пакет без production-кода — сторожит соглашение между
пайплайном и репозиторием: мутационный объём называет только существующие
пакеты, команда покрытия не выбрасывает несуществующий, в CI нет шага, который
сам про себя говорит «placeholder», и всякий workflow, который ставит Go,
закрепляет одну и ту же версию (две формы закрепки допустимы — `GO_VERSION` и
версия прямо в `setup-go`, — но разные версии в разных файлах означают, что
зелёная джоба собрана одним компилятором, а читают её о другом). Он читает
`.github/workflows/` с диска, а файл, который читает тест, для `go test` не
является входом, поэтому прогон обязателен с `-count=1`: иначе кэш результатов
отдаст зелёный ответ, измеренный по вчерашнему файлу (bug-0123).

**Измерение, а не гейт.** `.github/workflows/rendezvous.yml` раз в шесть часов
поднимает тех же двух участников против настоящего публичного DHT, **никогда не
валит пайплайн** и пишет результат в summary джобы. Проверка, которая краснеет
примерно в половине окон, учит игнорировать красное, поэтому замер — это ряд, а
не гейт: «сошлось ли за две минуты» и «сошлось ли вообще» не отвечаются одним
прогоном. Отдельный файл, а не джоба по расписанию внутри `ci.yml`: расписание
там гоняло бы ещё и мутационное тестирование (bug-0129).

**Что меряет ряд теперь.** Основной путь — адрес из кода — детерминирован, и
его закрывает герметичный гейт; живая сеть нужна для запасного пути, который
иначе не измерить. Ряд меряет запасной путь: сошлись ли участники, за сколько
и каким путём.

**Что ряд не меряет.** Прямой путь между двумя настоящими машинами в
интернете не измерен: у обоих участников измерения одна сеть, и там адрес
из кода всегда доступен. Это не задача, а решение: прямой путь держат два
гейта — герметичный и сценарий через namespace'ы, где прямой путь закрыт
нарочно, а релей и запасной работают, — и сценарий этот строже реального
случая, потому что маскирует **обе** стороны под **один** публичный адрес,
а один NAT с общим адресом к hole punching труднее, чем два разных.
Решение владельца, 2026-10-21: вторую машину не заводим (idea-0141 закрыта).

**Порог и что при его нарушении.** Ряд собирается в файле измерений в
репозитории (`measurements/rendezvous.md`): джоба дописывает строку и
закладывает её в `main` коммитом бота, иначе ряд живёт 14 дней в summary добы,
и его никто не видит. Порог: **не меньше 90% из 20 последних прогонов собираются
за 90 секунд или быстрее**. Ниже — джоба пишет карточку на доску (номер —
следующий свободный, его считает скрипт по доске и журналу): порог, который
никто не проверяет, мёртв.

Ряд ложится прямо в `main`, а не в pull request: репозиторий не разрешает
Actions создавать pull request'ы, и main не защищён. Строка измерений — это
данные, а не намерение: ей не нужно ревью, чтобы быть правдой.

Вся механика — в `.github/scripts/rendezvous-series.sh`, а не в YAML: скрипт
можно прогнать локально на настоящем ряду, и он же проверяется на записях, где
порог нарушен. Проверка порога никогда не валит прогон: измерение не должно
краснеть, а карточка — это то, что читает человек.

**Гейт, который умеет краснеть.** Герметичный сценарий встречи обязателен и
не мигает: ни одного срыва в N прогонах подряд на CI, иначе джоба краснеет.
Правило здесь то же, что и везде: нестабильную проверку чинят, а не заглушают (bug-0130).

**Измерение расхождения синхронизации.** Цель обещает, что участники комнаты
видят «тот же момент в той же секунде», и до 2026-10-21 этого никто не
измерял: тесты говорили, что команда дошла, а не то, что человек видит.

Измерение живёт в `frontend/internal/ui/sync_measurement_test.go` под меткой
`measurement` и гоняет то, что гоняет приложение: два настоящих mpv на одном
файле, одна настоящая комната поверх настоящего libp2p-потока, тот же
`roomTick`, тот же `applySeek`, тот же `FollowPosition`. Разница позиций
снимается каждые полсекунды; окно не рисуется — измерению не на что смотреть.

```bash
cd frontend
FYNE_DRIVER=offscreen go test -tags measurement -timeout 6m \
  -run TestTheRoomKeepsEveryoneInTheSameSecond -v ./internal/ui/
```

Метка, а не обычный тест, потому что это измерение: оно идёт две минуты и
живёт в своей джобе (`sync-measurement` в `ci.yml`), а не в каждом прогоне на
трёх платформах. mpv и ffmpeg ему нужны настоящие: без них измерение падает,
а не пропускается.

Что оно меряет — три вещи, и третье отдельно от первых двух:

| Что | Расхождение | Время |
|---|---|---|
| Комната играет | 0.20 с максимум | — |
| Пока команда перемотки летит | 60.00 с | это сам прыжок: участник на старой позиции, пока команда не дошла |
| После того, как команда встала | 0.20 с максимум | прыжок встал за 600–624 мс (два прогона) |

Порог стоит в самом измерении (`steadyDivergenceLimit` — одна секунда, порог
цели), и измерение краснеет, когда он нарушен; джоба `sync-measurement`
краснеет вместе с ним. Обещание «та же секунда» теперь проверяется, а не
предполагается (idea-0142, idea-0146).

**Ряд измерений расхождения.** Гейт отвечает на вопрос «этот прогон в
пределе?», а ряд — на вопрос, который один прогон не отвечает: **не растёт
ли расхождение**. Пока цифра держится у нуля, всё в порядке; когда она
ползёт к пределу, об этом должен узнать человек, а не тот, кто через полгода
откроет лог джобы.

Ряд живёт в `measurements/sync.md`: одна строка — один прогон, и кладёт её
сама джоба `sync-measurement` (только на пуше в `main`: измерение пул-реквеста
не пишет в `main`). Правило ряда: не меньше 90% из 20 последних прогонов
держат расхождение в пределах обещания — той же секунды. Ниже порога ряд
пишет карточку на доске.

Число обещания **читается из самого измерения** (`steadyDivergenceLimit` в
`frontend/internal/ui/sync_measurement_test.go`), а не живёт в скрипте
вторым экземпляром: ряд и гейт не могут сказать разного. Скрипт — тот же
`.github/scripts/sync-series.sh`, что и у запасного пути, и он же проверяется
на записях, где порог нарушен (тест `TestTheSeries*` в
`backend/internal/cicontract`).

Механика вся — в скрипте, а не в YAML: скрипт можно прогнать локально на
настоящем прогоне, и он же проверяется на записях, где порог нарушен.

```bash
cd frontend
FYNE_DRIVER=offscreen go test -tags measurement -timeout 6m \
  -run TestTheRoomKeepsEveryoneInTheSameSecond -v ./internal/ui/ 2>&1 | tee sync.log
cd ..
.github/scripts/sync-series.sh record frontend/sync.log measurements/sync.md \
  frontend/internal/ui/sync_measurement_test.go
.github/scripts/sync-series.sh check measurements/sync.md "$PWD" \
  frontend/internal/ui/sync_measurement_test.go
```

Фронтенд:

```bash
cd frontend
FYNE_DRIVER=offscreen go test ./...
FYNE_DRIVER=offscreen go test -race ./...   # как в CI
```

`FYNE_DRIVER=offscreen` обязателен: без дисплея тесты висят, ожидая окна, а не
падают — то есть зелёного прогона не будет, но и красного тоже.

**Сценарные тесты** (`frontend/internal/integration`) поднимают настоящие
бинарники бэкендов, локальный трекер и локальный DHT-testbed — и гоняют по ним
настоящую комнату без сервера: magnet по стримам, куски из роя,
команды хоста, takeover после его ухода. Это единственный тест, способный
поймать расхождение пиров между собой: модульные тесты кормят разбор тем
форматом, который разбор и ждёт, поэтому код и тест могут согласны быть между
собой и оба разойтись с сетью. Именно так находились баг с конвертом `P2PEvent`
и гонка рандеву на переиспользованном сигналлере.

**Сценарий «комната втроём»** (`TestARoomOfThreeIsARoomAndNotAPair`) — тот
же набор, но с тремя участниками: хост и два гостя, каждый со своим
бэкендом и своим mesh'ем, гости приходят по адресу из кода. Проверяется то,
что решается только втроём: гости находят **друг друга** (адресная книга
превращает звезду в mesh, и это видно по списку пиров), фильм доходит до
обоих и оба качают его из роя настоящими кусками, пауза хоста доходит до
обоих, отчёт о буферизации от **не-хоста** доходит до хоста и до второго
гостя, а после ухода хоста роль забирает наименьший живой peer ID, и оба
выживших называют его одного и того же.

Комната из двоих — это пара с протоколом; комната из троих — комната. Сколько
участников комната держит, по-прежнему не проверено: условие ADR про сотню
открыто, и проверять его надо на больших числах, а не на трёх.

```bash
cd frontend
FYNE_DRIVER=offscreen go test -v ./internal/integration/
```

**Сценарий «комната сквозь NAT»** — единственный, кому нужны права, и
единственный, кто ставит настоящий вопрос: сойдётся ли комната, когда стороны
не могут дозвониться друг другу. Два участника, два сетевых пространства, между
ними маскарадинг и сброшенное правило FORWARD: прямого пути нет, остаётся тот,
который обещает ADR — hole punching, а если не вышло, релей. Подготовка живёт
в `tests/netns/room-nat.sh`, участники — переисполняемый бинарник тестов
внутри каждого пространства, а проверка «соединение идёт через релей» берётся
из `ConnStatus`, а не из догадки.

```bash
sudo tests/netns/room-nat.sh up
TORRSYNC_NETNS=1 FYNE_DRIVER=offscreen \
  go test -timeout 12m -run TestARoomAcrossNAT ./internal/integration/...
sudo tests/netns/room-nat.sh down
```

Локальный прогон без пространств этот тест пропускает — и это пропуск явный: в
CI джоба Room Across NAT обязательная, и падает, если пространства не создались
(никакого `|| true`, никакого «пропустить, если не вышло»). Механика
участников при этом проверяется без привилегий: `TestTheNATParticipantMachineryWorksOnOneHost`
поднимает тех же двух участников на одной машине, где они соединяются прямо, —
чтобы механизм не ржавел между прогонами CI (idea-0126).

Один сценарий намеренно не делает: не добавляет magnet гостя. Добавление
magnet означает вход в рой и ожидание метаданных, а торрента из теста нет ни в
одном рое — ожидание зависло бы вместо падения. Тождество торрента проверяется
другим сценарием, на двух настоящих бэкендах.

Контракт (нужна нативная библиотека pact FFI, качается в CI автоматически):

```bash
cd backend
go test -tags contract -run PactProvider ./internal/contract/...
```

Мутационное покрытие ограничено пакетами `validation`,
`persistence`, `utils`, `buffer` — полный прогон по всему бэкенду занимает
часы ради числа, которое никто не смотрит. Порог задан в джобе
Mutation Testing и должен пересчитываться при изменении списка пакетов.
Список изначально содержал ещё и `internal/sync` с `internal/p2p` — пакеты,
удалённые вместе с брокером комнат, — то есть гейт мерил не то, что
объявлял, и оставался зелёным (bug-0123); теперь состав списка проверяется
тестом, а не комментарием.

`make test-all` запускает контракт. Pact-потребитель на фронтенде не
реализован: контракт проверяет провайдер на стороне бэкенда, а соответствие
клиента ему проверяют сценарные тесты — запуском настоящего бинарника.

`pacts/frontend-backend.json` поэтому — **фикстура, а не записанный
потребителем контракт**: записывавшего его Qt-клиента больше нет, и когда API
меняется, файл правится руками. Проверка честно отвечает на вопрос «этой ли
формы ответ», но не на вопрос «этого ли ждёт клиент»; за второе отвечают
сценарные тесты. Решение владельца — оставить файл в этом качестве и назвать
его так прямо (idea-0076).

## Запуск как службы

### Linux (systemd)

`/etc/systemd/system/torrsyncplayer.service`:

```ini
[Unit]
Description=TorrSyncPlayer Server
After=network.target

[Service]
Type=simple
User=torrsyncplayer
WorkingDirectory=/opt/TorrSyncPlayer
ExecStart=/opt/TorrSyncPlayer/build/torrsyncplayer
Restart=on-failure
RestartSec=5
Environment=PORT=8889

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now torrsyncplayer
```

### macOS (launchd)

`~/Library/LaunchAgents/com.torrsyncplayer.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
    "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.torrsyncplayer</string>
    <key>ProgramArguments</key>
    <array>
        <string>/path/to/torrsyncplayer</string>
    </array>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <true/>
</dict>
</plist>
```

```bash
launchctl load ~/Library/LaunchAgents/com.torrsyncplayer.plist
```

### Windows (NSSM)

```bash
nssm install TorrSyncPlayer "C:\path\to\torrsyncplayer.exe"
nssm start TorrSyncPlayer
```

## Docker

```bash
cd backend
docker build -t torrsyncplayer-server .

# в памяти
docker run -d --name torrsyncplayer \
  -p 8889:8889 -e LOG_LEVEL=info \
  torrsyncplayer-server

# с постоянным каталогом
docker run -d --name torrsyncplayer \
  -p 8889:8889 \
  -v torrsync-data:/data \
  -e DATA_DIR=/data -e LOG_LEVEL=info \
  torrsyncplayer-server

# с TLS
docker run -d --name torrsyncplayer \
  -p 8889:8889 \
  -v /path/to/certs:/certs:ro \
  -e TLS_CERT=/certs/cert.pem \
  -e TLS_KEY=/certs/key.pem \
  torrsyncplayer-server --tls
```
