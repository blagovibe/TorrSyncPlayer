# TorrSyncPlayer — Full Project Audit Plan

## Scope
Complete audit of the TorrSyncPlayer codebase: code quality, architecture, dependencies, security, tests, CI/CD, and documentation.

---

## 1. Security Vulnerabilities

### 🔴 HIGH — Transitive dependency vulnerabilities (15 total via npm audit)
**Severity: High (6 high, 5 moderate, 4 low)**

| Vulnerable Package | Severity | Issue | Fix |
|---|---|---|---|
| `ip` (via bittorrent-tracker) | **High** | SSRF improper categorization in isPublic (CVE-2024-294110) | Upgrade WebTorrent or patch transitive dep |
| `webtorrent` (via torrent-discovery → bittorrent-tracker → ip) | **High** | Same SSRF chain + load-ip-set vulnerability | WebTorrent 2.x has no fix; consider pinning or accepting risk |
| `vite` (via esbuild ≤0.24.2) | **Moderate** | Dev server request forgery (CWE-346) | Upgrade Vite to ≥8.0.14 (breaking — requires ESM rewrite) |
| `vitest` (via vite, @vitest/mocker, vite-node) | **Moderate** | Multiple transitive CVEs | Upgrade Vitest to ≥4.1.7 (breaking — major API changes) |
| `crypto-browserify` (via elliptic) | **Low** | Cryptographic primitive with risky implementation | Acceptable for non-crypto usage |
| `elliptic` | **Low** | CWE-1240 risky crypto implementation | Transitive; low impact |

**Recommendation:** These are primarily dev/build-time vulnerabilities (esbuild, vite, vitest, crypto-browserify). The runtime-critical ones (`ip` SSRF via bittorrent-tracker, webtorrent) are harder to fix without downgrading or replacing WebTorrent. Apply `overrides` in package.json for immediate mitigation where possible.

**Action:** Add npm `overrides` to force `ip >= 2.0.2` if compatible. Document accepted risks for WebTorrent chain.

### 🟡 MEDIUM — Magnet link validation too permissive
**File:** `client/src/utils/torrent.ts:3`

The regex `^magnet:\?xt=urn:(?:btih|btmh|sha1|ed2k):...` validates structure but doesn't sanitize trackers or other parameters. Malicious magnet links could contain tracker URLs pointing to internal services (SSRF via WebTorrent client).

**Recommendation:** Parse and validate individual magnet link parameters. Strip or validate tracker URLs (`tr=` params) against an allowlist.

---

### 🟡 MEDIUM — WebTorrent ServiceWorker intercepts all fetch events
**File:** `client/public/webtorrent-sw.js:14`

The SW scope check `url.includes(self.registration.scope + "webtorrent/")` is a simple string inclusion. A crafted URL like `https://evil.com/prefix/webtorrent/foo` could pass the filter if the scope substring appears elsewhere.

**Recommendation:** Use proper URL pathname matching: `new URL(url).pathname.startsWith(scope + "webtorrent/")`.

---

### 🟡 MEDIUM — IPC sender validation doesn't check in production static server origin
**File:** `client/electron/main.cjs:226-249`

`validateIpcSender` checks origin against allowed origins. In production, `staticServerInstance.url` is `http://127.0.0.1:RANDOM_PORT`, which is added correctly. However, if `staticServerInstance` fails to set, `allowedOrigins` only includes `devServerUrl`, meaning production IPC calls would be rejected — a silent failure.

**Recommendation:** Add explicit error logging when IPC validation fails in production.

---

### 🟢 LOW — Electron window close bypasses sandbox for destroy
**File:** `client/electron/main.cjs:317-323`

`win.destroy()` is called directly on `window-close-confirmed`. If an attacker could send this IPC message, they could force-kill the app. The `validateIpcSender` check mitigates this, but there's no rate limiting on IPC calls.

**Recommendation:** Add rate limiting to IPC handlers.

## 2. Bugs / Logic Issues

### 🔴 HIGH — Dual state management causing sync inconsistencies
**File:** `client/src/App.tsx`

App.tsx maintains **two parallel state systems** for room state:
1. Local `useState` hooks (50+ state variables, lines 30-65)
2. `RoomStateContext` via `useRoomStateContext()` (lines 79-98)

Both `selectedMediaIndex` (local state at line 44, context state at line 83) and `selectedMediaFile` (line 47 vs 84) and several others are duplicated. This causes:
- Stale reads when one is updated but the other isn't
- Race conditions in `loadTorrentRequest` which reads from both
- Confusing data flow — some functions use local state, others use context

**Recommendation:** Consolidate to a single state management approach. The `RoomStateContext` with `useReducer` is the cleaner pattern — migrate all state there.

---

### 🔴 HIGH — Electron backend cached after first check
**File:** `client/src/services/TorrentService.ts:875-878`

`getElectronBackend()` reads `window.torrsyncElectronTorrent` fresh each time (good), but once it returns non-null, `addWebTorrentSource` and other methods are called. However, the `client` field in `TorrentService` can be set by a prior `getClient()` call (WebTorrent browser), and then `addElectronTorrentSource` is called which may conflict. There's no guard against mixing browser/Electron backends within the same service instance.

**Recommendation:** Add a backend type flag set on first backend resolution and throw if mixed usage is detected.

---

### 🟡 MEDIUM — `disconnect()` doesn't reset `state` to `"destroyed"` after emitting `"disconnected"`
**File:** `client/src/services/P2PService.ts:846-868`

After calling `disconnect()`, `state` is `"disconnecting"` and then `"disconnected"` is emitted, but `state` is never actually set to `"disconnected"`. It remains `"disconnecting"`, which means `isInRoom()` still returns true (`this.state !== "disconnected"` check fails because it's `"disconnecting"`).

**Recommendation:** Add `this.state = "disconnected"` before emitting the disconnected event.

---

### 🟡 MEDIUM — `bindConnection` early return leaks resources on disconnecting state
**File:** `client/src/services/P2PService.ts:606-607,614-615`

When `this.state === "disconnecting"`, the `wasAlreadyOpen` path returns early but still adds the connection to `this.connections` map and sets up cleanups. The early return at line 615 prevents emit but the connection is already tracked.

**Recommendation:** Move the disconnecting check before `this.connections.set(peerId, conn)`.

---

### 🟡 MEDIUM — Reconnect double-call risk: `peer.reconnect()` + `this.connect()` overlap
**File:** `client/src/services/P2PService.ts:553-558`

In `attemptReconnect`, `this.peer.reconnect()` is called (which re-establishes signaling server connection) AND `this.connect(this.remotePeerId)` is called (which creates a new data connection). If `peer.reconnect()` triggers the `"open"` event on existing connections → `"connected"` event fires → then `connect()` creates a SECOND connection to the same peer.

**Recommendation:** Only call `peer.reconnect()` if `this.peer.destroyed` is true; otherwise just call `connect()`.

---

### 🟡 MEDIUM — `SyncService` heartbeat doesn't suppress duplicate `state` events after dedup send
**File:** `client/src/services/SyncService.ts:227-247`

The heartbeat deduplication at line 240 skips sending if state hasn't changed, but the `lastHeartbeatPosition` and `lastHeartbeatPlaying` are only updated when a message IS sent. If the first heartbeat sends, then the video position doesn't change for 10 heartbeats, then changes by 0.6s — it sends again. This is correct. However, the suppress flags (`suppressNextEventSync`) are reset in the event handlers (lines 197-198, 204-205, 211-213), but if `play()` is called and the `play` event fires BEFORE the `await video.play()` line, the suppress flag is already consumed by the explicit call. The `play().catch()` at line 101 resets the flag, but the `pause` call at line 109 does NOT have this protection — if `pause()` is called and `video.pause()` throws (unlikely but possible), the suppress flag stays set indefinitely.

**Recommendation:** Add try/catch wrappers around `video.play()` and `video.pause()` to always reset suppress flags.

---

### 🟢 LOW — `safeParseInt` missing for buffer settings inputs
**File:** `client/src/components/VideoPlayer.tsx:445,449`

The buffer settings inputs use `Number(e.target.value) || 50` and `Math.max/Math.min` clamping. This works, but `Number("")` returns `0`, which triggers the fallback to 50/500. If a user clears the input and clicks Apply, it silently resets to defaults without feedback.

**Recommendation:** Add visual feedback for clamped/invalid values.

---

### 🟢 LOW — `MAX_TORRENT_FILE_BYTES` duplicated between client and Electron main
**Files:** `client/src/config.ts:28-29`, `client/electron/main.cjs:261`

Both define `10 * 1024 * 1024` independently. If one changes, the other may not.

**Recommendation:** If sharing config is hard, at least add a comment referencing the other location.

## 3. Code Quality / Technical Debt

### 🟡 MEDIUM — `P2PService` and `TorrentService` are both ~870-1040 lines
Each handles multiple responsibilities (connection management, message parsing, rate limiting, ping/pong, event routing, state machine). They're borderline too large.

**Recommendation:** Extract message parsing/validation into a separate module. Extract state machine logic.

---

### 🟡 MEDIUM — `parseInboundMessage` uses exhaustive switch with JSON.parse fallback
**File:** `client/src/services/P2PService.ts:140-214`

The message parsing first tries `JSON.parse` if the input is a string, then manually validates each field. This is good defensive code, but the validation is incomplete:
- No maximum length check on `sourceKey` or `magnetLink`
- No validation that `sourceKey` matches a safe pattern
- `bytes` array elements are checked for 0-255 range but not for array prototype pollution

**Recommendation:** Add max length limits. Use a schema validation library like `zod` for inbound messages.

---

### 🟡 MEDIUM — Electron modules loaded via string path concatenation
**File:** `client/electron/torrent-bridge.cjs:4-5`

```js
const MemoryChunkStore = require(path.join(__dirname, "..", "node_modules", "memory-chunk-store"));
const { BoundedChunkStore } = require(path.join(__dirname, "bounded-chunk-store.cjs"));
```

Fragile — breaks if `node_modules` is hoisted or if the Electron app is packaged.

**Recommendation:** Use normal `require("memory-chunk-store")` and let the module resolution work. For `bounded-chunk-store.cjs`, rename to `.js` or use a proper build step.

---

### 🟢 LOW — CSS inline styles in JSX
**Files:** `ErrorBoundary.tsx:39-55`, `ConfirmModal.tsx:95`

Several React components use `style={{...}}` inline styles instead of CSS classes, despite having CSS files available. Inconsistent with the rest of the app.

**Recommendation:** Move inline styles to CSS classes.

---

### 🟢 LOW — `webtorrent-sw.js` has outdated structure
**File:** `client/public/webtorrent-sw.js`

The ServiceWorker code is verbose and was likely adapted from WebTorrent examples. It has:
- Manual client filtering that could use `clients.matchAll` more efficiently
- No error handling for `client.postMessage` failures
- A 5-second timeout (`postMessageTimeout`) that could be too aggressive on slow machines

**Recommendation:** Refactor with proper error handling and configurable timeouts.

---

### 🟢 LOW — `bittorrent-dht.ts` shim is a no-op
**File:** `client/src/shims/bittorrent-dht.ts`

```ts
export const Client = {};
```

This shim is meant to disable DHT, but it exports an empty object rather than `false` or `undefined`. The check in torrent-discovery is `typeof DHT !== "function"` — and `typeof {}` is `"object"`, which means the check passes and DHT is NOT disabled.

**Recommendation:** Verify this actually works as intended. May need to re-export differently.

---

### 🟢 LOW — Dead code: unused `syncLogger`
**File:** `client/src/utils/logger.ts:79`

`syncLogger` is created but never imported anywhere in the codebase. No other file imports it.

**Recommendation:** Remove it to reduce bundle size.

## 4. Test Coverage Gaps

### 🔴 HIGH — No integration/E2E tests
Per `QA_SMOKE_PLAN.md:25-27`: no component tests for `RoomPage`, no integration tests for host-guest pairing. The smoke plan explicitly notes this gap.

**Impact:** The core feature (synchronized playback) is entirely untested between components.

**Recommendation:** Add at minimum:
1. A RoomPage render + interaction test
2. An App.tsx integration test verifying room creation → torrent load flow
3. A Playwright or similar E2E test for the full host-guest scenario

---

### 🟡 MEDIUM — P2PService tests are mock-heavy, test implementation details
**Files:** `P2PService.connection.test.ts`

The tests mock the entire `peerjs` module with a hand-rolled mock. This tests that `P2PService` calls the right PeerJS methods, but doesn't test behavior under real-world conditions (connection timeouts, message ordering, reconnection).

**Recommendation:** Add a few tests that exercise error paths with deliberate message corruption.

---

### 🟡 MEDIUM — TorrentService tests reach into private state via `as unknown as {}`
`TorrentService.test.ts:121-123`, `TorrentService.test.ts:452`:

```ts
(service as unknown as { activeTorrent: ... }).activeTorrent = torrent;
(service as unknown as { enforceBufferLimit: () => void }).enforceBufferLimit();
```

These cast to `unknown` then to an anonymous type to access private members. This is fragile.

**Recommendation:** Either expose package-private methods with `@internal` JSDoc, or test through public API only.

---

### 🟢 LOW — ConfirmModal.test.tsx uses `getByRole("alertdialog")` but uses `<dialog>` without proper `role`
**File:** `ConfirmModal.tsx:103`

The modal uses `<dialog>` with `role="alertdialog"` on the inner `div`, not on the `<dialog>` element itself. The `<dialog>` element has an implicit `role="dialog"`. The test for `role="alertdialog"` should target the inner div.

**Recommendation:** Add `aria-modal="true"` to the `<dialog>` element itself per WAI-ARIA best practices.
