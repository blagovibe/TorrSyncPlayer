# Полный аудит проекта TorrSyncPlayer

## Обзор проекта

TorrSyncPlayer — настольное приложение для синхронного просмотра видео из торрентов. Архитектура: React 18 + TypeScript + Vite (renderer), Electron 42 (main process), PeerJS (сигнализация), WebTorrent (стриминг), WebRTC Data Channels (P2P синхронизация).

Исследовано ~80 файлов, включая все исходные коды, тесты, конфигурации, CI/CD и документацию.

## CRITICAL (критические баги, требующие немедленного исправления)

### C-1: `useRoomState` хук не используется, но создаёт зомби-refs
- **Где:** `client/src/hooks/useRoomState.ts` экспортируется из `hooks/index.ts`, но ни один компонент его не импортирует. В `App.tsx` состояние управляется напрямую через `useState` + `useRef`. Хук создаёт `useRef` объекты, которые никогда не инициализируются — технический долг, вводящий в заблуждение при чтении кода.
- **Рекомендация:** Выбрать одну модель управления состоянием — либо refs (useRoomState), либо useState + Context. Удалить неиспользуемый хук или мигрировать на него.

### C-2: Неполная очистка P2PService — `syncMessageTimestamps` не очищается при disconnect
- **Где:** `client/src/services/P2PService.ts:758` — `clearRateLimitForPeer()` удаляет только для конкретного peerId, а `disconnect()` (строки 828-846) не вызывает `clearRateLimitForPeer` для всех пиров и не очищает `syncMessageTimestamps`. При повторном соединении с тем же peer, старые временные метки влияют на rate limiting.
- **Рекомендация:** Добавить `this.syncMessageTimestamps.clear()` в метод `disconnect()`.

### C-3: `processTorrentLoadQueue` может запуститься рекурсивно без ограничений
- **Где:** `client/src/App.tsx:393` — в блоке `finally` вызывается `void processTorrentLoadQueueRef.current()` при наличии `pendingTorrentLoadRef.current`. Если очередь всегда непуста (например, из-за бага), это приведёт к бесконечной рекурсии в event loop без backpressure.
- **Рекомендация:** Добавить `setTimeout(() => processTorrentLoadQueueRef.current(), 0)` или аналогичную асинхронную разрывную связь вместо прямого вызова.

### C-4: Electron `validateIpcSender` пропускает все origin с портом 127.0.0.1
- **Где:** `client/electron/main.cjs:207-215` — проверка `parsed.protocol === "http:" && parsed.hostname === "127.0.0.1"` не валидирует порт. Природный риск: любое локальное приложение, поднятое на 127.0.0.1:PORT, может отправлять IPC сообщения. Также `localhost` принимается без проверки порта.
- **Рекомендация:** Ограничить до конкретного origin статического сервера (`http://127.0.0.1:<bound_port>`) или использовать токен в header.

### C-5: CSP разрешает `media-src 'self' blob: http://127.0.0.1` без ограничения порта
- **Где:** `client/index.html:5` и `client/electron/main.cjs:130` — `http://127.0.0.1` без порта и `connect-src` без порта. Это позволяет любому локальному серверу подключиться как media source.
- **Рекомендация:** В Electron-режиме убрать `http://127.0.0.1` из CSP, так как ресурсы загружаются через локальный сервер с известным origin (dynamic port).

### C-6: `sendTorrentSource` без валидации размера `bytes` массива
- **Где:** `client/src/services/P2PService.ts:792-803` и `client/src/App.tsx:173` — при broadcast torrent source содержимое `SharedTorrentSource.bytes` (весь .torrent файл) отправляется через WebRTC DataChannel без проверки размера. PeerJS DataChannel имеет лимит ~64KB на сообщение (при отсутствии chunking), при превышении соединение обрывается.
- **Рекомендация:** Ограничить размер `bytes` перед отправкой (например, 50KB), добавить wire protocol для chunked transfer.

### C-7: `destroy()` в `before-quit` может вызвать `forceExit` → `app.exit(0)` → повторный `before-quit`
- **Где:** `client/electron/main.cjs:331-373` — при быстром `app.exit(0)` окна уничтожаются, что может триггерить дополнительные quit events. `hasExited` предотвращает повторный exit, но `forceExit` одновременно вызывает `win.destroy()` для всех окон (что может быть veto-able если у них есть `close` handler с `event.preventDefault()`).
- **Рекомендация:** Убрать `event.preventDefault()` из `before-quit`, либо добавить однократный флаг для всех quit handlers.

## HIGH (серьёзные проблемы)

### H-1: `RoomStateContext` содержит дублирующее состояние по сравнению с `App.tsx` useState
- **Где:** `App.tsx` имеет ~25 `useState` хуков + `RoomStateContext` с `useReducer`. Состояние размазано между двумя системами. Например, `selectedMediaFile` хранится и в `selectedMediaFileState` (useState), и в контексте. Рассинхронизация приводит к багам, которые сложно отследить.
- **Рекомендация:** Консолидировать всё состояние room в одном месте (RoomStateContext) или полностью перейти на useState без контекста. Рекомендуется контекст + useReducer для читаемости.

### H-2: `trackerLost` использует устаревший ref при peerCount > 0
- **Где:** `client/src/App.tsx:800-804` — `trackerLostRef.current` проверяется в обработчике `peerCount`, но `trackerLost` state устанавливается на основе предыдущего состояния (async state update). Возможно состояние гонки: при быстром изменении peerCount с 0 → 1 → 0, `trackerLost` может не сброситься.
- **Рекомендация:** Использовать `setTrackerLost(prev => peerCount === 0 ? prev : false)` или `setTrackerLost(false)` напрямую.

### H-3: `scheduleBroadcast` (debounce) теряет последний broadcast при быстром отключении
- **Где:** `client/src/App.tsx:188-194` — `broadcastTimeoutRef.current` очищается в `clearBroadcastTimeout()`, которая вызывается только в `handleLeaveRoom`. Если peer отключится во время debounce-таймера, текущее состояние не будет отправлено.
- **Рекомендация:** Сделать flush при disconnect пира: `clearBroadcastTimeout(); broadcastCurrentRoomState(targetPeerId)`.

### H-4: MemoryChunkStore в Electron не учитывает WebTorrent 2.x API
- **Где:** `client/electron/torrent-bridge.cjs:381` — `BoundedChunkStore` передаётся как `store` option в `client.add()`. WebTorrent 2.x изменил API для custom stores, используя `store` через классическую цепочку прототипов. Проверка совместимости не проведена.
- **Рекомендация:** Проверить работу `BoundedChunkStore` с WebTorrent 2.6 и адапtapть при необходимости.

### H-5: `handleFfmpegQueue` имеет race condition
- **Где:** `client/electron/torrent-bridge.cjs:33-58` — `ffmpegQueue` содержит `task` и `reject`, но `next()` вызывается в `task()` и в catch-block. Если `next.task()` бросит исключение до `resolve`, `reject` может быть вызван или нет. При одновременном `reject` в queue и `resolve` в task промис может остаться pending forever.
- **Рекомендация:** Обернуть очередь в класс с правильным settled-state tracking.

### H-6: `parseInboundMessage` не валидирует размер `bytes` в torrent source
- **Где:** `client/src/services/P2PService.ts:178-181` — проверяется что `src.bytes` это массив чисел 0-255, но не проверяется длина массива. Злоумышленный peer может отправить массив из миллионов элементов и завесить main thread.
- **Рекомендация:** Добавить проверку `src.bytes.length <= MAX_TORRENT_BYTES` (где MAX_TORRENT_BYTES = 10MB).

### H-7: `playMediaFile` мержит асинхронные вызовы `play()` без координации
- **Где:** `client/src/App.tsx:248-258` — `mediaElement.play()` вызывается напрямую, а SyncService.master слушает `play` event и отправляет sync. Если `play()` вызван, но элемент быстро поставлен на pause до срабатывания event handler, sync сообщение может содержать неверное состояние.
- **Рекомендация:** Добавить AbortController или флаг для отмены autoplay error handling при быстром переключении файлов.

### H-8: SyncService читает `Date.now()` для latency compensation, но не учитывает clock drift
- **Где:** `client/src/services/SyncService.ts:138` — latency compensation = `(Date.now() - message.server_ts) / 1000`. Если часы host и guest рассинхронизированы (NTP drift), compensation содержит постоянное смещение.
- **Рекомендация:** Для MVP допустимо, но стоит добавить warning при latency > SYNC_CONFIG.maxLatencyCompensationSeconds.

## MEDIUM (проблемы средней серьёзности)

### M-1: `MAGNET_LINK_PATTERN` слишком строгий для реальных magnet-ссылок
- **Где:** `client/src/utils/torrent.ts:3` — `/^magnet:\?xt=urn:[a-z0-9]+:[a-z0-9]{32,40}(&.+)?$/i`. Не покрывает: верхний регистр в xt, `urn:btmh` (multihash), длинные hash, различные кодировки.
- **Рекомендация:** Использовать менее строгий regex: `/^magnet:\?xt=urn:[a-z0-9]+:[a-zA-Z0-9]+/`.

### M-2: `SyncService.applyRemoteSync` не проверяет границы `compensatedPosition`
- **Где:** `client/src/services/SyncService.ts:147` — после компенсации latency, `compensatedPosition` может быть отрицательным (если `server_ts > Date.now()` из clock drift) или больше длительности видео. Установка отрицательного `currentTime` вызовет DOMException в некоторых браузерах.
- **Рекомендация:** `Math.max(0, Math.min(compensatedPosition, this.video.duration || Infinity))`.

### M-3: `TorrentService.addWebTorrentSource` — `peer` event listener может вызвать утечку памяти
- **Где:** `client/src/services/TorrentService.ts:389-395` — `onPeer` callback добавляется через `this.cleanup.on()` каждый раз при `addWebTorrentSource`, но `discoveredPeerIds` не очищается между вызовами (очищается только в `clearActiveTorrentForAdd`). При повторном вызове без `clearActiveTorrentForAdd`, старые peer IDs остаются.
- **Рекомендация:** Переместить `discoveredPeerIds.clear()` в начало `addWebTorrentSource`.

### M-4: `P2PService.bindConnection` — `wasAlreadyOpen` проверяется один раз
- **Где:** `client/src/services/P2PService.ts:608-626` — если `conn.open === true` при вызове `bindConnection`, `onOpen` и `startPingInterval` вызываются синхронно. Но если соединение закроется сразу после этого (race condition), `startPingInterval` уже вызван, а ping будет отправляться в закрытое соединение.
- **Рекомендация:** Добавить проверку `connection.open` в `sendPing()` перед отправкой.

### M-5: `ConfirmModal` — `previousFocusRef` не очищается при закрытии
- **Где:** `client/src/components/ConfirmModal.tsx:31-46` — `previousFocusRef.current` сохраняется при открытии, но при закрытии через `onCancel` фокус возвращается на старый элемент. Если старый элемент был удалён из DOM (например, компонент размонтирован), фокус теряется.
- **Рекомендация:** Добавить проверку `document.contains(previousFocusRef.current)` перед `focus()`.

### M-6: `ErrorBoundary.handleReset` не сбрасывает состояние приложения
- **Где:** `client/src/components/ErrorBoundary.tsx:25-27` — после reset рендерится тот же `<App />`, но все сервисы (P2PService, TorrentService) остаются в неопределённом состоянии. Пользователь видит UI, но все соединения мертвы.
- **Рекомендация:** При reset вызывать `window.location.reload()` вместо или в дополнение к setState.

### M-7: `App.tsx` — обработчик `torrent_source` не проверяет что текущий torrent загружен
- **Где:** `client/src/App.tsx:462-478` — при получении `torrent_source` от host, guest вызывает `requestTorrentLoad` с `autoplay: true`. Если guest уже загрузил этот torrent (по sourceKey), но медиа-файл ещё не выбран, запрос будет проигнорирован (строки 293-319), но `pendingRemoteSync` уже очищен (строка 468).
- **Рекомендация:** Не очищать `pendingRemoteSync` до успешного завершения `requestTorrentLoad`.

### M-8: `TorrentService` — `streamFromUrl` не обрабатывает `AbortController` при смене URL
- **Где:** `client/src/services/TorrentService.ts:551-615` — `AbortController` создаётся для каждого вызова, но при повторном вызове `streamToMedia` с новым URL, предыдущий AbortController не связан с новым. События от старого видео элемента могут сработать после смены src.
- **Рекомендация:** Хранить `AbortController` как поле класса и вызывать `abort()` в начале `streamToMedia`.

### M-9: `electron/main.cjs` — `staticServerInstance` не обрабатывает ошибки сервера
- **Где:** `client/electron/main.cjs:80-163` — `server.on("error", reject)` вызывается только при старте. Если сервер упадёт после старта (например, port conflict), ошибка не обрабатывается.
- **Рекомендация:** Добавить `server.on("error", (err) => console.error(...))` после успешного старта.

### M-10: `prepare-electron-app.cjs` — не копирует `node_modules` для native модулей
- **Где:** `client/scripts/prepare-electron-app.cjs:17-21` — копируются только `dist/`, `electron/`, `package-lock.json`. Native модули (например, `memory-chunk-store`) должны быть пересобраны через `npm ci`, но `npmRebuild: false` в electron-builder конфигурации запрещает rebuild.
- **Рекомендация:** Установить `npmRebuild: true` или убедиться что все native модули совместимы с target Electron version без rebuild.
