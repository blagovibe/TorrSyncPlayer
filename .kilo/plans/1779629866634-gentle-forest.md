# TorrSyncPlayer — Full Project Audit Report

## Project Overview

**TorrSyncPlayer** is a desktop application (Electron + React + TypeScript) for streaming video via WebTorrent with real-time synchronization between multiple clients. One host controls playback; guests follow in sync.

**Tech Stack**: React 18, TypeScript, Vite 5, Electron 42, PeerJS 1.5, WebTorrent 2.6, Vitest 2.1, ESLint 9

## 1. SECURITY VULNERABILITIES (CRITICAL)

### 1.1 HIGH: `ip` package SSRF vulnerability
- **Severity**: HIGH
- **Location**: Transitive dependency via `webtorrent` → `torrent-discovery` → `bittorrent-tracker` → `ip`
- **Issue**: `ip` package has improper categorization in `isPublic` function, enabling SSRF attacks
- **Fix**: Upgrade `webtorrent` to a version that doesn't depend on vulnerable `ip`, or wait for upstream fix. No clean `npm audit fix` available without breaking changes.

### 1.2 HIGH: `elliptic` cryptographic primitive risk
- **Severity**: HIGH
- **Location**: `crypto-browserify` → `browserify-sign`/`create-ecdh` → `elliptic`
- **Issue**: Uses a cryptographic primitive with risky implementation
- **Fix**: `crypto-browserify` is a polyfill for WebTorrent browser mode. In Electron builds, this is unnecessary. Consider removing `crypto-browserify` from Electron builds or accepting the risk (polyfill is only used in browser context).

### 1.3 MODERATE: `esbuild` dev server request proxying
- **Severity**: MODERATE
- **Location**: `vite` → `esbuild`
- **Issue**: esbuild dev server allows any website to send requests and read responses
- **Fix**: This is a dev-only vulnerability. Ensure `vite dev` is never exposed to untrusted networks. Upgrade Vite when possible.

### 1.4 MODERATE: `ws` uninitialized memory disclosure
- **Severity**: MODERATE
- **Location**: `ws` package (used by WebTorrent/WebSocket trackers)
- **Issue**: Versions 8.0.0–8.20.0 disclose uninitialized memory
- **Fix**: Run `npm audit fix` (non-breaking) to update `ws`.

### 1.5 CSP in `index.html` is redundant with server header
- **Severity**: LOW
- **Location**: `client/index.html:6` and `client/electron/main.cjs:130`
- **Issue**: CSP is set both in `<meta>` tag and HTTP header. The meta tag is ignored when the header is present, creating confusion about which policy is active.
- **Fix**: Remove CSP from `<meta>` tag; keep only the HTTP header in `main.cjs`.

## 2. BUGS (HIGH)

### 2.1 Race condition in `P2PService.attemptReconnect()`
- **Severity**: HIGH
- **Location**: `client/src/services/P2PService.ts:526-562`
- **Issue**: Recursive `attemptReconnect()` call at line 559 can lead to unbounded reconnection attempts if `this.peer.reconnect()` succeeds but `this.connect()` keeps failing. The `reconnectAttempts` counter is only reset on full success, but `peer.reconnect()` may succeed independently.
- **Fix**: Add a guard to prevent recursive calls when already reconnecting, and ensure `reconnectAttempts` is properly tracked.

### 2.2 `P2PService.initialize()` doesn't reset `peerId` for guests
- **Severity**: MEDIUM
- **Location**: `client/src/services/P2PService.ts:464-478`
- **Issue**: When `role === "guest"`, the PeerJS ID is generated by the server, but the constructor already generated a random `peerId` at line 284. The guest's `peerId` is overwritten with the server-assigned ID, but this ID is never used for display — the host's prefix-based ID is what's shown.
- **Fix**: Clarify the peer ID generation flow for guests vs hosts.

### 2.3 `SyncService` heartbeat can fire after `dispose()`
- **Severity**: MEDIUM
- **Location**: `client/src/services/SyncService.ts:224-243`
- **Issue**: The heartbeat `setInterval` is registered via `this.cleanup`, but `isDisposed` check happens at the start of the callback. If `dispose()` is called between interval ticks, the callback still fires once before cleanup aborts it.
- **Fix**: The cleanup pattern handles this via `AbortSignal`, but the `isDisposed` flag is redundant and potentially misleading. Remove `isDisposed` and rely solely on the cleanup signal.

### 2.4 `TorrentService.addTorrentSource` queue can deadlock
- **Severity**: MEDIUM
- **Location**: `client/src/services/TorrentService.ts:311-333`
- **Issue**: If `clearActiveTorrentForAdd()` throws, `releaseQueue` is never called, permanently blocking all future torrent loads.
- **Fix**: Wrap in try/finally to ensure `releaseQueue` is always called.

### 2.5 `VideoPlayer` keyboard shortcuts persist after unmount
- **Severity**: MEDIUM
- **Location**: `client/src/components/VideoPlayer.tsx:266-285`
- **Issue**: The `keydown` event listener on `window` is removed on unmount, but if `canControlPlayback` changes while the listener is active, stale closures may cause incorrect behavior.
- **Fix**: Use refs for all callback dependencies in the keyboard handler.

## 3. TECHNICAL DEBT (MEDIUM)

### 3.1 Excessive `useCallback` dependency warnings
- **Severity**: MEDIUM
- **Location**: `client/src/App.tsx` (8 warnings)
- **Issue**: Multiple `useCallback` hooks have intentionally omitted dependencies (using `eslint-disable` comments). This is a known pattern for refs but makes the code fragile.
- **Fix**: Either include all dependencies and memoize properly, or refactor to use a stable pattern (e.g., custom hook for broadcast functions).

### 3.2 `App.tsx` is 1162 lines — too large
- **Severity**: MEDIUM
- **Location**: `client/src/App.tsx`
- **Issue**: The main App component handles P2P initialization, torrent loading, sync, room state, chat, and UI state. This is a significant maintainability burden.
- **Fix**: Extract into smaller hooks and components:
  - `useP2PConnection()` — P2P service lifecycle
  - `useTorrentLoader()` — torrent loading queue
  - `useRoomSync()` — sync service management
  - `useChat()` — chat state and sending

### 3.3 `TorrentService` is 1004 lines — too large
- **Severity**: MEDIUM
- **Location**: `client/src/services/TorrentService.ts`
- **Issue**: Handles both WebTorrent and Electron backends, streaming, buffering, and file management.
- **Fix**: Split into `WebTorrentBackend`, `ElectronBackend`, and `TorrentService` (coordinator).

### 3.4 `P2PService` is 823 lines — too large
- **Severity**: MEDIUM
- **Location**: `client/src/services/P2PService.ts`
- **Issue**: Handles connection management, message parsing, ping/pong, reconnection, and chat forwarding.
- **Fix**: Extract message parsing into a separate module, connection management into a connection pool class.

### 3.5 `torrent-bridge.cjs` is 998 lines — too large
- **Severity**: MEDIUM
- **Location**: `client/electron/torrent-bridge.cjs`
- **Issue**: Handles torrent management, ffmpeg probing, audio/subtitle streaming, and HTTP serving.
- **Fix**: Split into separate modules for torrent management, ffmpeg operations, and HTTP serving.

### 3.6 No error recovery for failed ffmpeg streams
- **Severity**: MEDIUM
- **Location**: `client/electron/torrent-bridge.cjs:689-864`
- **Issue**: If ffmpeg crashes mid-stream, the HTTP response is destroyed but no retry or graceful recovery is attempted.
- **Fix**: Implement retry logic for transient ffmpeg failures.

### 3.7 `roomPassword` is transmitted in plaintext
- **Severity**: MEDIUM
- **Location**: `client/src/services/P2PService.ts:783-791`
- **Issue**: Room password is sent over WebRTC data channel without encryption (PeerJS data channels are DTLS-encrypted, but the password is still visible in the application layer).
- **Fix**: This is acceptable for the current threat model (DTLS encryption in transit), but document this limitation.

### 3.8 No input validation on magnet link format
- **Severity**: LOW
- **Location**: `client/src/utils/torrent.ts:12-19`
- **Issue**: `createMagnetSource` only trims whitespace but doesn't validate magnet link format.
- **Fix**: Add regex validation for magnet link format.

## 4. CODE QUALITY ISSUES (LOW)

### 4.1 Unused imports
- **Location**: `client/src/components/VideoPlayer.tsx:109` — `_onMuxStreamRequest` is destructured but never used
- **Fix**: Remove or use the parameter.

### 4.2 Inconsistent error handling patterns
- **Location**: Throughout codebase
- **Issue**: Some functions use `try/catch`, others use `.catch()`, and some use the Result pattern. Inconsistent.
- **Fix**: Standardize on one pattern (preferably Result<T,E> as mentioned in SPEC).

### 4.3 `console.error` in production code
- **Location**: `client/src/App.tsx:445`, `client/src/components/HomePage.tsx:195`
- **Issue**: Direct `console.error` calls bypass the logging system.
- **Fix**: Use the structured logger (`uiLogger`, `p2pLogger`, etc.).

### 4.4 `any` types in electron-api.d.ts
- **Location**: `client/src/types/electron-api.d.ts:21` — `on?: (event: string, callback: (...args: unknown[]) => void) => void`
- **Issue**: Using `unknown[]` is better than `any` but still not type-safe.
- **Fix**: Define proper event type maps for torrent events.

### 4.5 Missing JSDoc on public APIs
- **Location**: All service classes
- **Issue**: Public methods lack documentation.
- **Fix**: Add JSDoc to all public methods.

### 4.6 `ConfirmModal` renders `<dialog>` even when closed
- **Location**: `client/src/components/ConfirmModal.tsx:56`
- **Issue**: Returns `null` when `!isOpen`, but the `useEffect` tries to access `dialogRef.current` which may be null.
- **Fix**: Guard the effect with `if (!isOpen) return`.

### 4.7 `RoomInfo` uses inline styles
- **Location**: `client/src/components/RoomInfo.tsx:70-104`
- **Issue**: Mixing CSS classes and inline styles reduces maintainability.
- **Fix**: Move all styles to CSS files.

### 4.8 No test coverage for `RoomPage` or `VideoPlayer` components
- **Location**: `client/src/components/__tests__/`
- **Issue**: Only `HomePage`, `ConfirmModal`, and `VideoPlayer` have tests. `RoomPage` (the main screen) has none.
- **Fix**: Add integration tests for `RoomPage`.

### 4.9 `ErrorBoundary` doesn't log to the structured logger
- **Location**: `client/src/components/ErrorBoundary.tsx:21`
- **Issue**: Uses `console.error` instead of the structured logging system.
- **Fix**: Integrate with the logger.

## 5. ARCHITECTURE CONCERNS (MEDIUM)

### 5.1 No state management library
- **Issue**: The SPEC mentions "Custom Zustand-like store" but the app uses raw `useState`/`useRef` in `App.tsx`. This leads to prop drilling and complex state synchronization.
- **Fix**: Either adopt Zustand or implement the documented custom store.

### 5.2 Dual backend complexity (WebTorrent vs Electron)
- **Issue**: `TorrentService` supports both browser WebTorrent and Electron native backend, with runtime detection. This doubles the testing surface and creates subtle behavioral differences.
- **Fix**: Since the app is Electron-only, consider removing the browser WebTorrent backend entirely.

### 5.3 No graceful degradation for missing ffmpeg
- **Location**: `client/electron/torrent-bridge.cjs:60-72`
- **Issue**: If ffmpeg is not available, audio track probing and mux streaming silently fail.
- **Fix**: Show a user-facing notification when ffmpeg is unavailable.

### 5.4 Service Worker dependency for WebTorrent streaming
- **Location**: `client/src/services/TorrentService.ts:921-950`
- **Issue**: The WebTorrent streaming path requires a Service Worker, which may not be available in all contexts.
- **Fix**: Since Electron is the primary target, rely on the Electron backend and remove the Service Worker path.

### 5.5 No rate limiting on torrent file uploads
- **Location**: `client/src/App.tsx:284-309`
- **Issue**: The 10MB limit is checked, but there's no rate limiting on repeated uploads.
- **Fix**: Add debouncing or rate limiting on torrent load requests.

## 6. DEPENDENCY CONCERNS (MEDIUM)

### 6.1 Outdated Vite version
- **Current**: Vite 5.4.10
- **Latest**: Vite 6.x
- **Issue**: Vite 5 uses esbuild with known vulnerabilities
- **Fix**: Upgrade to Vite 6 (requires testing for breaking changes)

### 6.2 Outdated Electron version
- **Current**: Electron 42.0.1
- **Latest**: Electron 35.x (stable)
- **Issue**: Electron 42 may be a pre-release or typo; verify version
- **Fix**: Pin to a stable release

### 6.3 `crypto-browserify` is unnecessary in Electron
- **Issue**: `crypto-browserify` is a Node.js crypto polyfill for browsers. In Electron, `crypto` is available natively.
- **Fix**: Remove from Electron builds to reduce bundle size and eliminate `elliptic` vulnerability.

### 6.4 `buffer`, `process`, `util`, `stream-browserify` polyfills
- **Issue**: These are all Node.js polyfills for browser context. In Electron, they're unnecessary.
- **Fix**: Remove from Electron builds.
