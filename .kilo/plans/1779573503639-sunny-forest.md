# TorrSyncPlayer — Full Project Audit Plan

## Scope
Complete audit of the TorrSyncPlayer project: code quality, architecture, dependencies, tests, CI/CD, security, and processes.

---

## Issues Found

### 🔴 CRITICAL (Fix Immediately)

#### C1. `noUnusedLocals` / `noUnusedParameters` disabled in root tsconfig.json
- **File**: `tsconfig.json:15-16`
- **Issue**: Root tsconfig has `noUnusedLocals` and `noUnusedParameters` but the file only includes `"include": ["src"]` — yet there is no `src/` at root. This tsconfig is effectively dead code and confusing. The real config is in `client/tsconfig.json`.
- **Impact**: Misleading configuration; developers may think root-level type checking covers the project.
- **Fix**: Remove root `tsconfig.json` or make it a proper project reference. The root `package.json` already delegates everything to `client/`.

#### C2. Electron main.cjs uses `require()` for ESM-only `webtorrent` in torrent-bridge
- **File**: `client/electron/torrent-bridge.cjs:542`
- **Issue**: `import("webtorrent")` is dynamic, but `webtorrent` v2.6 is ESM-only. The `memory-chunk-store` is loaded via `require()` from `node_modules` path. If `memory-chunk-store` also goes ESM-only, this breaks.
- **Impact**: Potential runtime crash on fresh installs if module resolution changes.
- **Fix**: Add explicit `.mjs` wrapper or document the CJS/ESM interop requirement. Test with `npm ci` in clean environment.

#### C3. `BoundedChunkStore` doesn't call `cb` on successful `put`
- **File**: `client/electron/bounded-chunk-store.cjs:53`
- **Issue**: `this.baseStore.put(index, buf, cb)` is called, but if `cb` is `undefined` (not passed by caller), this can throw. WebTorrent's internal store always passes a callback, but the defensive pattern is missing.
- **Impact**: Potential unhandled exception if store API changes.
- **Fix**: Guard: `if (cb) this.baseStore.put(index, buf, cb); else this.baseStore.put(index, buf);`

#### C4. `ffmpegQueue` length not decremented on error in `handleAudioRequest`
- **File**: `client/electron/torrent-bridge.cjs:762-776`
- **Issue**: When `activeFfmpegCount < MAX_CONCURRENT_FFMPEG`, the count is incremented and `spawnFfmpeg()` is called. But if `spawn()` throws synchronously, `activeFfmpegCount` is never decremented and the queue is never drained.
- **Impact**: Gradual resource leak; after enough errors, all ffmpeg requests queue forever.
- **Fix**: Wrap in try/catch/finally to always decrement and drain queue.

### 🟠 HIGH (Fix Soon)

#### H1. `TorrentService` uses `any` types despite ESLint `no-explicit-any: error`
- **File**: `client/src/services/TorrentService.ts:42,46`
- **Issue**: `// eslint-disable-next-line @typescript-eslint/no-explicit-any` is used twice. The ESLint config explicitly forbids `any`. This is a rule circumvention.
- **Impact**: Type safety holes in the torrent event system.
- **Fix**: Define proper event callback types. Replace `(...args: any[]) => void` with specific signatures.

#### H2. `P2PService` uses `any` via type assertion
- **File**: `client/src/services/P2PService.ts:407`
- **Issue**: `onWire as (...args: unknown[]) => void` — the `any` is hidden via `unknown` cast. The `wire` handler's `closeHandler` is a no-op `() => {}`.
- **Impact**: Dead code; the close handler does nothing.
- **Fix**: Remove the no-op handler or implement actual wire tracking.

#### H3. `App.tsx` is 1184 lines — monolithic component
- **File**: `client/src/App.tsx`
- **Issue**: Single component manages all state for P2P, sync, torrent, UI, chat, modals, and lifecycle. Contains 30+ state variables, 15+ refs, and complex interdependent effects.
- **Impact**: Extremely difficult to test, debug, and maintain. High risk of subtle bugs from stale closures and effect ordering.
- **Fix**: Extract custom hooks: `useP2PConnection()`, `useTorrentLoading()`, `useSyncService()`, `useRoomState()`. Split into smaller container components.

#### H4. `handlePong` doesn't validate RTT sanity
- **File**: `client/src/services/P2PService.ts:737-743`
- **Issue**: Only checks `rtt >= 0`. A malicious or buggy peer could send a `pong` with a future timestamp, causing negative RTT (silently dropped), or a very old timestamp causing huge RTT.
- **Impact**: Connection quality indicator can be manipulated; no upper bound on RTT.
- **Fix**: Add upper bound: `if (rtt >= 0 && rtt < 30000)`.

#### H5. No input sanitization on chat messages
- **File**: `client/src/components/RoomInfo.tsx:74`
- **Issue**: Chat messages are rendered directly via `{msg.text}` in JSX. While React escapes by default, there's no length limit on incoming messages, and no rate limiting.
- **Impact**: A malicious peer could send thousands of messages or extremely long messages, filling memory and DOM.
- **Fix**: Add max message length (e.g., 500 chars), max message count (e.g., 200), and rate limiting on the P2P service.

#### H6. `ConfirmModal` renders even when `isOpen=false` (returns null but dialog ref persists)
- **File**: `client/src/components/ConfirmModal.tsx:48`
- **Issue**: `if (!isOpen) return null;` — the component unmounts/remounts each time. This means the `<dialog>` element is recreated on every open, losing any native dialog state. The `useEffect` tries to manage this but the pattern is fragile.
- **Impact**: Potential for dialog to not show if state races occur.
- **Fix**: Always render the dialog element but control visibility via CSS or the `open` attribute.

#### H7. `webtorrent-sw.js` has broken client handling
- **File**: `client/public/webtorrent-sw.js:4-6`
- **Issue**: `clients.get(event.clientId).catch(() => null)` — `clients.get()` returns a Promise, but the result is never awaited (no `await`). The `if (!client)` check on the next line always evaluates to `true` because a Promise is truthy.
- **Impact**: The service worker's origin check is effectively broken; it may serve cross-origin requests.
- **Fix**: `const client = await clients.get(event.clientId); if (!client) return null;`

#### H8. `ensureStreamServer` race condition
- **File**: `client/src/services/TorrentService.ts:936-965`
- **Issue**: If `ensureStreamServer()` is called twice concurrently, `streamServerPromise` is set but the `streamServerReady` flag isn't checked until after the promise resolves. Both calls could pass the `if (this.streamServerReady) return;` check before either sets it.
- **Impact**: Double service worker registration, potential errors.
- **Fix**: Check `streamServerReady` again inside the promise body, or use a mutex pattern.

### 🟡 MEDIUM (Fix When Possible)

#### M1. `TorrentService` test helper duplicated across 2 test files
- **Files**: `TorrentService.test.ts:22-47`, `TorrentService.fixes.test.ts:22-47`
- **Issue**: The `createTorrent()` helper function is copy-pasted identically.
- **Impact**: Maintenance burden; changes to the mock must be made in both places.
- **Fix**: Extract to a shared `__tests__/helpers.ts` or `__tests__/mocks.ts` file.

#### M2. `SyncService` heartbeat doesn't stop on dispose during interval wait
- **File**: `client/src/services/SyncService.ts:224-249`
- **Issue**: `startHeartbeat` uses `setInterval` registered with cleanup, but the heartbeat callback checks `this.isDisposed` — if dispose happens between interval fires, there's a window where it still sends sync messages.
- **Impact**: Minor — one extra heartbeat may be sent after dispose.
- **Fix**: Add a guard at the top of the interval callback that returns immediately if disposed.

#### M3. `P2PService` doesn't validate peer ID format on `connect()`
- **File**: `client/src/services/P2PService.ts:325-354`
- **Issue**: `App.tsx` validates the peer ID length (6 chars) but `P2PService.connect()` accepts any string. If called programmatically with an invalid ID, it will silently fail with a confusing error.
- **Impact**: Poor error messages for developers using the service directly.
- **Fix**: Add peer ID format validation in `P2PService.connect()`.

#### M4. `RoomPage` has unused `peerRole` prop
- **File**: `client/src/components/RoomPage.tsx:66`
- **Issue**: `peerRole` is destructured but never used directly in the component (only `canControlTorrent` and `isGuest` derived from it are used). Actually it IS used in the type but not in the JSX — wait, checking... it's not used in the component body. The `isGuest` variable is derived from `peerRole` but `peerRole` itself is unused.
- **Impact**: Minor lint warning (though `noUnusedParameters` is set).
- **Fix**: Remove from destructuring or use it.

#### M5. `StatusBar` doesn't show P2P connection quality color
- **File**: `client/src/components/StatusBar.tsx:27`
- **Issue**: `qualityClass` is computed but the `connectionQuality` text label shows "unknown" as "—" with no styling. The `ok`/`warning`/`error` classes are applied but may not have corresponding CSS.
- **Impact**: Users can't visually distinguish connection quality.
- **Fix**: Verify CSS classes exist; add explicit styling for `.ok`, `.warning`, `.error` in status bar.

#### M6. `dist/` directory committed to git
- **File**: `client/dist/` exists in the repo
- **Issue**: The `client/dist/` directory (build output) is present in the working tree. `.gitignore` at root ignores `dist/` but `client/dist/` has its own `.gitignore` that also ignores `dist`. However, the files are already tracked.
- **Impact**: Build artifacts in source control; potential merge conflicts.
- **Fix**: `git rm -r --cached client/dist/` and verify `.gitignore` covers it.

#### M7. `package-lock.json` at root is gitignored
- **File**: `.gitignore:31`
- **Issue**: `/package-lock.json` is gitignored. The root `package.json` is the primary entry point for the project. Without lockfile, CI builds may get different dependency versions.
- **Impact**: Non-reproducible builds.
- **Fix**: Remove `/package-lock.json` from `.gitignore` and commit it.

#### M8. Electron CSP allows `http://127.0.0.1:*` for media-src
- **Files**: `client/electron/main.cjs:130`, `client/index.html:6`
- **Issue**: `media-src 'self' blob: http://127.0.0.1:*` — the wildcard port `*` is not valid CSP syntax. Browsers will ignore this directive, potentially blocking media from the local stream server.
- **Impact**: Media may not load from the local Electron static server on some ports.
- **Fix**: Use `http://127.0.0.1` without port wildcard, or set a fixed port.

#### M9. `TorrentService` `updatePlaybackPosition` uses `fileDurationSeconds` from video element
- **File**: `client/src/App.tsx:856-863`
- **Issue**: `handleTimeUpdate` passes `video.duration` which can be `NaN` for streaming content (live or incomplete metadata). This would cause `updatePlaybackPosition` to silently skip (due to `fileDurationSeconds <= 0` check), meaning buffer prioritization never works for some streams.
- **Impact**: Buffer management doesn't work for certain torrent streams.
- **Fix**: Add a fallback duration estimate or use a different strategy for unknown durations.

#### M10. `P2PService` `disconnect()` doesn't clear `reconnectAttempts`
- **File**: `client/src/services/P2PService.ts:775-785`
- **Issue**: When `disconnect()` is called (user leaves room), `reconnectAttempts` is not reset. If the user reconnects, the counter still has the old value.
- **Impact**: After a manual disconnect, auto-reconnect may give up sooner than expected.
- **Fix**: Reset `this.reconnectAttempts = 0` in `disconnect()`.

- **Issue**: The `withRetry` and `getBackoffDelay` functions are exported but never imported anywhere in the codebase.

#### L2. `syncUtils.ts` only has 2 small functions
- **File**: `client/src/utils/syncUtils.ts`
- **Issue**: `clampSyncTolerance` is a one-liner used in 3 places. `isPlaybackBlockedError` is a small utility. This file could be merged into a more general utils file.
- **Impact**: Unnecessary file fragmentation.
- **Fix**: Merge into `format.ts` or a new `playerUtils.ts`.

#### L3. `types.ts` has unused exports
- **File**: `client/src/services/types.ts:48-73`
- **Issue**: `TorrentSourceMessage`, `ChatMessage`, `Peer`, `PeerRole`, `PeerConnectionState` — some of these are used, but `TorrentSourceMessage` is defined in both `types.ts` and `P2PService.ts` (as a local type).
- **Impact**: Confusion about which type to use.
- **Fix**: Consolidate duplicate type definitions.

#### L4. `server/` directory is empty placeholder
- **File**: `server/README.md`
- **Issue**: The `server/` directory exists with only a README saying it's reserved. It adds confusion to the project structure.
- **Impact**: Developers may wonder if something is missing.
- **Fix**: Either remove the directory or add a `.gitkeep` with a clearer explanation.

#### L5. `ErrorBoundary` is never tested
- **File**: `client/src/components/ErrorBoundary.tsx`
- **Issue**: No tests for the error boundary component.
- **Impact**: If it's broken, errors will be silent.
- **Fix**: Add a test that renders a component that throws and verifies the fallback UI.

#### L6. `VideoPlayer` has unused `_onMuxStreamRequest` parameter
- **File**: `client/src/components/VideoPlayer.tsx:109`
- **Issue**: `onMuxStreamRequest: _onMuxStreamRequest` — prefixed with underscore to suppress lint, but the prop is never used in the component body.
- **Impact**: Dead prop; confusing API surface.
- **Fix**: Remove the prop or implement mux stream handling in the player.

#### L7. `TorrentService` `normalizeError` returns generic message for non-string errors
- **File**: `client/src/services/TorrentService.ts:999-1003`
- **Issue**: `typeof error === "string" ? error : "Unknown torrent error"` — if error is an object with a message, it's lost.
- **Impact**: Poor error messages for debugging.
- **Fix**: Extract `error.message` or use `String(error)`.

#### L8. CI builds don't cache `node_modules` for Electron build jobs
- **File**: `.github/workflows/build.yml:78-83`
- **Issue**: The `build` job runs `npm ci` but doesn't cache `node_modules`. The `checks` job does cache, but the build job re-downloads everything.
- **Impact**: Slower CI builds, more bandwidth.
- **Fix**: Add cache configuration to the build job steps.

#### L9. `electron:build` script doesn't specify platform
- **File**: `client/package.json:12`
- **Issue**: `"electron:build"` without a platform flag will build for the current platform only. This is fine for local dev but the script name implies it's generic.
- **Impact**: Confusing for developers.
- **Fix**: Rename to clarify or add platform auto-detection.

#### L10. `TorrentService` `enforceBufferLimit` uses type assertion instead of proper types
- **File**: `client/src/services/TorrentService.ts:819-836`
- **Issue**: Casts `activeTorrent` to an anonymous type with `paused`, `pause`, `resume`, `downloaded` properties instead of extending the `TorrentInstance` interface.
- **Impact**: Type safety hole; if WebTorrent changes its API, this silently breaks.
- **Fix**: Add these properties to the `TorrentInstance` interface.

#### L11. `P2PService` `listeners` uses `Set` but iteration order matters
- **File**: `client/src/services/P2PService.ts:262-274`
- **Issue**: `Set` iteration order is insertion order, which is fine, but there's no way to prioritize or deduplicate listeners. If the same callback is added twice, it'll fire twice.
- **Impact**: Potential duplicate event handling if `on()` is called multiple times with the same callback.
- **Fix**: Add deduplication check in `on()` method.

#### L12. `App.tsx` `handleLeaveRoom` doesn't abort pending torrent load before destroying
- **File**: `client/src/App.tsx:695-729`
- **Issue**: `torrentLoadAbortRef.current?.abort()` is called, but the `processTorrentLoadQueue` finally block checks `abortController.signal.aborted` before processing the next queue item. However, the current in-flight `loadTorrentRequest` is NOT aborted — it continues running to completion.
- **Impact**: Torrent loading continues in the background after leaving the room, wasting resources.
- **Fix**: Pass the abort signal into `loadTorrentRequest` and check it at each async step.

## Architecture Assessment

### Strengths
- Clean service-layer separation (P2PService, SyncService, TorrentService)
- Consistent cleanup pattern via AbortController
- Good use of TypeScript strict mode
- Electron sandboxing and context isolation properly configured
- CI gates for lint, type-check, and tests

### Weaknesses
- Monolithic App.tsx (1184 lines) — biggest architectural risk
- No state management library (Zustand mentioned in SPEC but not used)
- No component-level testing
- No E2E or integration testing
- Mixed CJS/ESM in Electron layer creates fragility
- Service worker has a critical `await` bug
