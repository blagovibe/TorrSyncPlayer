# TorrSyncPlayer — Full Project Audit

## Scope
Complete audit of codebase, architecture, dependencies, tests, CI/CD, security, and processes.

## 1. CRITICAL ISSUES (Fix Immediately)

### 1.1 `package-lock.json` committed despite `.gitignore` rule
- **Location:** `.gitignore:31` (`/package-lock.json`) vs `client/package-lock.json` (404KB)
- **Severity:** Medium
- **Description:** The root `.gitignore` bans `/package-lock.json` but the client lockfile is commit-tracked. The root-level rule only applies to the repo root, not `client/`. This is inconsistent — the project has a lockfile that can drift from `package.json`.
- **Recommendation:** Either commit the lockfile intentionally (remove the gitignore rule) or add `client/package-lock.json` to gitignore. If committed, ensure CI uses `npm ci`.

### 1.2 No `license` field in `package.json`
- **Location:** `client/package.json`, `package.json`
- **Severity:** Medium
- **Description:** README says "Private project. All rights reserved" but `package.json` lacks a `license` field. This causes npm warnings and is ambiguous for contributors.
- **Recommendation:** Add `"license": "UNLICENSED"` or `"license": "MIT"` depending on intent.

### 1.3 `P2PService` — No input validation on outbound peer messages
- **Location:** `client/src/services/P2PService.ts:749-777`
- **Severity:** Medium
- **Description:** `sendTorrentSource`, `sendSync`, `sendRoomConfig` perform no validation on parameters before sending. A buggy caller could send `NaN`, `Infinity`, or `null` values to peers, causing JSON parse failures on the receiving end.
- **Recommendation:** Add basic validation (finite numbers, non-empty strings) to outbound send methods.

### 1.4 `P2PService` — Event listener leak on reconnection
- **Location:** `client/src/services/P2PService.ts:524-558`
- **Severity:** High
- **Description:** `attemptReconnect()` creates a new `setTimeout` via `this.cleanup.setTimeout()` but `cleanup.abort()` is never called during reconnect. After `maxReconnectAttempts` is reached, stale timers remain registered in the cleanup handle, potentially firing after disconnect/leave.
- **Recommendation:** Clear the specific reconnect timeout on disconnect, or track reconnect timer IDs for explicit cleanup.

### 1.5 `App.tsx` — Memory leak: `beforeunload` cleanup removes listener but `doCleanup` runs every time
- **Location:** `client/src/App.tsx:1004-1022`
- **Severity:** Medium
- **Description:** The `useEffect` for `beforeunload` returns a cleanup that calls `doCleanup()`. The `doCleanup` function destroys `p2pServiceRef`, `syncServiceRef`, `torrentServiceRef`, and the video element. But this cleanup runs both on `beforeunload` event AND on component unmount (React strict mode double-fire). The `doCleanup` function is not idempotent — calling it twice on the same refs causes errors.
- **Recommendation:** Add an `_isCleanedUp` guard to prevent double-execution, or use `useRef` for the cleanup function instead of defining it inline.

### 1.6 Electron CSP allows `unsafe-inline` for styles (necessary but undocumented)
- **Location:** `client/index.html:6`, `client/electron/main.cjs:130`
- **Severity:** Low
- **Description:** Both the HTML meta CSP and the Electron server CSP include `style-src 'unsafe-inline'`. While required for React inline styles, it weakens XSS protection. This is a trade-off that should be documented.
- **Recommendation:** Add a comment in the CSP string explaining why `unsafe-inline` is needed. Consider migrating to CSS-in-JS with nonce-based CSP in the future.

## 2. HIGH PRIORITY ISSUES (Fix Soon)

### 2.1 `TorrentService.electronBackend` cached at class field level — stale after window reload
- **Location:** `client/src/services/TorrentService.ts:859-869`, line 140
- **Severity:** High
- **Description:** `electronBackend` is resolved once via `this.getElectronBackend()` which caches in `cachedElectronBackend`. If the Electron preload fails on first load or the backend changes, the service will never retry.
- **Recommendation:** Make `getElectronBackend()` re-check `window.torrsyncElectronTorrent` each time instead of caching permanently.

### 2.2 `App.tsx` — `torrentServiceRef` recreated on every render via `getTorrentService`
- **Location:** `client/src/App.tsx:98-103`
- **Severity:** Medium
- **Description:** `getTorrentService` creates a new `TorrentService` if the ref is null. But the ref is set to `null` in `handleLeaveRoom` (line 707). On re-entry to the room, a new service is created. However, `torrentServiceVersion` state (line 97) is used to force re-subscriptions — this pattern is fragile and can cause stale closures.
- **Recommendation:** Create the torrent service in a `useEffect` tied to the view lifecycle, not lazily in a callback.

### 2.3 `handlePong` doesn't validate RTT sanity upper bound properly
- **Location:** `client/src/services/P2PService.ts:741-747`
- **Severity:** Medium
- **Description:** `handlePong` accepts any RTT under 30 seconds (`rtt < 30000`). A RTT of 29 seconds would be accepted and used for connection quality calculation, causing misleading UI.
- **Recommendation:** Set a more realistic upper bound (e.g., 5000ms) and clamp/discard outliers.

### 2.4 `P2PService.connect` — exponential backoff without jitter
- **Location:** `client/src/services/P2PService.ts:345-359`
- **Severity:** Low
- **Description:** Retry delay uses `baseDelay * Math.pow(2, attempt - 1)` without jitter. If multiple clients fail simultaneously (e.g., server outage), they'll all retry at the same times, creating thundering herd.
- **Recommendation:** Add random jitter: `delay * (0.5 + Math.random() * 0.5)`.

### 2.5 `SyncService` — Heartbeat suppression flags never reset on error
- **Location:** `client/src/services/SyncService.ts:224-231`
- **Severity:** Medium
- **Description:** The heartbeat reset block clears suppression flags unconditionally. If a `play()` call sets `suppressNextEventSync.play = true` but the subsequent `video.play()` fails (line 106 resets it), and the heartbeat fires in between, the flag could be cleared prematurely, causing a duplicate sync event.
- **Recommendation:** Remove the unconditional flag clearing from heartbeat; instead, set a TTL on suppression flags.

### 2.6 No error handling for `navigator.clipboard.writeText`
- **Location:** `client/src/components/HomePage.tsx:62-74`, `client/src/components/RoomPage.tsx:171-183`
- **Severity:** Low
- **Description:** `copyPeerId` catches errors and logs to console but provides no user feedback. In Electron with clipboard permissions denied, users see nothing.
- **Recommendation:** Show a toast or fallback (e.g., `execCommand('copy')`) or display the ID with a selectable text field.

## 3. MEDIUM PRIORITY ISSUES (Technical Debt)

### 3.1 Monolithic `App.tsx` (1184 lines) — needs decomposition
- **Location:** `client/src/App.tsx`
- **Severity:** Medium
- **Description:** Single file contains all state management, event handlers, P2P lifecycle, torrent lifecycle, and UI logic for the entire application. This makes testing, debugging, and onboarding extremely difficult.
- **Recommendation:** Extract into:
  - `useP2PConnection()` hook
  - `useTorrentPlayback()` hook
  - `useRoomState()` hook
  - Move utility functions (`hashBytes`, `createMagnetSource`, `createTorrentFileSource`) to `utils/torrent.ts`

### 3.2 `resetTorrentState` commented-out player readiness reset
- **Location:** `client/src/App.tsx:141-143`
- **Severity:** Medium
- **Description:** `setIsPlayerReady(false)` and `isPlayerReadyRef.current = false` are commented out with a comment explaining the intent. This means player readiness persists across torrent resets, but the `tryApplyPendingRemoteSync` / queue processing depends on this flag. This could cause stale sync to be applied to a new torrent.
- **Recommendation:** Either implement proper player readiness reset with a state machine, or remove the dead code and document the invariant.

### 3.3 `parseInboundMessage` validates `syncToleranceSeconds` is finite but not positive
- **Location:** `client/src/services/P2PService.ts:192-199`
- **Severity:** Medium
- **Description:** `room_config` messages accept any finite number including negative values and zero. The receiver calls `clampSyncTolerance()` which handles this, but the sender (`sendRoomConfig`) does not clamp before sending, so a buggy state could propagate an invalid tolerance to guests.
- **Recommendation:** Clamp `syncToleranceSeconds` at both send and receive boundaries.

### 3.4 `webtorrent-sw.js` — No origin validation on fetch handler
- **Location:** `client/public/webtorrent-sw.js:6`
- **Severity:** Medium
- **Description:** The service worker checks `event.clientId` exists but the origin check on the URL only happens inside `serve()` for window clients. The initial `listener()` function doesn't validate the request origin.
- **Recommendation:** Add origin validation in the `listener()` function before processing.

### 3.5 `ensureAudioServer` uses a custom promise-based waiter pattern instead of standard async
- **Location:** `client/electron/torrent-bridge.cjs:620-636`
- **Severity:** Low
- **Description:** The `_ensureAudioServerWaiter` / `_resolveAudioServerWaiter` pattern is error-prone. If `setStreamBaseUrl` is never called (e.g., app shuts down), the promise hangs until `destroy()` resolves it with `null`.
- **Recommendation:** Use `AbortController` or a proper async-ready pattern with timeout.

### 3.6 No TypeScript types for Electron API surface
- **Location:** `client/src/services/TorrentService.ts:76-102` (inline type), `client/electron/preload.cjs`
- **Severity:** Medium
- **Description:** The `ElectronTorrentBackend` type is defined in `TorrentService.ts` but the actual implementation in `preload.cjs` and `torrent-bridge.cjs` is untyped JavaScript. Type mismatches won't be caught at build time.
- **Recommendation:** Create a shared `electron-api.d.ts` type definition file and validate `preload.cjs` against it manually or via JSDoc.

### 3.7 `torrent-bridge.cjs` — `BoundedChunkStore` and `MemoryChunkStore` loaded via relative `node_modules` path
- **Location:** `client/electron/torrent-bridge.cjs:4-5`
- **Severity:** Medium
- **Description:** Uses `path.join(__dirname, "..", "node_modules", "memory-chunk-store")` which breaks if dependencies are hoisted by a package manager (pnpm, yarn PnP) or if the electron-builder asar layout differs.
- **Recommendation:** Use normal `require("memory-chunk-store")` and configure electron-builder to include it in externals if needed.

### 3.8 ESLint `no-explicit-any` rule but `Record<string, unknown>` used extensively
- **Location:** `client/eslint.config.js:27`, used throughout `TorrentService.ts`
- **Severity:** Low
- **Description:** The codebase uses `Record<string, unknown>` and `any` in several places that ESLint's `no-explicit-any` would catch. The `TorrentEventCallback` type (`TorrentService.ts:36-43`) uses `(...args: unknown[]) => void` which is intentionally loose, but there are other places where proper types could be used.
- **Recommendation:** Audit all `unknown[]` callback signatures and replace with proper typed events where possible.

## 4. LOW PRIORITY ISSUES (Nice to Have)

### 4.1 Duplicate test setup in `TorrentService.test.ts` and `TorrentService.fixes.test.ts`
- **Location:** Both files have identical `vi.hoisted()` blocks and `createTorrent()` helper
- **Severity:** Low
- **Recommendation:** Move shared test infrastructure to `test-utils.ts` or a shared fixture file.

### 4.2 `test-utils.ts` is nearly empty
- **Location:** `client/src/services/__tests__/test-utils.ts`
- **Severity:** Low
- **Description:** Only exports one function (`setupElectronBackendCleanup`). The common mock torrent/webTorrent setup is duplicated across test files.
- **Recommendation:** Consolidate all shared mocks and helpers into this file.

### 4.3 No integration/E2E tests
- **Severity:** Medium
- **Description:** All 39 tests are unit tests with mocked dependencies. There are no integration tests for:
  - PeerJS connection lifecycle with a real signaling server
  - Torrent download + video playback end-to-end
  - Sync accuracy measurement
  - Electron app packaging smoke test
- **Recommendation:** Add at least one E2E test using Playwright (was listed as available skill) to verify the app launches and creates a room.

### 4.4 `App.tsx` uses refs for state that should be in state or context
- **Location:** Multiple refs (lines 94-117)
- **Severity:** Medium
- **Description:** `selectedMediaFileRef`, `currentTorrentSourceRef`, `isLoadingTorrentRef`, etc. are refs used to avoid stale closures, but this pattern is error-prone and makes the code hard to follow.
- **Recommendation:** Consider using `useReducer` + `useContext` to manage room state, which eliminates most stale closure issues.

### 4.5 Unused imports
- **Location:** `client/src/App.tsx:7` — `SubtitleTrackInfo` is imported but used only as a prop type in child components
- **Severity:** Low
- **Recommendation:** Audit all unused imports and remove them.

### 4.6 `VideoPlayer.tsx` — `_onMuxStreamRequest` is prefixed with underscore but still destructured
- **Location:** `client/src/components/VideoPlayer.tsx:109`
- **Severity:** Low
- **Description:** The prop `onMuxStreamRequest` is destructured as `_onMuxStreamRequest` to suppress the unused warning, but the underscore convention doesn't suppress ESLint `@typescript-eslint/no-unused-vars` without explicit config.
- **Recommendation:** Either use the prop or remove it from destructuring.

### 4.7 CI builds on `ubuntu-latest` and `windows-latest` but tests only run on `ubuntu-latest`
- **Location:** `.github/workflows/build.yml:18-43`
- **Severity:** Medium
- **Description:** Lint/typecheck/tests run only on Ubuntu. Windows-specific issues (path separators, native module builds) won't be caught until the build job.
- **Recommendation:** Run `type-check` on both platforms, or add a Windows test job.

### 4.8 Release workflow creates a tag but the tag format `push-${run_id}-${run_attempt}` is not semver
- **Location:** `.github/workflows/build.yml:104-110`
- **Severity:** Low
- **Description:** The auto-generated tags are not semantic versions, which makes it hard to determine the latest release programmatically.
- **Recommendation:** Use `v${version}` tags based on `package.json` version, or use GitHub's `generate_release_notes` with a date-based tag.

### 4.9 No `CHANGELOG.md`
- **Severity:** Low
- **Description:** The project has version 0.1.12 but no changelog. The `changelog-generator` skill is available.
- **Recommendation:** Generate an initial changelog from git history.

### 4.10 `TorrentService.fixes.test.ts` duplicates mock setup from `TorrentService.test.ts`
- **Location:** `client/src/services/__tests__/TorrentService.fixes.test.ts:7-20`
- **Severity:** Low
- **Description:** The `vi.hoisted()` block is copy-pasted almost verbatim.
- **Recommendation:** Extract to shared test utility.

## 5. SECURITY AUDIT

### 5.1 Content Security Policy
- **Status:** Well-configured for Electron context. Blocks `object-src`, restricts `connect-src` to known tracker domains, sets `frame-ancestors 'none'`.
- **Risk:** Inline styles (`unsafe-inline`) needed for React. Acceptable for desktop app.
- **Recommendation:** Good as-is.

### 5.2 Electron Security
- **Status:** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`. All properly configured.
- **Risk:** Low.

### 5.3 IPC Input Validation
- **Location:** `client/electron/main.cjs:203-255`
- **Status:** All IPC handlers validate input types and lengths before passing to `TorrentBridge`.
- **Risk:** Good.

### 5.4 Torrent Bridge URL Validation
- **Location:** `client/electron/torrent-bridge.cjs:979-995`
- **Status:** `validateLocalStreamUrl` enforces http/https protocol and loopback-only hostnames.
- **Risk:** Good.

### 5.5 Service Worker Origin Check
- **Location:** `client/public/webtorrent-sw.js:6`
- **Risk:** Medium — The `event.clientId` check doesn't validate origin. A malicious page in the same origin could potentially interact with the SW.
- **Recommendation:** Add explicit origin check.

### 5.6 No rate limiting on PeerJS message handling
- **Location:** `client/src/services/P2PService.ts:608-648`
- **Risk:** Low (P2P context, not server). A malicious peer could flood sync messages.
- **Recommendation:** Add a simple rate limiter (max 10 sync msgs/sec per peer).

## 7. ARCHITECTURE NOTES

### Strengths
- Clean service separation (P2P, Sync, Torrent)
- Good use of AbortController-based cleanup pattern
- Well-structured Electron main process with proper security defaults
- Input validation on IPC boundaries
- Custom `BoundedChunkStore` for memory management
- Rate-limited ffmpeg process spawning

### Weaknesses
- `App.tsx` is a god component (1184 lines)
- Heavy use of refs instead of proper state management
- No state management library (SPEC mentions "Custom Zustand-like store" but none exists)
- Test coverage is low (~39 tests, all unit, no E2E)
- No error reporting/telemetry in production
