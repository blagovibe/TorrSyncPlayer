## 2. Critical Issues (P0 — Must Fix)

### 2.1 — 9 TorrentService Tests Failing (Broken Mock Setup)

**Severity:** 🔴 Critical
**Affected:** `TorrentService.test.ts` (7 failures), `TorrentService.fixes.test.ts` (2 failures)

**Root cause:** `vi.mock("webtorrent", ...)` uses `vi.hoisted(() => ({ addMock: vi.fn(), ... }))`, but `addMock` and `webTorrentMock` are referenced inside the factory *before* the hoisted bindings are wired to the outer scope. The `const { addMock } = vi.hoisted(...)` destructuring in the test file captures the *initial* `vi.fn()` instances, while `addMock.mockReturnValue(...)` in tests reconfigures those — but `TorrentService.getClient()` triggers a fresh `import("webtorrent")` each time the mock factory runs, creating *new* `addMock`/`webTorrentMock` instances that the tests never see. The mock's `add` call inside `TorrentService` calls a *different* `addMock` than the one the test configures.

Additionally, 8 "unhandled rejection: TorrentService has been destroyed" errors cascade because `clearActiveTorrentForAdd()` destroys the service when the Electron backend test leaks state into subsequent tests.

**Fix:** Restructure the mock so a shared mutable ref object is used, and ensure `afterEach` fully resets service state between tests.

### 2.2 — RoomStateContext Exports Non-Component Utility (React Refresh Warning)

**Severity:** 🔴 Warning → error risk
**File:** `RoomStateContext.tsx:130`

`useRoomStateContext` (a hook, not a component) is exported from the same file as `RoomStateContext` (a context). `react-refresh/only-export-components` warns because this breaks Fast Refresh guarantees. At scale, can cause stale closures in dev mode.

**Fix:** Move `useRoomStateContext` to a separate file (e.g., `hooks/useRoomStateContext.ts`).

## 3. High-Severity Issues (P1 — Should Fix Soon)

### 3.1 — Electron IPC `validateIpcSender` Rejects `file://` Protocol

**Severity:** 🔴 High
**File:** `main.cjs:240`

```js
if (parsed.protocol === "file:") return false;
```

In production builds, the app loads from the local static server (`http://127.0.0.1:<port>`), not `file:`. But this check is overly restrictive and inconsistent: it blocks `file:` while allowing only `http:` with `127.0.0.1`/`localhost`. If the static server were misconfigured or a race condition occurs, all IPC calls silently fail with "Unauthorized IPC caller."

**Fix:** Remove the `file:` rejection. The `allowedOrigins` check is sufficient.

### 3.2 — `isDestroyed` Flag Not Reset on Reuse After `destroy()`

**Severity:** 🔴 High
**File:** `TorrentService.ts:136,716`

After `destroy()` sets `this.isDestroyed = true`, the service is permanently unusable. But in the TorrentService tests, the mock test `uses the Electron backend...` calls `clearActiveTorrentForAdd()` → `destroy()`, then the *next* test in the same file creates a fresh service but shares module-level mock state — the `vi.clearAllMocks()` in `afterEach` doesn't reset `isDestroyed` on already-created instances.

More critically, in `App.tsx`, if a guest disconnects and reconnects within the same session, the old `TorrentService` is destroyed but the getter `getTorrentService()` may return the stale ref.

**Fix:** Either reset `isDestroyed = false` in `clearActiveTorrentForAdd()` when creating a new internal instance, or make `getTorrentService()` replace the service after destruction.

### 3.3 — `ffmpegQueue` has Race Condition in `handleAudioRequest`

**Severity:** 🟠 High
**File:** `torrent-bridge.cjs:809-841`

The inline rate-limiting for ffmpeg processes has a bug: when `activeFfmpegCount >= MAX_CONCURRENT_FFMPEG`, the code creates a `Promise` and pushes to `ffmpegQueue`, but the `task` closure captures `ffmpeg` from the outer scope *before* it's assigned inside the queued task. The `resolve()` is called immediately (line 836) before ffmpeg actually spawns, so `session.process = ffmpeg` (line 842) runs *before* the inner `task()` completes, assigning `undefined`.

**Fix:** Move `session.process = ffmpeg` inside the queued task body, after spawning.

### 3.4 — Torrent File Size Limit Discrepancy

**Severity:** 🟠 High
**Files:** `P2PService.ts:28`, `preload.cjs:5`, `main.cjs:261`

- P2P max: `P2P_MAX_TORRENT_BYTES = 50 * 1024` = 51,200 bytes
- IPC max: `MAX_TORRENT_FILE_BYTES = 10 * 1024 * 1024` = 10,485,760 bytes  
- Preload: `magnetLink.length > 10000` but no equivalent in main process (main checks 7000)
- App.tsx load: `MAX_TORRENT_FILE_SIZE = 10 * 1024 * 1024` (browser-side)

The P2P limit is 50KB — torrents larger than that silently fail to send to guests with only a log warning. The IPC limit is 1MB. These should be consistent and documented.

**Fix:** Align limits to `IPC_MAX_TORRENT_BYTES` (10MB) everywhere, and expose a user-facing error.

### 3.5 — `bounded-chunk-store.cjs` Returns Callback-Style but WebTorrent Expects Promises

**Severity:** 🟠 High
**File:** `bounded-chunk-store.cjs`

`put()` and `get()` use callback-style (`cb(err, result)`), but modern WebTorrent may call them without callbacks (expecting synchronous behavior or promises). The `get()` method sets `opts = null` when called with 2 args, which could cause issues if WebTorrent passes options.

**Fix:** Ensure all methods handle both callback and no-callback (sync) calls correctly.

## 4. Medium-Severity Issues (P2 — Technical Debt)

### 4.1 — Duplicate State Management (`App.tsx` + `RoomStateContext` + `useRoomState`)

**Severity:** 🟡 Medium
**Files:** `App.tsx`, `RoomStateContext.tsx`, `useRoomState.ts`

Room state is managed in three places:
1. `App.tsx`: `useState` for `selectedMediaIndexState`, `selectedMediaKind`, etc.
2. `RoomStateContext`: React context with `useReducer` for the same values (`selectedMediaIndex`, `selectedMediaFile`, etc.)
3. `useRoomState`: `useRef` refs returned to `App.tsx` for "current source key" tracking

This causes:
- Redundant re-renders (state + context dispatch)
- Risk of divergence between the three sources
- Confusing `selectedMediaIndex` (context) vs `selectedMediaIndexState` (local) naming

**Fix:** Consolidate to a single source of truth. Recommend the context reducer as the primary state, eliminating the duplicate `useState` fields in `App.tsx`.

### 4.2 — Missing `RoomPage` and `RoomInfo` Component Tests

**Severity:** 🟡 Medium

`RoomPage.tsx` (464 lines — the most complex component) and `RoomInfo.tsx` (121 lines with chat) have zero tests. These contain drag-and-drop, role-based UI, chat rendering, and peer list management.

**Fix:** Add component tests for `RoomPage` and `RoomInfo`.

### 4.3 — `NoUnusedLocals` Disables OSA (`App`-related) — Incomplete Cleanup

**Severity:** 🟡 Low-Medium
**File:** `TorrentService.ts:79`

`onAny()` in `cleanup.ts` is defined but never used in the codebase. It's dead code.

**Fix:** Remove `onAny()` from the cleanup utility.

### 4.4 — CSP Header Mismatch Between HTML and Electron

**Severity:** 🟡 Medium
**Files:** `index.html` (meta tag), `main.cjs` (response header)

The HTML meta CSP allows `media-src 'self' blob: http://127.0.0.1` (hardcoded), but the Electron CSP builds `media-src 'self' blob: ${mediaSource}` where `mediaSource` is the dynamically assigned port. If the HTML meta is served, it may conflict with the HTTP header (browsers use the stricter of the two).

**Fix:** Align CSP policies. Remove the meta tag from `index.html` and rely solely on the Electron HTTP header.

### 4.5 — `prepare-electron-app.cjs` Copies `package-lock.json` Without Filtering Dev Dependencies

**Severity:** 🟡 Medium
**File:** `prepare-electron-app.cjs:21`

`fs.cpSync(... "package-lock.json")` copies the full lock file (including dev dependency resolution), then runs `npm ci --omit=dev`. This works but is fragile: if the lock file references registries or optional deps unavailable in the build environment, `npm ci` fails.

**Fix:** Use `npm ci --omit=dev --no-optional` or generate a production-only lock.

### 4.6 — `webtorrent-sw.js` Service Worker Has No Origin Validation on PostMessage

**Severity:** 🟡 Medium
**File:** `webtorrent-sw.js:86-96`

The service worker posts messages to all clients indiscriminately. Any page in the same scope can receive the message. While the response is filtered by `self.registration.scope`, a malicious page could intercept torrent data.

**Fix:** Validate `event.source` origin before posting, or use a shared secret.

### 4.7 — `SyncService.applyRemoteSync` Doesn't Handle `NaN` Duration

**Severity:** 🟡 Low
**File:** `SyncService.ts:147`

`Math.min(rawCompensatedPosition, snapshot.duration || Infinity)` — if `snapshot.duration` is `NaN` (which happens before metadata loads), `NaN || Infinity` evaluates to `Infinity`, which is safe. But if `snapshot.duration` is `0` (falsy), it also falls to `Infinity`, which could allow seeking to arbitrary positions before media is ready.

**Fix:** Use `Number.isFinite(snapshot.duration) && snapshot.duration > 0 ? snapshot.duration : Infinity`.

### 4.8 — `P2PService.disconnect()` Doesn't Clear `isReconnecting` Flag

**Severity:** 🟡 Low
**File:** `P2PService.ts:847-868`

`disconnect()` sets `state = "disconnecting"` and clears timers, but doesn't reset `this.isReconnecting = false`. If `disconnect()` is called during a reconnect attempt, the `attemptReconnect()` method checks `if (this.isReconnecting) return;` — but the state is `"disconnecting"`, so it returns early. However, `isReconnecting` remains `true` permanently, which could affect future reconnection attempts if the service is reused.

**Fix:** Add `this.isReconnecting = false;` in `disconnect()`.

## 7. Architecture Observations

### Strengths
- Clean service-layer separation (P2PService, SyncService, TorrentService)
- Good use of AbortController-based cleanup pattern
- Type-safe Electron API surface via `electron-api.d.ts`
- Rate limiting on P2P messages and ffmpeg processes
- Input validation on inbound P2P messages
- CSP headers and security best practices in Electron main process

### Weaknesses
- Triple state management (useState + Context + refs) creates confusion
- No integration/E2E tests for the core host-guest sync flow
- Electron torrent bridge is 1052 lines with mixed concerns (streaming, probing, rate limiting)
- Mock setup in TorrentService tests is fragile and order-dependent
