# TorrSyncPlayer — Full Project Audit Plan

## Project Summary

TorrSyncPlayer is an Electron + React desktop app for synchronized torrent-based video streaming between peers. Stack: React 18, TypeScript, Vite, Electron 42, PeerJS, WebTorrent. ~3500+ lines of application code across client + Electron main process.

---

## CRITICAL Issues

### 1. XSS via Chat Messages — Inner HTML Injection
- **File**: `RoomInfo.tsx:67-73`, `App.tsx:939`
- **Severity**: CRITICAL
- **Description**: Chat messages (`msg.text`) are rendered as text content, but there's no sanitization on input or display. The `handleSendChat` function in `App.tsx:934` only checks length and rate limits — it does not strip HTML/script. If a peer sends a malicious message containing `<img onerror=...>` or similar, it will be rendered. React's JSX escaping mitigates this in the current code, but the `RoomInfo` component uses `msg.text` directly in JSX which IS safe. However, if anyone switches to `dangerouslySetInnerHTML` in the future, or if the P2P message parsing logic is exploited, this becomes exploitable. The defense is currently accidental (React auto-escaping), not intentional.
- **Recommendation**: Add explicit HTML entity encoding/sanitization on chat content at the boundary (P2P message receipt in `App.tsx:510-513`). Add a CSP `script-src` directive without `'unsafe-inline'` enforced — currently CSP in `main.cjs:73` uses `'self'` only which is good.

### 2. Electron Static Server — Missing CSP in Error Paths
- **File**: `main.cjs:135-138`
- **Severity**: CRITICAL
- **Description**: The static server catches errors and sends a generic 500 response but does NOT set security headers (CSP, X-Frame-Options, etc.) on error responses. An attacker who can trigger server errors (e.g., via crafted requests) gets responses without CSP, potentially enabling injection if content is reflected.
- **Recommendation**: Add security headers to error response paths (`main.cjs:126-138` and `main.cjs:136`).

### 3. IPC Channel Spoofing — Window Close Confirmation
- **File**: `main.cjs:296-305`, `preload.cjs:51-60`
- **Severity**: CRITICAL
- **Description**: The `window-close-confirmed` IPC channel (line 296) calls `app.exit(0)` which destroys all windows and exits. It does NOT call `validateIpcSender(event)` unlike every other IPC handler. Any webpage or compromised renderer can send this IPC to force-kill the app.
- **Recommendation**: Add `validateIpcSender` check to `window-close-confirmed` handler. Same for `window-close-cancelled`.

### 4. Service Worker Registration Without Integrity Check
- **File**: `TorrentService.ts:954`
- **Severity**: CRITICAL
- **Description**: Service worker is registered from `webtorrent-sw.js` which is expected to be in the web root. In Electron mode this file doesn't exist (electron doesn't serve static web root in the same way). If somehow a malicious service worker gets registered, it would have full control over fetch requests for the origin.
- **Recommendation**: In Electron builds, skip service worker registration entirely. Add a check: `if (!this.getElectronBackend() && 'serviceWorker' in navigator)`.

## HIGH Issues

### 5. No Input Sanitization on Magnet Link Display
- **File**: `RoomPage.tsx:262`, `RoomPage.tsx:280-292`
- **Severity**: HIGH
- **Description**: Magnet link value from user input is rendered in a `<textarea>` and also displayed as `sharedSourceLabel`. While React auto-escapes, the `sharedSourceLabel` at line 289-291 is concatenated into a string that could contain special characters. If this is ever used in a different context (e.g., HTML attribute, URL), it could be exploitable.
- **Recommendation**: Sanitize display strings. Never use magnet link values in URL construction without validation.

### 6. FFmpeg Arbitrary URL Execution
- **File**: `torrent-bridge.cjs:710`, `torrent-bridge.cjs:757`, `torrent-bridge.cjs:79`
- **Severity**: HIGH
- **Description**: The `runWithFfmpegLimit` function at line 78-79 spawns `ffmpeg` with `session.streamUrl` as an argument. While `validateLocalStreamUrl` checks for loopback, the `session.streamUrl` is set from `createAudioTrackStreamUrl`, `createMultiplexedStreamUrl`, etc., which receive `streamUrl` from the client. The stream URLs come from WebTorrent's internal server (localhost), but if an attacker can control the session parameters, they could potentially pass arbitrary URLs to ffmpeg via the IPC bridge.
- **Recommendation**: Validate `streamUrl` again at the point of ffmpeg execution, not just at session creation. Add allowlist for stream URL patterns in `handleAudioRequest`.

### 7. Race Condition in Torrent Load Queue
- **File**: `App.tsx:392-401`
- **Severity**: HIGH
- **Description**: When the `finally` block of `processTorrentLoadQueue` runs and there's a pending load, it schedules a new queue processing via `setTimeout(resolve, 0)` but does NOT check if a new abort controller has been set. The reference comparison `pendingTorrentLoadRef.current === pending` could pass even after a new torrent load started, causing duplicate or conflicting loads.
- **Recommendation**: Use a version counter or WeakRef pattern to ensure stale queue processing doesn't interfere with new loads.

### 8. Double State Management (Redundant Room State)
- **File**: `App.tsx:44-52` vs `RoomStateContext.tsx:6-13` vs `useRoomState.ts:6-12`
- **Severity**: HIGH (Technical Debt / Bug Risk)
- **Description**: Room state is managed in THREE places: (1) `App.tsx` useState hooks (`selectedMediaIndexState`, `selectedMediaFileState`, etc.), (2) `RoomStateContext` reducer, and (3) `useRoomState` hook with refs. The App.tsx state drives the UI (jit.si), while the context is used for P2P broadcast decisions. These can get out of sync — e.g., `setSelectedMediaIndexState` (line 321) updates local state but the P2P broadcast at line 353 uses `selectedMediaIndex` from the context, which is set separately via `setMediaIndex`. There are at least 2 places where these can diverge.
- **Recommendation**: Consolidate to a single state source. Use the `RoomStateContext` as the single source of truth, or remove the context entirely and use refs + useState.

### 9. Service Worker Never Unregistered on Electron
- **File**: `TorrentService.ts:953-976`
- **Severity**: HIGH
- **Description**: `ensureStreamServer()` always attempts service worker registration when `navigator.serviceWorker` exists. In Electron, service workers exist but `webtorrent-sw.js` file won't exist (it's a web-only asset), causing a silent failure that sets `streamServerPromise = null` which triggers an infinite retry loop on every `streamToMedia` call.
- **Recommendation**: Detect Electron backend before attempting stream server setup. Add max retry count.

### 10. Stale Closure in processTorrentLoadQueueRef
- **File**: `App.tsx:356-404`, `App.tsx:406-412`
- **Severity**: HIGH
- **Description**: `processTorrentLoadQueueRef.current` is reassigned at line 404 to a new function that closes over current state values. When effects at line 878-889 call `processTorrentLoadQueueRef.current()`, they use whichever version was last assigned, which may have stale closures for `loadTorrentRequest` (depends on state that changes).
- **Recommendation**: Use a queue version counter and always read from refs instead of closures for mutable state.

## MEDIUM Issues

### 11. No Maximum File Count / File Size Validation on .torrent Upload
- **File**: `App.tsx:262-282`, `main.cjs:240-253`
- **Severity**: MEDIUM
- **Description**: While there's a 10MB file size limit enforced in both client and Electron, there's no validation on the number of files _inside_ the torrent. A malicious .torrent file could reference millions of files, causing memory exhaustion when parsed.
- **Recommendation**: Add limits on torrent content (max file count, max filename length) in `TorrentBridge.addSource()`.

### 12. No Cleanup of Event Listeners on Room Leave
- **File**: `App.tsx:582-617` (`handleLeaveRoom`)
- **Severity**: MEDIUM
- **Description**: When leaving a room, `torrentServiceRef.current.destroy()` is called which should clean up listeners. However, the `useEffect` at `App.tsx:790-818` registers listeners on the torrent service and returns a cleanup function. If `torrentServiceRef.current` is set to `null` before the effect cleanup runs, those listeners remain attached to the old service instance.
- **Recommendation**: Call effect cleanup explicitly before nullifying the ref. Or ensure the effect cleanup uses the same service instance reference.

### 13. Non-Atomic State Updates in SyncService
- **File**: `SyncService.ts:128-186`
- **Severity**: MEDIUM
- **Description**: `applyRemoteSync` performs multiple non-atomic operations: check readystate, calculate latency, adjust position, set play/pause. Between these steps, the video element's state could change (e.g., user seeks, network buffering). This can cause sync jitter or unexpected playback states.
- **Recommendation**: Snapshot video state at the start of `applyRemoteSync` and use the snapshot for all calculations. Apply all changes in a single microtask.

### 14. Ping Interval Not Tied to Specific Connection
- **File**: `P2PService.ts:743-755`
- **Severity**: MEDIUM
- **Description**: `startPingInterval()` is called for every new connection (`P2PService.ts:618,625`), but `stopPingInterval()` is only called in `disconnect()`. With multiple connections, only the last connection triggers a new interval, but the first connection's interval keeps running and sending pings to potentially closed connections.
- **Recommendation**: Maintain a single ping interval that iterates all open connections. Use a Set to track active intervals.

### 15. DHT Disabled Without Fallback Warning
- **File**: `bittorrent-dht.ts:1-3`
- **Severity**: MEDIUM
- **Description**: The DHT shim completely disables DHT (`Client = {}`), meaning the app relies entirely on public WebRTC trackers for peer discovery. If tracker connections fail in the browser (no Electron fallback), no peers can be found and streaming stalls without clear user feedback.
- **Recommendation**: Add UI notification when DHT is unavailable and only trackers are used. In Electron mode, enable the real DHT.

### 16. No Timeout on `ensureAudioServer()`
- **File**: `torrent-bridge.cjs:632-648`
- **Severity**: MEDIUM
- **Description**: If `setStreamBaseUrl` is never called (e.g., Electron static server fails to start), `ensureAudioServer()` will hang indefinitely waiting for the `_ensureAudioServerWaiter` promise. This blocks audio track probing, mux stream creation, etc.
- **Recommendation**: Add a timeout (e.g., 10s) to the waiter promise, rejecting with a clear error if the audio server doesn't become available.

### 17. Chat Rate Limiter Uses Component Ref (Not Global)
- **File**: `App.tsx:922-932`
- **Severity**: MEDIUM
- **Description**: The chat rate limiter uses `chatRateTimestamps` (a ref in App component). If the App component re-renders or is recreated, the rate limiter state is lost. Also, the P2P-level sync rate limiting in `P2PService.ts:761-772` uses `syncMessageTimestamps` per peer — but the chat messages are NOT rate-limited at the P2P level, only at the UI level. A malicious peer could flood chat messages.
- **Recommendation**: Add chat message rate limiting at the P2P message handling level, similar to sync message rate limiting.

### 18. Torrent Error Events Don't Distinguish Fatal vs Transient
- **File**: `TorrentService.ts:443-447`, `App.tsx:792-796`
- **Severity**: MEDIUM
- **Description**: All torrent errors (tracker timeout, wire error, metadata error) are emitted through the same `error` event. Some errors are transient (single tracker timeout), others are fatal (no metadata). The UI treats them all equally, showing the error message but potentially leaving the system in an inconsistent state.
- **Recommendation**: Add error severity classification. Allow retry for transient errors. Only update UI error state for fatal errors.

### 19. In-Memory Storage Can Grow Unbounded (Web Mode)
- **File**: `TorrentService.ts:855-864`
- **Severity**: MEDIUM
- **Description**: In browser mode (non-Electron), WebTorrent's default storage is used without the `BoundedChunkStore` limit. The browser's memory can grow unbounded for large torrents. The `bufferWindowBytes` and `maxBufferBytes` settings only affect prioritization, not actual storage in browser mode.
- **Recommendation**: In browser mode, pass a bounded store option to WebTorrent client creation, similar to how Electron mode uses `BoundedChunkStore`.

### 20. Room Password Sent in Plaintext Over P2P
- **File**: `P2PService.ts:812-820`, `App.tsx:181`
- **Severity**: MEDIUM
- **Description**: `roomPassword` is sent via `sendRoomConfig` as a plaintext field. While WebRTC data channels are encrypted (DTLS), the password is still visible in memory and could be intercepted if the DTLS session is compromised. There's no zero-password enforcement — guests can ignore it.
- **Recommendation**: Document that this is not a security mechanism, just a convenience gate. Don't call it "password" in UI if it's not enforced on the guest side. Consider removing or enforcing it.

## LOW Issues

### 21. No `await` for `mediaElement.play()` Error in Buffering Handler
- **File**: `VideoPlayer.tsx:262-264`
- **Severity**: LOW
- **Description**: The `onPlay` event handler sets buffering to false but doesn't catch potential play errors (e.g., if play() was called and failed just before the event fired). This is cosmetic — the buffering indicator might flash incorrectly.
- **Recommendation**: Minor — add error handling if needed.

### 22. Duplicate Magnet Link Source Key Generation
- **File**: `torrent.ts:27`
- **Severity**: LOW
- **Description**: Magnet source key is `magnet:${magnetLink}` which is the full magnet URI. This is sent over P2P and stored. If the magnet link contains unique parameters (tracker auth, etc.), the source key changes even for the same content.
- **Recommendation**: Extract the `xt` hash from the magnet link as the source key for deduplication.

### 23. No ESLint Rule for `console.log` Usage
- **File**: `eslint.config.js`
- **Severity**: LOW
- **Description**: The project has a structured logger system (`utils/logger.ts`) with `torrentLogger`, `p2pLogger`, etc., but ESLint doesn't enforce using it over `console.log`/`console.error`. Several `console.error`/`console.warn`/`console.log` calls remain in `torrent-bridge.cjs` (lines 99, 317, 326-327, 846-847) and Electron main process.
- **Recommendation**: Add `@typescript-eslint/no-console` rule for TS files. Acceptable in CJS files where the logger isn't imported, but add a custom ESLint override for those.

### 24. WebTorrent Client Imported Dynamically Without Retry
- **File**: `TorrentService.ts:856-864`
- **Severity**: LOW
- **Description**: The dynamic `import("webtorrent")` at line 857 will fail permanently if the first load fails (e.g., network issue for chunk loading). There's no retry mechanism.
- **Recommendation**: Add exponential backoff retry for WebTorrent import with a max retry count and user-visible error.

### 25. `navigator.serviceWorker` Null Check Incomplete
- **File**: `TorrentService.ts:950`
- **Severity**: LOW
- **Description**: The check `typeof navigator === "undefined" || !("serviceWorker" in navigator)` doesn't guard against `navigator.serviceWorker` being `undefined` in some Electron versions (it exists but is non-functional).
- **Recommendation**: Add explicit check: `if (!navigator.serviceWorker?.register) return;`

### 26. Hardcoded Sync Tolerance Default Duplicated
- **File**: `config.ts:32` (`SYNC_CONFIG.defaultToleranceSeconds = 1.5`) vs `App.tsx:28` (`DEFAULT_SYNC_TOLERANCE_SECONDS = 1.5`)
- **Severity**: LOW
- **Description**: The default sync tolerance is defined in two places. If changed in one, the other becomes stale.
- **Recommendation**: Import the config value in App.tsx instead of redefining it.

### 27. Room State Context Never Reset on Re-enter
- **File**: `RoomStateContext.tsx:36-55`, `App.tsx:615`
- **Severity**: LOW
- **Description**: `roomState.reset()` is called in `handleLeaveRoom`, but when creating a new room, `useState(roomReducer, initialState)` in the provider means the context state is only the initial state on first mount. If `reset()` doesn't fully clear all state (e.g., `pendingRemoteSync`), stale values from the previous session could persist.
- **Recommendation**: Verify `reset()` clears all fields. Add unit test for room lifecycle (create → leave → create).

### 28. No Test Coverage for Electron Bridge
- **File**: `client/electron/torrent-bridge.cjs`
- **Severity**: LOW
- **Description**: The entire Electron native torrent backend (1020 lines) has zero test coverage. This is the most security-critical and complex part of the application.
- **Recommendation**: Add integration tests for `TorrentBridge` using a mock WebTorrent client. At minimum, test: input validation, session management, error handling, concurrent ffmpeg limits.

### 29. Windows CI Build Doesn't Run Tests
- **File**: `.github/workflows/build.yml:87-88`
- **Severity**: LOW
- **Description**: The Windows build job only runs `type-check` but not `unit tests`. The Linux checks job runs tests, but type-check on Windows doesn't guarantee test pass on that platform.
- **Recommendation**: Add `npm run test` to the Windows build job, or note that tests are covered by the Linux checks gate.

### 30. Unused Type Exports
- **File**: `types.ts:48-73`
- **Severity**: LOW
- **Description**: `TorrentSourceMessage`, `ChatMessage`, `PeerRole`, `PeerConnectionState`, `Peer` are exported but `TorrentSourceMessage` is redefined locally in `P2PService.ts:12-17` (identical structure). `ChatMessage` interface has different fields than the actual chat message objects used in `App.tsx`.
- **Recommendation**: Remove duplicate/inconsistent type definitions. Use shared types consistently.

## Architecture / Technical Debt Observations

### A1. Monolithic App.tsx (1047 lines)
The App component handles: P2P lifecycle, torrent lifecycle, sync, chat, UI state, routing, modals, keyboard shortcuts, Electron IPC coordination. This makes testing extremely difficult and is the root cause of many state synchronization bugs.

**Recommendation**: Extract custom hooks: `useP2PConnection`, `useTorrentLoader`, `useSyncService`, `useChat`. Keep App.tsx as a composition layer.

### A2. Dual State Management Pattern
As noted in issue #8, state is split between `useState` hooks, `RoomStateContext`, and `useRoomState` refs. This inconsistency is the #1 source of potential sync bugs.

**Recommendation**: Adopt a single state management approach. Recommended: Zustand store (mentioned in SPEC.md but not used).

### A3. No Error Recovery Strategy
When the P2P connection drops, the app shows "Connection lost" but doesn't offer reconnection for the host role. Guests have auto-reconnect (good), but hosts don't.

**Recommendation**: Add host reconnection on PeerJS `disconnected` event (currently `P2PService.ts:516` only reconnects guests).

### A4. Inconsistent Error Propagation
Electron IPC errors are thrown as `new Error("...")`. P2P errors are emitted as events. Torrent errors use the EventBus pattern. Sync errors are silently caught. This makes debugging difficult.

**Recommendation**: Standardize error handling across all services with a unified error type and handling strategy.
