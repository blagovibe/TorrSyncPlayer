# Дизайн: Tauri-фронт — окно целиком на Rust

- Date: 2026-11-17
- Status: approved (owner answers recorded 2026-11-17; owner approved 2026-11-17)
- Owner decisions (2026-11-17): Tauri shell + embedded web frontend;
  full parity in the first release; all three platforms; rooms rewritten in
  Rust on rust-libp2p; delete the Go frontend once parity ships; protocol v3,
  no wire compatibility with the Go build. Room "done" = restored CI tests
  (room of three, divergence ≤ 1 s, rendezvous ≥ 90 % of 20 runs ≤ 90 s);
  the live public-DHT nightly series stay a post-release concern. Visual
  work ships as one RC, then a big error-fix pass. No deadline; order of
  phases follows risk (room first). Frontend is vanilla TS + CSS, no bundler.
  Test bar for new code: mechanisms covered (room state machine, buffer math,
  obvious-file, integration tests ported), UI verified by eye and screenshots;
  public-DHT live series remain a CI artifact, not a release gate.

## Зачем это всё

Владелец после v0.4.13 посмотрел на приложение и сказал, что оно ему
абсолютно не нравится: «Fyne-оболочка целиком: рамка, виджеты, шрифты,
иконки, тень, полные состояния», и «всё выглядит кучей, нет воздушности».
Это не вопрос вкуса к конкретной палитре — это приговор классу виджетов.
Нативный рендер Fyne не умеет: скруглённые панели с настоящей тенью,
backdrop-blur поверх контента, произвольную типографику, hover/press
state-переходы, настоящие анимации, layout как в сетке. Всё, что
предлагают референсы (Apple Vision Pro YouTube, Netflix home) — это
скоуп, за который Fyne никогда не заплатит.

Вариантов было три, выбран один:

**A — Tauri 2** (выбран). Ядро на Rust: дочерний процесс с бэкендом, HTTP
клиент, mpv-IPC, трей, файловый диалог, настройки; отрисовка — веб-view
(CSS/TS), где все визуальные приёмы из референсов доступны напрямую.
**B — egui** — честный нативный-Rust рендер, но каждый компонент рисуется
руками, и стеклос/тени/размытие остаются «как в Fyne, только лучше».
**C — Rust UI + Go-sidecar для комнат** — компромисс; отвергнут владельцем:
он хочет, чтобы новое решение было цельным, без второго языка в окне
(протокол v3 — герметичный, без совместимости со старым Go-кодом).

## Что это заменяет

`frontend/` (Go, Fyne, ~10 500 строк без тестов) + его тесты. Уходит целиком.
Остаётся: `backend/` (Go-бэкенд без изменений), `crates/` новый Cargo-воркспейс
(или `app/` — каталог сверить по вкусу, см. «Открытые вопросы»), пакетный
скрипт релиза (адаптируется). Репозиторий остаётся одним.

## Цели

1. Приложение выглядит как в референсах: floating-панели, backdrop-blur,
   сетка постеров как в Apple TV, hero с CTA «Смотреть» как в Netflix home.
   Не «Fyne с лучшими цветами», а другая категория.
2. Полный паритет с Go-фронтом на момент выпуска: добавление торрентков
   (магнит и .torrent), полка постеров, плеер (mpv), дорожки и субтитры,
   выбор файла, комната (создать/войти/выйти, ростер), настройки, трей,
   диагностика, язык (en/ru), первичная настройка хранилища, горячие
   клавиши, закрытие-в-трей.
3. Комнаты работают на Rust: DHT/rendezvous/relay, handshake доступа,
   синхронизация паузы и позиции — как в Go-версии, но переписано целиком.
   Протокол — v3, совместимость со старыми Go-пирами не гарантируется.
4. Три платформы в первом релизе (Windows, macOS, Linux AppImage) — то же,
   что выпускает текущий CI.

## Не-цели

- Бэкенд не переписывается. Вообще. Клиент — его HTTP API на 127.0.0.1.
- Обновление приложения (auto-update) — v2, не входит.
- Мобильные платформы.
- Смешивание комнат Go↔Rust (протокол v3, это решение владельца — см. выше).

## Анти-цели (регрессии)

- Обрыв синхронизации паузы/позиции в комнате хуже, чем было (≤ 1 s).
- Пауза mpv не доходит до всех участников немедленно.
- Буфер-репортинг backend'у перестаёт работать → приоритеты на куски
  сломаются.
- Трей не появляется / закрытие окна убивает загрузку.
- Выбор файла в комнате иначе, чем у хоста — рассинхрон с протокольной
  логикой (в Rust-версии dedikte host-authoritative logic).
- Ошибки, которые были видны людям в диагностическом логе, становятся
  немыми.

## Ограничения и условия

- Windows-машина владельца — единственная живая проверка. Сборки должны
  проходить на ней; CI — на runners (windows/macos/ubuntu), как сейчас.
- mpv поставляется рядом как сейчас (бандл внутрь zip/DMG/AppImage).
- WebView2 на Windows 10/11 — предустановлен в актуальных системах.
  На старых — сообщение при старте; bundle его не тащит (MSI/MSIX — другое
  пространство). Linux: WebKitGTK — зависимость пакетной сборки.
- Боковой эффект: пакет сборки меняется с `cmd/build` (Go) на `cargo tauri build`,
  но внешние ассеты (mpv, каталог libmpv при tauri bundler), иконки, NOTICE
  собираются так же, теми же шагами — адаптируется.

## Форма приложения

```
Tauri shell (Rust)
 ├─ backend child process (неизменённый TorrSyncPlayer-backend; на старте, порт и токен как сейчас)
 ├─ window (frameless или кастомный chrome вместо системной рамки)
 │    └─ frontend (TS/HTML/CSS): экраны, состояние, ROP данных через fetch() POST/GET на http://127.0.0.1:port
 │         ├─ what flows from Go backend: torrents list, files, select, magnet, buffer position, streams
 │         └─ what Tauri does itself: tray, window close/hide, file open dialog, settings.json read/write, diagnostics
 │            (the backend owns nothing of these; settings.json lives in the shell, as it does in the Go frontend)
 ├─ room (Rust module, rust-libp2p)
 │    ├─ DHT rendezvous (IPFS kademlia) + circuit relay v2 autorelay
 │    ├─ Noise + Yamux transport, identify, ping
 │    ├─ protocol /torrsync/sync/3.0.0 (newline-delimited JSON, как v1/v2, но другой protocol ID)
 │    ├─ admission handshake: HMAC от (password, key) из инвайта — как v2 по форме, но без совместимости
 │    └─ host authority прописывается: host назначает магнит и паузу; гости сходятся ≤ 1 s
 └─ diagnostics: torrsyncplayer.log рядом с настройками (как сейчас),
      backend's lines that start with "backend: "
```

## Компоненты, которые должны существовать на Rust стороне

### Прогин бэкенда к окну (неизменён)
- HTTP API уже есть и работает — Rust-клиент это маленький HTTP-клиент:
  GET / POST / DELETE /api/v1/torrents, /files, /select, /magnet, /subtitles,
  POST /api/v1/torrents/{id}/buffer/position, GET /api/v1/version, /api/v1/torrents/{id}/buffer/info.
  mpv получает тот же token в http-header-fields. Это переиспользуется без изменений.
- Бэкенд поднимается с переменной окружения `CORS_ORIGINS`, в которую перечислены
  origin'ы Tauri-окна (`tauri://localhost`, `http://tauri.localhost`, `http://localhost:1420` для dev) —
  иначе вебвью не сможет читать ответы (бэкенд держит allow-list, как и сейчас).

### mpv-клиент (Rust, вместо player/)
- Запуск mpv с флагами как сейчас (--input-ipc-server=.\pipe\torrsync-<pid>,
  http-header-fields, --no-input-default-bindings, subtitles через HTTP API —
  mpv тянет субтитры сам).
- IPC-клиент: подключение к именованному каналу (\.\pipe\torrsync-<pid> на
  Windows, $TMPDIR/torrsync-<pid>.sock на unix) — через tokio::net::windows
  либо явный CreateFileW через windows crate (см. риски), запросы:
  loadfile/pause/play/seek/get_property (pause, position, duration, volume,
  track-list, sub-track, audio-track), observe_property, обсервёрные события.
- Порт следствий: буфер-репортинг теми же semantics, те же 2 Гц — mpv-позиция
  в секундах × размер файла в байтах ÷ длительность (room.BytePosition);
  фронтенд шлёт POST /buffer/position; гости сообщают свою буфер-отсечку в комнату.
- Порт obvious-file логики из Go (один файл / явно доминирующее видео) в Rust.

### Комната (Rust, rust-libp2p) — самый дорогой компонент
- Клиент: noise/yamux/identify/ping, DHT (IPFS kademlia), relay v2 autorelay,
  rendezvous с ключом того же формата (можно переименовать в v3-формате —
  правило "admission by invite" сохранить), протокол потоков
  `/torrsync/sync/3.0.0`, JSON-строки через `libp2p-swarm`.
- Handshake: как в Go (HMAC от инвайта), но можно обновить и имя — главное
  не совместить с Go протоколом (v3, no interop).
- Поведение комнаты (cooродинация): Magnet начинает комнату;
  хост-эликция по истории (здравый смысл Go); пауза/позиция — ведёт хост;
  при отставании участника хост останавливает себя сам (sync-the-room-stop).
  Буферные отчёты участников (кто из гостей пуст) → хост тоже встаёт.
- Миграция: тому, что было в Go protocol.go — пересобрано по отработанной
  схеме, протокол v3; версия протокола 14 или просто 3 — деталь.
  Тестируется теми же интеграционными тестами: a room of three is a room,
  not a pair; rendezvous ≥ 90 % of shots ≤ 90 s; расхождение ≤ 1 s.

### Прочие части CL жалкие
- Настройки: тот же settings.json (language, darkTheme, storageMode,
  dataDir, displayName, bootstrap, relays, playerBinary) + чтение флагов
  (--lang, --bootstrap, --relays, --dark-theme) — чтобы не ломать UX тестам.
- Трей: tauri tray-icon, меню (открыть/настройки/выйти) как сейчас.
- Закрытие карточки в трей; без трея — выход.
- Горячие клавиши: Ctrl+L (сфокусировать поле), Ctrl+R (обновить), Ctrl+,
  (настройки).
- Языки: en/ru каталоги как сейчас, встроены в бандл; поиск перевода с
  fallback на английский; свидетельство `lang` провайдера удалено — WebView
  сам перевода не требует.
- Диагностика: тот же torrsyncplayer.log с префиксом backend:, те же
  бандлы: версия, путь к mpv, OS/arch, хвост лога — собираются оболочкой,
  backend endpoint'а для этого не существует и не делается.
- Первичная настройка хранения (в-памяти vs диск) — тот же диалог.

## Что проверяем

- Спайк (не релиз): Tauri-окно + spawn Go-бэкенда + /api/v1/version живого
  процесса в строке UI; mpv-пайп отвечает на get_property pause/duration;
  тёплый клик Play выполняет loadfile. Цель — увидеть, что тулчейн жив,
  воспринимается визуально и не рушится на этой машине. Это не этап плана,
  это разведка, которую пишет исполнитель до фазы 1.
- Фазы дальше — только после того подтверждения: фаза 1..N по плану.
- Интеграционные тесты: порт a-room-of-three, расхождение, rendezvous;
  на Windows CI они должны работать (есть и сейчас).
- Визуальная проверка: владелец на своей машине видит релиз-кандидата.

## План работы (фазы, рисунки в плане)

0. Разведка: спайк (см. выше). Решение по нему — жить ли вообще.
1. Фан-каркас: Tauri-приложение, спавн бэкенда, HTTP-клиент, очередь,
   окно с шеллом; бэкенд запускается, версия видна, клиент настраивается.
2. Комната (фаза 2 — раньше, по решению владельца: порядок по риску):
   discovery, handshake, хост-магнит, синхрон-пауза, ростер,
   гость поднимает торрент по магниту, миграция хоста при обрыве;
   интеграционные тесты (Room of Three и др.) зелёные на CI до перехода дальше.
3. Библиотека: макет полки постеров, добавление по магниту и
   .torrent; один файл очевиден, Play работает, mpv-канал жив.
4. Плейбэк: буфер-репортинг, слайдер, громкость, дорожки, субтитры.
5. Настройки, первичный вопрос хранилища, диагностика, трей, выход,
   горячие клавиши, локализация.
6. Упаковка: three ОС; релиз v0.5.0-rc1; приёмка на машине владельца —
   один заход, потом большая работа над ошибками.
7. Удаление Go-фронта. CHANGELOG / доска / релиз v0.5.0.

## Открытые вопросы (не блокируют черновик)

- Каталог: `app/`, `tauri/` или `frontend/` (переименованный)? Определяется
  тем, что tauri ожидает `src-tauri/`; `frontend/` опустошается.
- Дизайн конкретного окна (геро, сетка постеров) — отдельная фаза и серия
  скринов, не предмет этого документа.
- Обновление приложения (auto-update) — не в этой итерации.
- MSIX/app bundles vs ZIP/DMG/AppImage — регламент релиза менять не нужно.
- Подписи бинарников (codesign) — не блокируют релиз rc1 на машине владельца.

## Риски

1. **mpv IPC в Rust на Windows** — именованные каналы создаются mpv, окно
   подключается как клиент; синхронные вызовы — не вопрос перехода, но
   ошибки трансляции ломают клиента целиком. Спайк фазой 0 это решит
   до того, как что-нибудь построено.
2. **WebView2 runtime** — если на чистой Windows нет runtime, окно не
   поднимется и мы увидим это только на релизе; mitigation: проверить на
   другой машине владельца + инструкция/загрузчик.
3. **Компиляция rust-libp2p** — тяжёлый dep tree, первые сборки долги;
   кеш на CI есть.
4. **Совместимость протокола комнаты v3** — полная замена; старые Go-пользователи
   не подключаются. Сознательный выбор владельца.
5. **WebKitGTK в Linux-сборке** — релизный образ должен включать
   зависимости webkit2gtk, иначе начинается «почему не запускается у других».
6. **Тестовое покрытие** — старые интеграционные/платформенные тесты (a room of
   three, divergence, rendezvous 90%) должны быть восстановлены в Rust, иначе
   регрессии не будут пойманы CI.
7. **rust-libp2p — большое дерево зависимостей** (сотни крейтов). Первая сборка
   на холодном кеше — долгие минуты; CI обязательно кэшировать target/ и registry.
8. **Один RC с полным фикс-фронтендом** — по решению владельца ошибки фиксим
   пачкой в конце; поэтому фаза 0 (спайк) обязательна: она единственное
   дешёвое доказательство, что тулчейн/пайпы/спавн/вебвью живут до того,
   как мы инвестируем в фазы 1–7.
